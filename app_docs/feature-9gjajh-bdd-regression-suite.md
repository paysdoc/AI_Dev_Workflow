# BDD Regression Suite

## Overview

`features/regression/` is the permanent, executed BDD test suite for ADW. It contains feature files covering the full SDLC surface matrix (orchestrators, phases, edge cases, smoke paths), a typed Cucumber World, shared step definitions, and the vocabulary registry that governs which per-issue scenario patterns are eligible for promotion into this suite. Two supporting layers make the suite hermetic: `test/mocks/` (the mocked GitHub API, git remote, and Claude CLI that step definitions run against, wired together by a composition-root test harness) and the Docker-based runner (`test/Dockerfile` + `test/docker-run.sh`) that re-executes the suite in a container, in a writable copy of the read-only mounted checkout, as the `docker` job of the daily regression workflow.

## Responsibilities

- Maintain `vocabulary.md`: the canonical registry of regression step phrases with their semantics, execution pattern (`subprocess`, `phase-import`, `mock-query`), and assertion targets. Defines the rot-detection rubric (phrases must assert observable system behavior, not source-code properties).
- Define five observable assertion surfaces: state files, recorded HTTP requests (mock server), git artefacts, exit codes, and log streams.
- Define three execution patterns: subprocess (spawns orchestrator binary), phase-import (imports a phase function directly), and mock-query (inspects recorded calls only without running a subprocess).
- Maintain `features/regression/smoke/` — high-level end-to-end smoke scenarios (`adw_sdlc_happy_path`, `cron_trigger_spawn`, `pause_resume_rate_limit`, `cancel_directive`, `promotion_commenter`, `promotion_mover`, `promotion_threshold_auto_ramp`, `adw_chore_diff_verdicts`).
- Maintain `features/regression/surfaces/` — the SDLC surface matrix: 35 row-numbered `.feature` files covering each orchestrator × phase × happy/edge-case combination from `adwPlan` workflow init through `adwDocument` and `adwSdlc` cron scenarios.
- Maintain `features/regression/multilang/` — Python fixture e2e regression.
- Maintain `features/regression/upgrade/` — promoted single-scenario-file features for the `adwUpgrade` lane (e.g. `feature-729.feature`), each paired with its own scenario-specific step-def file directly under `features/regression/step_definitions/` (not folded into the shared given/when/then registries).
- Maintain `features/regression/hashing/` — promoted single-scenario-file features for the framework content-hash lane (e.g. `feature-537.feature`, the `computeFrameworkHash` deep-module contract), following the same subject-named-subdirectory-plus-flat-step-def shape as `upgrade/`.
- Maintain `features/regression/pause-queue/` — the promoted `feature-910.feature` (34 scenarios): the pause queue's reset-time wait. It covers the real pause path recording `rateLimitType` and an ISO 8601 `resetsAt` (inventing neither), the pure decider's decision table, the scanner running no probe before reset, strikes only on confirmed non-rate-limit failures, eviction leaving the workflow `paused` with `## Retry`, a legacy-entry row, and the #840 early-eviction replay plus an end-to-end pause → wait → resume journey.
- Maintain `features/regression/pause-queue/` — promoted `feature-911.feature` (35 scenarios): per-repo pause-queue ownership (the pure decider's `skip_not_owner` rule), each cron acting only on its own entries (including the 2026-09-22 incident replay), remove-before-spawn resume with re-queue plus one strike on a failed spawn, a real `trigger_cron.ts --target-repo` process, and the type-check / git-gh-guard backstops. Every assertion reads a runtime artefact (decider action, `agents/paused_queue.json`, fixture launch logs, recorded probe calls, mock-API comments).
- Maintain `features/regression/webhook/` — the promoted `cron_on_every_event.feature` (`@regression @webhook`, six scenarios, 11 examples): the webhook ensures a cron for the repository of every accepted event. It drives the real exported `dispatchWebhookEvent(req, res, rawBody, mintEventBoundary)` in-process with a fake request, a recording response and a fake boundary whose `providers` getter throws, and asserts only on the recorded response, the recorded launches and the cron registry record. Rows: an approved signed review launches exactly one cron and nothing else; an outline over six event/action pairs; an already-running cron is left alone; a wrong signature gets 401; invalid JSON gets 400; no repository gets 200 — the last three launch no cron. Its step definitions are `step_definitions/webhookCronSteps.ts` (G-WH1–3, W-WH1–5, T-WH1–6) and its `@webhook or @adw-961` hooks save, neutralise and restore `GITHUB_WEBHOOK_SECRET`, the GitHub App variables, `SLACK_WEBHOOK_URL`, `PATH`, `agents/.auth_gate`, and each touched cron registry entry and log. Deliberately uncovered: ordering against `ensureAppAuthForRepo` (no longer called), `/health`/404/405 (answered by the HTTP listener, `/health` runs a real `claude -p` probe), and `issues` opened/closed and `pull_request` closed (hand work to a provider).
- Provide `support/launchRecorder.ts`, the shared, hook-free launch recorder: a `/bin/sh` `bunx` shadow that records its NUL-separated argv and exits at once, put first on `PATH` only for the synchronous dispatch (`withLaunchRecorderOnPath`), with query helpers (`recordedLaunches`, `settleLaunches`, `waitForLaunch`, `isCronLaunch`, `isCronLaunchFor`, `describeLaunches`, `disposeLaunchRecorder`). A cron launch is a record naming `adws/triggers/trigger_cron.ts` and `--target-repo <repo>`. Later slices reuse it.
- Own the pause-queue harness step definitions, relocated together with the scenario so nothing depends on swept per-issue files: `feature-910.steps.ts`, `feature-911.steps.ts`, `realCronProcess.ts`, `feature-902.steps.ts` (injected `probeStub`, the Claude-CLI probe-answer step) and `feature-902-queue.steps.ts` (queue-file save/restore, `gh`/`bunx` shadows, mock-infra hooks tagged `@adw-902/907/910/911` or the promoted features' own `@pause-queue-reset-time` / `@pause-queue-ownership`). Per-issue step files (907, 908, 909-tooling) import them via `../../regression/step_definitions/…`.
- Provide `RegressionWorld` (extends Cucumber `World`): typed container for `MockContext`, `lastExitCode`, `worktreePaths`, `prsByBranch`, `targetBranch`, `harnessEnv`, Python fixture state, the per-scenario `gitGhGuardResult` (exit code + output of W16, so T34 can never pass on a previous scenario's run), and scenario proof results.
- Provide shared step definitions: `givenSteps.ts` (G1–G26 setup vocabulary), `whenSteps.ts` (W1–W16 invocation vocabulary, W16 = `the git/gh guard is run across the repository`), `thenSteps.ts` (T1–T34 assertion vocabulary, including T22 `the ADW TypeScript type-check passes`, T25 `the resumed comment is recorded on issue {int} in the target repository {string}` and T34 `the git/gh guard reports no violations`), `pythonFixtureE2ESteps.ts` (G-PY1, W-PY1, T-PY1 through T-PY6).
- Provide scenario-specific step-def files for promoted single-scenario features (e.g. `feature-729.steps.ts`) that keep their own module-scoped state and tag-scoped `Before`/`After` hooks (e.g. `{ tags: '@upgrade-regen' }`) rather than sharing the generic registries.
- Provide `support/hooks.ts` for test lifecycle setup/teardown; it initializes the mock infrastructure before each scenario, tears it down after, and sets the suite's 60 s default step timeout (`setDefaultTimeout(60_000)`).
- Provide the mock infrastructure (`test/mocks/`) that every step definition runs against: `test-harness.ts` is the composition root, exposing `setupMockInfrastructure(config?)` / `teardownMockInfrastructure()` for `Before`/`After` hooks, `resetMock()` to clear mock-server state between scenarios without restarting it, `setupFixtureRepo(fixtureName)` / `teardownFixtureRepo(ctx)` to materialize a real `git init`-ed working directory from a `test/fixtures/{fixtureName}/` template, and `createGitMockDir` / `cleanupGitMockDir` to stand up the temp directory holding the `git` wrapper that delegates to `git-remote-mock.ts`. The mocked services are the GitHub API server (`github-api-server.ts`), the Claude CLI stub (`claude-cli-stub.ts`), and the git remote mock. The git mock appends one `{ subcommand, args, cwd }` JSONL line per intercepted network subcommand to the file named by `MOCK_GIT_LOG` (helpers in `gitMockLog.ts`: `appendGitMockInvocation`, `readGitMockLog`); `setupMockInfrastructure` creates that file per setup under an `adw-git-log-` temp directory, exposes it as `MockContext.gitLogPath`, and teardown removes it. ## Contracts & Invariants

- Every step phrase used in a regression scenario must appear in `vocabulary.md`; phrases that reference source file content (not artefacts) violate the rot-detection rubric and must not be added.
- A promoted scenario's step-definition dependency closure moves with it, without rewriting moved files' relative imports; both `features/regression/step_definitions/` and `features/per-issue/step_definitions/` are three levels deep, so specifiers resolve unchanged. Importers that stay behind are repointed. The per-issue sweep's sibling rule (`startsWith('feature-N.')`) would otherwise orphan `feature-902-queue.steps.ts` and crash the whole Cucumber load.
- Hook compatibility for the moved harness: `setupMockInfrastructure()` is idempotent, so its `Before` runs first and the `@regression` `Before` reuses the running mock; the `@regression` `After` restores `PATH` (dropping the `gh` shadow) and stops the mock before the harness's own file/process cleanup.
- `RegressionWorld.harnessEnv` is the canonical env overlay for subprocess invocations; steps must not mutate `process.env` directly.
- Scenarios tagged `@regression` are part of the regression suite; `@smoke` additionally marks the subset run in fast CI; `@python-e2e` tags the multilang fixture test.
- The surface matrix numbering is load-bearing for test organization; gaps in the sequence (e.g., no row-28) reflect deliberately removed scenarios.
- `W1` (subprocess invocation) populates `World.lastExitCode`; assertion step `T5` reads this field; they must be used together. `T5` always compares `World.lastExitCode` (which is `-1` until a subprocess step records an exit code), so "exited 0" fails when nothing ran.
- `T1` (`the state file for adwId {string} records workflowStage {string}`) asserts on runtime artefacts only, whichever hooks ran: it reads `agents/<adwId>/state.json`, or failing that `.adw/state.json` under the worktree G6/G11 registered for the adwId. It fails naming every path it tried when neither exists, and fails when `workflowStage` differs. No shared step reads `adws/` source files or branches on `mockContext === null`.
- A When step never passes by doing nothing: `W1`, `W9` and `W10` return `'pending'` unless the scenario carries `@subprocess` and so has a harness.
- The install phase never fails (`executeInstallPhase` catches every error), so row 18 proves only the wiring from phase name to `install_completed`. The commit agent throws on failure and the stub's `onCommitCommand` fails on a clean worktree, so row 26's manifest answers `/commit` with a `byCommand` allow-empty commit.
- No stub manifest may write a file a Then step reads as the system's output: the refusal guard rejects `.adw/state.json`, `agents` and everything under it, and any path resolving outside the worktree (`./agents/x` and `src/../agents/x` included), over top-level edits, deletes and every `byCommand` entry's edits. Manifests may still edit `.adw/commands.md`, `.adw/project.md`, `.claude/**`, `specs/**` and `src/**`, except that row manifests must not touch `.adw/` or `.claude/` because the plan commit guard would fail the plan phase.
- Surface phase rows assert only artefacts the real run produces: the phase outcome, stage comments recorded by the mock server, the top-level state file, the git-mock log and the spawn-lock file. adwPlan, adwChore and adwPlanBuildDocument pass no phase name to `runPhase`, so their rows (02, 03, 13, 14, 27) assert outcome and comments, not T1; adwBuild passes `'build'` and `'install'`, adwPatch `'build'` and `'pr'`, adwPrReview its three `pr_review_*` names, so those rows assert T1 `<name>_completed`. Rows are titled for the orchestrator that runs the phase in production (row 12 adwPatch, row 18 adwBuild, row 27 adwPlanBuildDocument); row 35 is titled for the setup itself because no orchestrator calls it.
- `mockForgeProviders` implements `commentOnIssue`, `moveToStatus`, `getDefaultBranch` (always `main`, the branch G11 commits), `createPullRequest` (POST `/pulls`), `commentOnPullRequest` (POST `/issues/<pr>/comments`) and `setSecret` (PUT Actions secret, value unsealed); every other port method throws `mockForgeProviders: <method> not supported`. Every method that reaches the server throws when it is answered with status 400 or more. In-process code never builds a production launch boundary or reads `GITHUB_PAT`.
- Subprocess children are hermetic: they reach GitHub only through the `gh` shadow, Claude only through the stub, and use a temp `HOME` and `TARGET_REPOS_DIR`. The shadow directory is prepended to the child's `PATH` only, never the Cucumber process's own. Script paths passed to children are absolute and real (`realpathSync`), because `adwMerge.tsx`, `adwChore.tsx` and `adwUpgrade.tsx` run `main()` only when `import.meta.url` equals `file://${process.argv[1]}`, so a relative path exits 0 having done nothing.
- Harness scratch state — on the host and inside the Docker leg — must live under `os.tmpdir()` and never under `process.cwd()`, because on the host the cwd is the developer's checkout: `createGitMockDir` and `setupFixtureRepo` both use `mkdtempSync(join(tmpdir(), '<prefix>-'))`. ADW's own runtime state (`agents/`, `agents/paused_queue.json`, `agents/.auth_gate`, `logs/`) is cwd-relative by design, so the Docker leg gives it a writable cwd by running the suite in the `/tmp/bdd/workspace` copy, never in the `/workspace` mount (`-v "${REPO_ROOT}:/workspace:ro"`).
- The anonymous volume over `/workspace/node_modules` hides the host's modules, so the copy starts with an empty `node_modules` and `bun install --frozen-lockfile` (run in the copy, per the Dockerfile `CMD`) installs fresh every run. The volume's mount point must already exist in the read-only checkout, because Docker cannot create it there, which is why the `docker` job runs `bun install` on the runner first.
- The suite runs in a `cp -R` copy owned by the container user, so git accepts it. `cp -a` would keep the mounted files' host UID, and git ≥2.35.2 would refuse the copy as "dubious ownership".
- Both jobs are time-bounded: `host` and `docker` each set `timeout-minutes: 30`, so a hang in either leg costs minutes of runner time, not GitHub's 360-minute default. Two full runs no longer share one budget.
- `TEST_RUNTIME=docker` is set as an image `ENV` so code under test (and the mock harness) can detect the container runtime if it ever needs runtime-specific behavior, though current code intentionally avoids branching on it in favor of the runtime-agnostic `os.tmpdir()` scratch location.
- `teardownMockInfrastructure()` is unconditional and idempotent: it has no `isSetUp` guard — every step it performs (`stopMockServer()`, `cleanupGitMockDir()`, env restore) is individually guarded on the resource it releases (`activeServer`, `gitMockTempDir`, `savedEnv`), so calling it before, during, or after a successful setup is always safe and never double-closes or throws.
- `setupMockInfrastructure()` is crash-safe: everything after `savedEnv` is captured runs inside a `try/catch`; any failure (e.g. the git-mock temp dir can't be created) triggers `await teardownMockInfrastructure()` before the error is rethrown, so a mock server that started listening is always stopped even if a later setup step throws.
- Environment mutation by `setupMockInfrastructure` is fully reversible: `savedEnv` snapshots every variable it is about to overwrite; teardown restores each one (or deletes it, if it was previously unset) rather than assuming a fixed baseline.

## Configuration

The regression suite runs via Cucumber.js. Configuration (paths, require globs, tags) is in the project's `cucumber.js` or equivalent config file.

- `MOCK_FIXTURE_PATH`, `MOCK_STREAM_DELAY_MS` — control the Claude CLI stub's canned JSONL output and streaming delay; `MOCK_STREAM_DELAY_MS` is forwarded into the Docker container if set on the host.
- `MOCK_RESPONSE=rate-limited` — asks the stub for its rate-limited response on a direct spawn; `MOCK_RATE_LIMIT_RESETS_AT` (epoch seconds) and `MOCK_RATE_LIMIT_TYPE` override its defaults (now + 300s, `"five_hour"`). A manifest `response` block takes precedence over all three, because `getSafeSubprocessEnv()` drops every `MOCK_*` name from a production spawn's environment — only the manifest marker-file path survives that allowlist.
- `<worktree>/.adw-stub-invocations` — a best-effort counter file the stub reads/increments only when a manifest `response.limitedInvocations` is set, so the first N invocations are rejected and the next answers normally; a missing or corrupt file counts as 0.
- `<worktree>/.adw-stub-manifest.json` — the marker the stub reads: it searches its cwd and every directory above it, the nearest wins (`test/mocks/stubMarker.ts` `findStubManifestMarker`), and every harness marker lives under `os.tmpdir()`. The subprocess harness puts the row's manifest at the temp `TARGET_REPOS_DIR` root, above every worktree a run creates. Production spawns drop `MOCK_*` names, so the in-process harness copies the manifest G3 named to this path (stub delivery) and points `CLAUDE_CODE_PATH` at the stub, calling `clearClaudeCodePathCache()`.
- `GH_HOST`, `GH_TOKEN`, `MOCK_GITHUB_API_URL`, `MOCK_SERVER_PORT` — set by `setupMockInfrastructure` to route `gh`/HTTP calls to the mock server; restored by teardown.
- `ADW_GH_STATE`, `ADW_GH_LOG` — the `gh` shadow's forge-state file and write log; both must be set or the shadow exits 1.
- `CLAUDE_CODE_PATH` — overridden to point at `claude-cli-stub.ts` for the duration of the mock session.
- `REAL_GIT_PATH` — the real `git` binary path, resolved before `PATH` is modified, so `setupFixtureRepo` and other real-git callers can bypass the mock wrapper.
- `BDD_TAGS` (default `@regression`) — the Cucumber tag filter used by the Docker leg, overridable via `--tags` on `docker-run.sh` or `-e BDD_TAGS=...` directly.
- `--build` (flag on `docker-run.sh`) — forces an image rebuild even if `adw-bdd-runner:latest` is already cached.
- `--shell` (flag on `docker-run.sh`) — opens an interactive shell inside the container (entrypoint override) for debugging mount/permission issues. The shell opens in the read-only `/workspace`: the image's `CMD` does not run, so no copy is made.

## Gotchas

- G18 `the ADW codebase is checked out` (a deliberate no-op used by the Backgrounds of the hashing, upgrade and pause-queue features and many per-issue features) is defined once, in `step_definitions/givenSteps.ts`. Defining it a second time makes it ambiguous in every feature that uses it; deleting it leaves those Backgrounds undefined. No `.feature` file may sit outside the `cucumber.js` paths, or it is never run.
- `@webhook` scenarios must pick events that end in `ignored` without reaching a provider: provider-branch errors end in `reportWebhookEventFailure`, which posts to Slack. While `agents/.auth_gate` holds a record the review, review-comment and comment branches answer `auth_gate_set`, which is why the hook clears it and `T-WH1` asserts the exact body.
- In cucumber expressions `/` is the alternation operator; a literal `git/gh` in a step pattern must be escaped as `git\\/gh`.
- Any step that shells out to `tsc` must pass `--incremental false`: the root tsconfig is incremental and would otherwise write `tsconfig.tsbuildinfo` into the checkout, and a run of the suite must leave the checkout unchanged.
- The mock GitHub API server records real HTTP calls but cannot see GitHub App auth flows or `gh` GraphQL calls; scenarios that assert auth behavior must use `phase-import` pattern and call auth functions in-process.
- `RegressionWorld.worktreePaths` maps adwId to temp directories created per-scenario; these are isolated temp git repos, not the production worktrees directory.
- The Python e2e test (`@python-e2e`) depends on a fixture repo under `test/fixtures/` and requires the scenario proof pipeline to be functional; it is not a pure mock-query test.
- Step definitions for `W1` spawn real subprocesses; test isolation depends entirely on the `harnessEnv` overlay pointing processes at mock infrastructure rather than live GitHub.
- The built-in `adws/promotion/` automated flow has never successfully promoted a `features/per-issue/` scenario into this suite (no step-def relocation, no vocabulary registration, no `@regression` tag). Real promotions are done by hand: `git mv` the `.feature` and `.steps.ts` files, replace the feature-level `@adw-` tags with `@regression` and remove every scenario-level `@adw-` tag, and register the scenario's novel phrases in `vocabulary.md` — as done for `feature-729.feature` into `features/regression/upgrade/` and `feature-537.feature` into `features/regression/hashing/`.
- A promotion is not always a two-file move: when the step file imports sibling per-issue modules or relies on steps/hooks defined in other per-issue files, promote the whole dependency closure into `features/regression/step_definitions/` (contents untouched, moved together) and re-point remaining per-issue importers. `perIssueScenarioSweep.ts` deletes `features/per-issue/step_definitions/feature-N.*` siblings, so any harness left there breaks the promoted scenario when swept. Steps that live only in a sweepable file (e.g. T25) are moved, not copied, into the generic registries — a copy makes the phrase ambiguous.
- `vocabulary.md` registers the `@pause-queue-ownership` pause-queue phrases (G-PQ1–14, W-PQ1–5, T-PQ1–17) in their own section; the backstop phrases W16 and T34 sit in the generic When/Then tables. `W16`'s cucumber expression escapes the slash (`git\\/gh`) because `/` is alternation.
- The T1/T5/W1/W10 verdicts are proven by `features/per-issue/feature-960.feature`, whose step definitions write throwaway features and run them through Cucumber in a child process (always with a `--tags` filter, because cucumber-js merges CLI paths with the `paths` in `cucumber.js`). Never run a second Cucumber process alongside it from the same checkout other than that `spawnSync` child.
- Under `@regression`, feature-911 is wrapped by both the suite's `@regression` hooks and the moved `feature-902-queue` hooks; this is safe because `setupMockInfrastructure` returns the live context on a second call and `teardownMockInfrastructure` is a no-op the second time.
- Pause-queue scenarios share `agents/paused_queue.json` and spawn-lock files under the cwd and use real timers (overlapping-cycle and crash-on-first-launch rows use the ~2 s readiness window): never run two cucumber processes from the same checkout at once.
- A promoted scenario drops every `@adw-` tag — a regression feature never carries a per-issue tag — and any scenario-specific `Before`/`After` hook keyed on those tags is re-keyed to a descriptive tag added to the moved feature, so cleanup still scopes to that one feature after the move: the four promoted features use `@framework-hash` (`feature-537`), `@upgrade-regen` (`feature-729`), `@pause-queue-reset-time` (`feature-910`) and `@pause-queue-ownership` (`feature-911`). The pause-queue hooks keep their per-issue `@adw-910`/`@adw-911` alternatives for the rows still under `features/per-issue/` (`feature-902`, `feature-907`, `feature-908`), which carry those tags.
- The `@regression` mock infrastructure (`setupMockInfrastructure`) is transparent to promoted scenarios that only use local git subcommands (`init`, `add`, `commit`, `rev-parse`, `show`, `check-ignore`, etc.) — `test/mocks/git-remote-mock.ts` only intercepts network subcommands (`push`, `fetch`, `clone`, `pull`, `ls-remote`) and delegates everything else to real git.
- A setup failure that orphans a listening mock HTTP server used to hang the whole process (Bun's event loop stays alive on an open socket) — inside the Docker leg this silently turned a CI failure into a 6-hour job timeout before `setupMockInfrastructure`'s crash-safety and `teardownMockInfrastructure`'s unconditional-teardown invariants were added; each job's `timeout-minutes: 30` is now the backstop if a hang recurs.
- A hang inside the Docker container does not surface as a normal test failure — `docker run` simply never returns; without the job-level `timeout-minutes` backstop, GitHub's default 360-minute timeout would be the only thing that stops it.
- Inside the container, cwd, `REPO_ROOT` and the step definitions' `ROOT` all resolve to `/tmp/bdd/workspace`. An `EROFS` error at a path under `/workspace` therefore means something resolved a path against the mount instead of the copy.
- The Docker image has no ADW source baked in, so a stale cached image (`docker image inspect` hit, no `--build` passed) can mask source changes that aren't otherwise re-triggering `bun install` — pass `--build` when in doubt. The copy step lives in the image's `CMD`, so a change to `test/Dockerfile` needs `--build` or `bun run test:docker:build`.
- Both jobs fail on a pending or undefined scenario (Cucumber's default `strict`), so the daily run stays red while the smoke and surface `When` steps return `'pending'`. ADW's own test phase scores those scenarios as skipped (`classifyTestCase`).
- A phase's own `process.exit` (pause, timeout) is not a phase failure: the `phase run failed` Then requires `error` set and `exitCode` undefined.
- `postIssueStageComment` does not await `commentOnIssue`, so a forge that posts over HTTP would let the phase resolve before the comment is recorded; `mockForgeProviders` dispatches synchronously for that reason.
- `executeBuildPhase` throws without a committed plan; row 04 uses G-S1 `the worktree for adwId {string} has the plan for issue {int} committed on its branch`.
- The error response keeps `api_error_status: null`: a 401/429/529/5xx would classify as an auth, rate-limit, overload or server-error signal and send the run down the pause path's `process.exit`.
- A cron child reads the checkout's `agents/.auth_gate` and `scanAuthQueue` rewrites every `paused_auth` state in `agents/`, whatever its repository, so W10 refuses to start when any such state exists and the harness removes the auth gate for the scenario. The cron cadence variables are pinned to `1000000` so one tick never runs a sweep.
- Seeded cron issues must be older than the 5-minute grace period and carry an `adw:*` label (G4); G7 and G10 must not wipe what G4 and earlier Givens seeded.
- Run subprocess scenarios alone: never two Cucumber processes from one checkout, because the rows share `agents/`, `logs/` and spawn locks under the cwd.
- T6's callback must be `function (this: RegressionWorld, issueNumber: number)`; a leading `_this` parameter makes Cucumber treat the second as a callback and time out after 60 s.
- Row 32's G-PQ14 holder and its lock outlive the scenario unless G-PQ14 registers `releaseHeldSpawnLocks` on `World.cleanup`.
- The surface rows use fixed adwIds, and `agents/<adwId>/` lives in the checkout, which is why `buildConfigFor` clears it.
- `createGitMockDir`'s temp dir is prefixed `adw-git-mock-` and is unique per call (via `mkdtempSync`), so there is no fixed-name collision risk between concurrent setups.
- `test/fixtures/jsonl/envelopes/` is not just fixture data — `bun run jsonl:check` (see the JSONL Schema doc) validates every template in that directory against the committed schema and ADW's parsers, so a stub envelope change that drifts from the real CLI fails the same CI gate a fixture drift would.
- `test/mocks/__tests__/test-harness.test.ts` exercises the mock-infrastructure invariants directly (writable-location assertion via `os.tmpdir()`, teardown-always-closes-server by calling `startMockServer` directly before teardown, and setup-crash-safety by pointing `TMPDIR` at a non-existent path) — it's the fastest way to reproduce either bug deterministically without Docker.
