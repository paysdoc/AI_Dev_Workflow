# Git/GH CLI Guard

## Overview

This module enforces the GitContext PRD invariant that all `git` and `gh` shell-outs, all repo-identity resolution, and all provider/context construction must route through the `adws/gitContext/` core (for `git`), the `adws/providers/github/` forge adapter (for `gh`, via the core's executor), and the launch boundary (for provider/context construction). It is an AST-based standalone scanner wired into a dedicated CI workflow that fails the build on any of four independent rules: a direct `exec`/`spawn`/`execSync` of a `git …` or `gh …` command string outside the structurally-exempt packages (`git-gh-shellout`), a `gitContextForRepo(…)` construction fed cwd-derived identity instead of a threaded launch-boundary `GitContext` (`cwd-derived-identity`, #769), ad-hoc construction of a forge provider, the RepoContext factory, or a GitContext factory outside a file-scoped allowlist (`unsanctioned-construction`, #795), or a framework import reaching into a package that is supposed to extract cleanly (`extraction-readiness`, #816). As of #701, the `ALLOWLIST` machinery had been entirely removed — the `ALLOWLIST` const, the `allowed` Set, and the per-file skip are gone, and #769 introduced no path allowlist either. As of #792, the single-string `EXEMPT_PACKAGE_DIR` was replaced with a closed, named, two-entry `EXEMPT_PACKAGES` array: `adws/gitContext` (git core, may run `git`) and `adws/providers/github` (GitHub forge adapter, may issue `gh` commands by feeding command strings into the core's executor). As of #795, the entry point (`adws/checkGitGhGuard.ts`) shrank to discovery + the shellout rule + composition + the CLI, and the other rules moved into a small `adws/guard/` package — see **Module layout** below. As of #816, `extraction-readiness` serves `specs/prd/gitcontext-library-extraction.md`: it machine-checks that `adws/gitContext/` and `adws/providers/` (the two directories the PRD moves to a standalone library) can be extracted as a pure file move, by failing the build the moment an in-scope file imports anything outside that pair. The wrong path is now mechanically unrepresentable for shell-outs, identity re-derivation, ad-hoc construction, and framework re-entanglement alike.

## Module layout (#795, #816)

- `adws/checkGitGhGuard.ts` — the entry point. Owns `EXEMPT_DIR_NAMES`, `EXEMPT_PACKAGES`, `isExemptPackage`, `collectTsFiles`/`visitDir` (generalised with a `descend` predicate, #816), the `git-gh-shellout` rule (`walkNode`/`extractGitGhCommand`), `scanFiles`/`scanSource`, `collectExtractionScopeFiles`/`scanExtractionScope` (#816), and `main()` (stdout composition + the stale-entry ratchet + `process.exit`; the two report-block printers live in `adws/guard/guardReport.ts`, #816, to keep this file under the 300-line guideline). Re-exports `Violation`/`ViolationRule` from `adws/guard/violationTypes.ts` so no downstream import path changes.
- `adws/guard/violationTypes.ts` — the cross-rule `ViolationRule` (`'git-gh-shellout' | 'cwd-derived-identity' | 'unsanctioned-construction' | 'extraction-readiness'`) and `Violation` types, shared by the entry point and all rule modules.
- `adws/guard/identityRule.ts` — the `cwd-derived-identity` rule (#769), moved verbatim. Exports a single entry point `flagCwdDerivedIdentityUses(sourceFile)` that collects cwd-derived names internally, plus `CWD_DERIVED_IDENTITY_FNS` and `CONTEXT_CONSTRUCTOR_NAME` (consumed by the rename-detection test, AC3).
- `adws/guard/constructionRule.ts` — the `unsanctioned-construction` rule (#795): `PROVIDER_CONSTRUCTORS`, `CONTEXT_CONSTRUCTORS`, `GIT_CONTEXT_CLASS_NAME`, the `SANCTIONED_CONSTRUCTION_SITES` allowlist, `isSanctionedConstructionSite`, `flagUnsanctionedConstruction(sourceFile, relPath)`, `hasGuardedConstruction(sourceFile)`, and `findStaleSanctionedEntries(seenFiles)`.
- `adws/guard/extractionRule.ts` (#816) — the `extraction-readiness` rule: `EXTRACTABLE_SET`, `EXTRACTION_SCOPE`, `isInExtractableSet`, `isInExtractionScope`, `resolveImportTarget`, `collectImportSpecifiers`, `flagFrameworkImports(sourceFile, relPath)`. Pure — no filesystem access.
- `adws/guard/guardReport.ts` (#816) — stdout-only: `printSanctionedConstructionSites()`, `printExtractionScope(scannedCount)`. Extracted purely to keep `checkGitGhGuard.ts` under the line-count guideline; no behavioural change.

**The re-export contract is load-bearing.** `scanFiles` is imported from `adws/checkGitGhGuard.ts` by `feature-691.steps.ts`, `feature-769.steps.ts`, and `feature-792.steps.ts`; `collectTsFiles` by `feature-792.steps.ts`; `EXEMPT_PACKAGES`/`isExemptPackage` by the unit suite. None of these import paths changed — the module split (#795) and the #816 additions are purely additive. `collectExtractionScopeFiles`/`scanExtractionScope` are new exports (#816), consumed by `adws/guard/__tests__/extractionRule.test.ts`'s real-tree test and by `adws/__tests__/checkGitGhGuard.test.ts`.

## Responsibilities

- Walk all `.ts`/`.tsx` source files under the repo (excluding `node_modules`, `dist`, `.worktrees`, `.claude`, `features`, `test`, both `EXEMPT_PACKAGES` directories (`adws/gitContext/**`, `adws/providers/github/**`), and `*.test.ts` / `__tests__/**`)
- Parse each scanned file with the TypeScript compiler API (AST-based scan — comment text is never a false positive)
- **`git-gh-shellout` rule:** detect call expressions whose first argument is a string/template literal matching `/^(git|gh)(\s|$)/` — catches `execSync('git …')`, `execWithRetry(\`gh …\`)`, `execFileSync('git', […])`, injected `deps.exec(\`gh …\`)`, and any other call shape
- **`cwd-derived-identity` rule (#769, `adws/guard/identityRule.ts`):** two-pass per file. Pass 1 (`collectCwdDerivedIdentityNames`) collects the names of local variables whose initializer is a zero-argument `getRepoInfo()`/`readLocalRepoInfo()` call. Pass 2 flags any `gitContextForRepo(…)` call (bare identifier or property access) whose first argument is either an inline zero-argument read of one of those two functions, or an identifier collected in pass 1
- **`unsanctioned-construction` rule (#795, `adws/guard/constructionRule.ts`):** a file-scoped guard clause (`isSanctionedConstructionSite`) short-circuits sanctioned files to zero violations; everywhere else, flags a bare-identifier `new GitContext(…)` or a bare-identifier call to any name in `PROVIDER_CONSTRUCTORS` (`createGitHubIssueTracker`, `createGitHubCodeHost`, `createGitHubBoardManager`, `createGitLabCodeHost`, `createGitLabBoardManager`, `createJiraIssueTracker`, `createJiraBoardManager`) or `CONTEXT_CONSTRUCTORS` (`createRepoContext`, `mintBoundProviders`, `gitContextFor`, `gitContextForSync`, `gitContextForRepo`). Property-access callees (`deps.gitContextForRepo(…)`) are never flagged — an injected seam is the sanctioned pattern. Function declarations are never flagged, only call/new expressions.
- **`extraction-readiness` rule (#816, `adws/guard/extractionRule.ts`):** discovery is a SEPARATE walk (`collectExtractionScopeFiles`) over `EXTRACTION_SCOPE`'s entries that does NOT prune `EXEMPT_PACKAGES` — the only discovery in this module that looks inside them — but still applies `isScannable`, so `__tests__/**`/`*.test.ts` are excluded. For each in-scope file, every statically-resolvable import specifier is collected (`import`/`import type`, `export … from`/`export * from`, `import x = require(…)`, dynamic `import(…)`, `require(…)` — all literal-specifier forms; non-literal dynamic imports are ignored) and resolved against the importing file's directory (`@adws/*` maps to `adws/*`). A bare specifier (npm package, Node builtin, with or without `node:`) resolves to `null` and is always allowed. A resolved target outside `EXTRACTABLE_SET` (`adws/gitContext`, `adws/providers`) is a violation, printed in the same listing under its own `[extraction-readiness]` tag. `main()` additionally prints a dedicated "Extraction-readiness scope" block (`adws/guard/guardReport.ts`'s `printExtractionScope`) naming every `EXTRACTION_SCOPE` entry, its reason, and the issue that widened scope to include it.
- Exit `0` (pass) when no violations of any rule are found AND no allowlist entry is stale; exit `1` (fail) with a `path:line  [rule]  command` listing and a per-rule remedy line when violations exist, and/or a stale-transitional-entry listing when the ratchet fires
- Print `Git/GH CLI Guard — scanned N files (0 allowlisted)` on every run — the `(0 allowlisted)` literal is byte-identical to its pre-#795 form and preserves the capstone `(\d+) allowlisted` regex observable — followed by the two exempt packages and their roles, followed by a **sanctioned construction sites** block, followed by the **extraction-readiness scope** block (#816). **Neither the sanctioned-construction-sites block nor the extraction-readiness-scope block ever contains the substring "allowlisted"** — so the `(\d+)\s+allowlisted` regex (non-global; matches the FIRST occurrence in stdout) keeps matching only the original capstone line
- Run as `bun run lint:git-guard` and as the sole step in `.github/workflows/git-cli-guard.yml` (triggers on every `pull_request` and `push`)

## Contracts & Invariants

- **Structural exemption — closed, named, two-entry set (`EXEMPT_PACKAGES`, #792):** `adws/gitContext` and `adws/providers/github`. Neither directory is ever scanned by any of the three rules — `visitDir` prunes both before any file reaches `scanFiles`, so the adapter package that DEFINES the provider factories the construction rule flags needs no allowlist entry of its own. `isExemptPackage(relPath)` — exported for reuse — returns true when `relPath` equals one of the two directories or starts with `<dir>/`
- **No allowlist for `git-gh-shellout`/`cwd-derived-identity`; a file-scoped PERMANENT+TRANSITIONAL allowlist for `unsanctioned-construction` only:** the `ALLOWLIST` const and per-file skip were deleted in #701, and #769 added no allowlist for `cwd-derived-identity`. #795's `unsanctioned-construction` rule is the one rule with a path allowlist — `SANCTIONED_CONSTRUCTION_SITES`, an `as const` array of `{ file, reason, owner? }`:
  - **PERMANENT (2, no `owner`):** `adws/core/launchGitContext.ts` (the launch boundary — the one sanctioned construction site, PRD story 6) and `adws/providers/repoContext.ts` (the mint implementation the boundary delegates to). Nothing will ever remove these.
  - **TRANSITIONAL (27, each carrying `owner: '#796'`):** the residual non-boundary `gitContextFor`/`gitContextForSync`/`gitContextForRepo` call sites — every `createRepoContext`/forge-provider-factory (`createGitHubCodeHost` and siblings) construction site was migrated to the boundary by #797, so no transitional entry is owned by `#797` any longer; only the git-context-factory residue remains, owned by `#796`. Two of the 27 (`workflowInit.ts`, `prReviewPhase.ts`) are non-boundary `gitContextForSync`/`gitContextFor` call sites specifically for worktree work, now that their `createRepoContext` construction was removed in favor of `bindWorkspaceContext` (#797) — see `app_docs/feature-k2tkdn-gitcontext-boundary-constructor.md`. Each entry is deleted the moment its migration slice lands. **Nothing may ever be added to the transitional half** — a new construction site must call `buildLaunchBoundary`, not join this list.
  - `isSanctionedConstructionSite(relPath)` does **exact path match only** — a directory prefix is never sanctioned.
- **Self-cleaning ratchet (stale-entry check, #795):** `main()` re-parses every scanned file a second time through the pure predicate `hasGuardedConstruction(sourceFile)` (ignores the allowlist — asks "would this file trip the rule if it weren't sanctioned") to build the set of files that still construct something, then calls `findStaleSanctionedEntries(seenFiles)` — every TRANSITIONAL entry (permanent entries are exempt from staleness) whose file is not in that set. A non-empty result fails the build with `Remove the stale transitional entry — <file> no longer constructs a provider or context (#796/#797).`, forcing the allowlist to shrink to zero as `#796`/`#797` land rather than rotting.
- **Detection by command string, not callee (`git-gh-shellout`):** the scanner matches the literal string argument, not the function name. This catches `execSync`, `execWithRetry`, `spawn`, `execFileSync`, and injected callback forms uniformly
- **Detection by composite shape, not a single call (`cwd-derived-identity`):** neither `getRepoInfo()`/`readLocalRepoInfo()` alone nor `gitContextForRepo(x)` alone is flagged — only the composition of a zero-argument cwd read feeding a `gitContextForRepo` construction, either inline or via a local variable bound to one earlier in the same file.
- **Detection by explicit name set, never a `create*` pattern (`unsanctioned-construction`):** `PROVIDER_CONSTRUCTORS`/`CONTEXT_CONSTRUCTORS` are closed `ReadonlySet<string>`s. Deliberately NOT caught: `createGhCommandRunner`, `createGitHubTokenProvider` (auth/token plumbing, not a provider or context), `createGhRepoApi` (a bound view over a caller-supplied `GitContext`, selecting no identity of its own — the relocation target of GitContext's former `gh` semantic surface, #797), and `createIssueCmd`/`createPRCmd`/`createLabelCmd` (pure command-string builders). A bare identifier callee is required — `deps.gitContextForRepo(…)`/`d.gitContextForRepo(…)` (property access) are injected seams and are deliberately unflagged, and are correctly absent from the transitional list. Function declarations (`export function createGitHubCodeHost(...) {…}`) are never flagged, only call/new expressions.
- **The two `gitContextForRepo`-related rules are independent:** the identical source `gitContextForRepo(repoInfoParam)` is ZERO violations under `cwd-derived-identity` (an unrelated parameter is never collected) but ONE violation under `unsanctioned-construction` at a non-allowlisted path (the construction rule does not care where the argument came from — it flags the bare call itself). Conversely, a guarded fallback `gitContextForRepo(x ?? getRepoInfo())` stays legal under `cwd-derived-identity` but is still a construction-rule violation outside the allowlist.
- **Guarded fallbacks stay legal under `cwd-derived-identity` specifically:** `x ?? getRepoInfo()` is a `BinaryExpression` initializer, never collected by pass 1. An argument-bearing call (`getRepoInfo(cwd)`, `readLocalRepoInfo(REPO_ROOT)`) is likewise never collected by that rule.
- **AST-only, no regex on source text:** `ts.createSourceFile` + node walking means `git …` mentions or `gitContextForRepo`/`getRepoInfo`/provider-factory-name mentions in JSDoc, comments, or string variables never passed to a real call are never flagged. `adws/checkGitGhGuard.ts`'s own module docblock mentions `gitContextForRepo` in prose — this is never flagged, and the file is correctly absent from the allowlist.
- **`scanFiles`/`scanSource` are pure and their signature never changed by #795 or #816:** no I/O inside the scan core. `scanFiles.length === 2` (`relPaths`, `repoRoot`) is itself asserted by a unit test. The stale-entry ratchet's second pass (`collectConstructionSeenFiles`, private to `checkGitGhGuard.ts`) and the extraction-scope scan (`scanExtractionScope`) are separate helpers — neither extends `scanFiles`'s signature or return shape, and `scanExtractionScope` runs ONLY the `extraction-readiness` rule.
- **Extraction-readiness scope list is widen only, never narrow (#816):** `EXTRACTION_SCOPE` (`adws/guard/extractionRule.ts`) is an `as const` array of `{ path, reason, since }`. Each de-tangling slice of the gitContext extraction PRD appends the package it cleaned, in the same PR that cleans it; no entry is ever removed. A unit test pins the two initial entries (`adws/gitContext`, `adws/providers/types.ts`) as a superset — so widening never breaks the test, and removing either one does. `EXTRACTABLE_SET` (`adws/gitContext`, `adws/providers`) is fixed until the extraction switchover (PRD stories 23/25), at which point both the rule and this module are deleted together with the two directories.
- **`import type` counts as a violation (#816):** the rule flags every statically-resolvable import shape, including type-only imports and re-exports — a moved file that cannot type-check is not a pure file move.
- **A scope entry absent from the scanned tree contributes zero files, never a crash (#816):** `collectExtractionScopeFiles` is run over BDD fixture trees that hold only the files their scenario declares, so a missing entry (or, in principle, a renamed real-repo package) must not throw. In the real repository, a rename is instead caught by two dedicated unit tests — the real-tree assertion that the initial scope collects `adws/gitContext/gitContext.ts` and `adws/providers/types.ts`, and the rename-detection `it.each` table's `GitContext barrel` row — not by the CLI run itself.
- **The three pre-#816 rules never see extraction-scope files, and vice versa (#816):** `collectTsFiles` (whole-repo walk) still prunes `EXEMPT_PACKAGES`; `collectExtractionScopeFiles` (scope walk) does not prune them but is a wholly separate traversal feeding a wholly separate scan (`scanExtractionScope`) that runs only `flagFrameworkImports`. `scanFiles.length === 2` still holds.
- **Neither stdout block ever contains "allowlisted" (#795, #816):** the extraction-readiness scope block follows the same rule as the sanctioned-construction-sites block — see Gotchas.
- **Unit-tested (both directions, all four rules):** `adws/__tests__/checkGitGhGuard.test.ts` covers all four rules, `isSanctionedConstructionSite`, `findStaleSanctionedEntries`, and a rename-detection table (`it.each`) asserting every guarded factory name (`gitContextFor`/`gitContextForSync`/`gitContextForRepo`, `getRepoInfo`, `readLocalRepoInfo`, `createRepoContext`/`mintBoundProviders`, the seven provider factories, `GitContext`, and the `GitContext` barrel re-export) is still declared/present in its owning source file — a rename now fails a test instead of silently disarming a rule. A dedicated test asserts the near-miss set is permitted: `createGhCommandRunner`/`createGitHubTokenProvider`/`createIssueCmd`/`createGhRepoApi` in one source string trip zero violations, proving the flagged set is explicit names, never a `create*` pattern. `adws/guard/__tests__/extractionRule.test.ts` (#816) covers the rule module in isolation: the specifier resolver table, both membership predicates, specifier collection across every import shape, both directions of `flagFrameworkImports`, the scope-list invariants, and a real-tree assertion that the initial scope is clean today.

## Configuration

- `EXEMPT_DIR_NAMES` (Set in `adws/checkGitGhGuard.ts`): directory basenames pruned during file discovery. Currently: `node_modules`, `dist`, `.worktrees`, `.claude`, `features`, `test`
- `EXEMPT_PACKAGES` (readonly array of `{ dir, role }`, #792, in `adws/checkGitGhGuard.ts`): the closed, CI-enforced, named set of packages permitted to shell out — `adws/gitContext` and `adws/providers/github`
- `isExemptPackage(relPath): boolean` (exported from `adws/checkGitGhGuard.ts`): true when `relPath` equals one of `EXEMPT_PACKAGES`' `dir`s or starts with `<dir>/`
- `SANCTIONED_CONSTRUCTION_SITES` (readonly `as const` array of `{ file, reason, owner? }`, #795, in `adws/guard/constructionRule.ts`): the permanent+transitional allowlist for `unsanctioned-construction` — see Contracts above
- `EXTRACTABLE_SET` (readonly `['adws/gitContext', 'adws/providers']`, #816, in `adws/guard/extractionRule.ts`): the fixed allowed-import-target set for `extraction-readiness`
- `EXTRACTION_SCOPE` (readonly `as const` array of `{ path, reason, since }`, #816, in `adws/guard/extractionRule.ts`): the enforced-file subset of `EXTRACTABLE_SET` — widen only, never narrow; see Contracts above
- `package.json` `scripts.lint:git-guard`: `bunx tsx adws/checkGitGhGuard.ts`
- `.github/workflows/git-cli-guard.yml`: CI trigger (`on: [pull_request, push]`), single job, steps: checkout → setup-bun → bun install → `bun run lint:git-guard`

## Gotchas

- **The ALLOWLIST has been deleted (#701) for `git-gh-shellout`; #795 introduced a NEW, DIFFERENT, file-scoped allowlist for `unsanctioned-construction` ONLY.** Do not conflate the two. `git-gh-shellout` and `cwd-derived-identity` still have zero path allowlist — any violation anywhere fails CI. Only `unsanctioned-construction` has `SANCTIONED_CONSTRUCTION_SITES`, and it is a *shrinking* ratchet, not a static exemption: the stale-entry check fails the build if a transitional entry stops constructing anything, so it cannot be used to permanently exempt a file.
- **`(0 allowlisted)` is a literal string, and neither the sanctioned-construction-sites block nor the extraction-readiness-scope block may ever contain the word "allowlisted".** `features/per-issue/step_definitions/feature-700.steps.ts` parses the FIRST `(\d+)\s+allowlisted` match in the whole guard stdout — that must stay the original capstone line. The #795 and #816 blocks instead say "sanctioned construction sites" / "permanent" / "transitional" and "Extraction-readiness scope" / "entries, widen only".
- **Any new raw `git` call outside `adws/gitContext/`, or raw `gh` call outside `adws/providers/github/`, immediately fails CI.** No allowlist escape hatch.
- **Any new `gitContextForRepo(getRepoInfo())`-shaped composite immediately fails CI (#769).** Resolution: thread the caller's launch-boundary `GitContext` in instead of reconstructing one.
- **Any new bare call to a provider factory, `createRepoContext`, `mintBoundProviders`, a `gitContextFor*` factory, or `new GitContext(…)`, outside the allowlist, immediately fails CI (#795).** Resolution: receive providers from `buildLaunchBoundary(...)` instead of constructing them — the boundary is the only sanctioned construction site. There is no escape hatch for a *new* file; only the 27 pre-existing transitional entries are grandfathered, and each is deleted as `#796` migrates it.
- **Any new import in an `EXTRACTION_SCOPE` file that resolves outside `EXTRACTABLE_SET` immediately fails CI (#816).** Resolution: inject the dependency through a port (`TokenProvider`/`Logger`/config) or move the needed shape into the extractable set — never narrow `EXTRACTION_SCOPE` to make a violation disappear.
- **Widening `EXTRACTION_SCOPE` is a deliberate, reviewed act, not routine maintenance (#816).** The not-yet-widened providers files (`repoContext.ts`, `github/*`, `gitlab/*`, `jira/*`) import the framework today, by design — appending a package to the scope makes every remaining framework import in it fail CI immediately, so a de-tangling PR must clean the package and widen the scope in the same change.
- **`extraction-readiness` is the only rule that scans inside `EXEMPT_PACKAGES` (#816).** Its discovery walk (`collectExtractionScopeFiles`) deliberately does not apply `pruneExemptPackages` — if that ever changes, the git core's `git …` strings and the forge adapter's `gh …` strings would start reaching `git-gh-shellout` too (see feature-816.feature §6 for the regression net).
- **`features/` and `test/` are fully excluded from scanning**, and `adws/providers/github/**` / `adws/gitContext/**` are pruned at the directory-walk level before any of the first three rules ever sees them — the adapter package that defines the seven provider factories needs no allowlist entry of its own.
- **AST scan only — comments and string variables are not flagged, for any of the four rules.**
- **`scanFiles`, `scanSource`, and `scanExtractionScope` are exported as a module** — `main()` is only called when `process.argv[1]` includes `checkGitGhGuard`, so test imports work without triggering the guard.
- **`Violation.rule` is now a four-member union** (`adws/guard/violationTypes.ts`, #816) — `'git-gh-shellout' | 'cwd-derived-identity' | 'unsanctioned-construction' | 'extraction-readiness'`. Re-exported from `adws/checkGitGhGuard.ts` so no downstream import path changes.
- **A rename of any guarded factory now fails a test, not just silently disarms a rule.** The `it.each` rename-detection table in the unit suite reads each owning source file as plain text (via `vi.importActual('fs')`, since the suite mocks `fs` at module scope) and asserts the declaration string is still present.
- **The rule (and `adws/guard/extractionRule.ts`) is deleted at the extraction switchover, together with `adws/gitContext/` and `adws/providers/` (PRD story 23).** Until then, every de-tangling issue widens `EXTRACTION_SCOPE`; none may narrow it.
