# BDD Per-Issue Scenarios

## Overview

`features/per-issue/` is the collection of BDD scenario files scoped to individual GitHub issues. Each file covers the acceptance criteria for one issue and is used as the plan/implementation contract during the ADW SDLC pipeline — the build agent implements against these scenarios and the scenario proof pipeline runs them to verify the implementation.

## Responsibilities

- Store one `.feature` file per issue in `features/per-issue/feature-{issueNumber}.feature`, tagged with `@adw-{issueNumber}` so the scenario runner can discover the correct file for a workflow.
- Provide the acceptance contract that `validationAgent` and `resolutionAgent` check for alignment with the issue body before and after build.
- Serve as the input to `scenarioFidelityAgent`, which re-validates the frozen scenario set against the issue body after the first green test run.
- Store paired step definitions in `features/per-issue/step_definitions/feature-{issueNumber}.steps.ts` (TypeScript) or the equivalent for the target repo's language, generated by the `generate_step_definitions` command.
- Accept promotion candidates: individual scenarios tagged `@promotion-suggested-<date>` by the promotion sweep, and `@promotion` by human approval, triggering the promotion mover to migrate them to `features/regression/`.
- Get swept: `perIssueScenarioSweep.ts` (documented in the GitContext module doc) removes a feature file and its step-def siblings once its linked PR has been merged for more than `RETENTION_DAYS` (14), committing and pushing the removal so it persists to `origin` rather than leaving an uncommitted working-tree deletion.

## Contracts & Invariants

- Per-issue feature files are input documents for plan/build validation and scenario proof — they are not executed as part of the permanent regression suite.
- Scenarios in per-issue files that are tagged `@promotion` are moved (not copied) to the regression suite; the source file retains only non-promoted scenarios.
- The scenario proof pipeline runs per-issue scenarios in isolation tagged by `@adw-{issueNumber}`; scenarios tagged for other issues in the same file are ignored.
- Step definitions for issues #609 and #610 are owned by the registry module (the provider/issue-registry subsystem) and are not general-purpose per-issue stubs.
- The `gherkinFreeze` mechanism snapshots all per-issue `.feature` files before the scenario-fix loop; edits to `.feature` files during fixing are rejected by `resolveFreezeGuard`.

## Configuration

No configuration file. The `features/per-issue/` directory is discovered by the ADW pipeline via path convention. The Cucumber step definition require path includes `features/per-issue/step_definitions/` so all per-issue step files are loaded automatically.

## Gotchas

- Per-issue step definitions are generated by LLM and may be stubs (pending implementations) until the build agent fills them in; a pending step definition causes Cucumber to report the scenario as `pending`, not `failing`.
- The `.gitkeep` file in `features/per-issue/` ensures the directory exists in the repository even when no per-issue scenarios have been created yet.
- Feature files accumulate across all issues until swept: promoted scenarios are moved out immediately, and the rest are removed 14 days after their PR merges by `perIssueScenarioSweep.ts`. Scenarios for issues never merged (abandoned) remain indefinitely — the sweep only acts on a resolved merge date.
- Issues whose step definitions require non-TypeScript implementations (Python, etc.) must use the polymorphic step definition pattern described in the multilang regression tests.
