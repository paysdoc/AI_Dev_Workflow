# Takeover, Coordination & Stage Recovery Policy

## Overview

This module governs how multiple concurrent ADW events safely coordinate around a single issue, and how a workflow recovers when it stalls, crashes, or fails a gated check. It provides the per-issue spawn lock, the takeover decision tree, the pause queue scanner, the merge dispatch gate, and the per-repository concurrency guard, together preventing double-spawning and resuming paused workflows after rate-limit recovery. Underneath, an exhaustive stage classifier (`adws/core/stageClassifier.ts`) maps every `WorkflowStage` literal to one of six `StageClass` values that both the takeover decision and cron eligibility dispatch on, a bounded resume-cap policy (`adws/core/resumePolicy.ts`) caps automatic `phase_timeout` recovery before escalating to a human, and a `## Retry` directive handler (`adws/triggers/retryHandler.ts`) lets a human reset a human-gated stage back into the automatic recovery path.

## Responsibilities

- `classifyStage(stage: WorkflowStage): StageClass` (`adws/core/stageClassifier.ts`) — exhaustive `switch` mapping every `WorkflowStage` literal to one of `'active' | 'awaiting_merge' | 'retriable' | 'resumable' | 'terminal' | 'human_gated'`, with a compile-time `never` guard so an unhandled literal fails `tsc`. `classifyStageString(stage: string): StageClass` adapts raw persisted strings, checking the dynamic `${phaseName}_running`/`${phaseName}_completed` values `phaseRunner` emits (which are not `WorkflowStage` literals) before delegating to `classifyStage`.
- `evaluateCandidate` (`takeoverHandler`): the single decision tree for any candidate arriving at an issue. Attempts to acquire the spawn lock; if held by a live process, returns `defer_live_holder`. Otherwise reads state and dispatches on the stage's `StageClass` (see table below), with two raw-stage overrides checked ahead of the class fallthrough: `phase_timeout` (bounded-resume cap gate) and the `review_failed` routing folded into `human_gated`. The `retriable` class and the `phase_timeout` override share a single `recoverViaResumeInPlaceOrReset` seam that probes the worktree via `decideWorktreeReuse` and reuses it in place if healthy, else falls back to `recoverViaResetFromRemote`.
- `resolveAdwId` (inside `buildDefaultTakeoverDeps`): resolves the canonical adwId from issue comments via one of two routes. When an `EvaluateCandidateInput.boundary` (`LaunchBoundary`) is supplied, it reads `boundary.providers.issueTracker.fetchComments(issueNumber)`, maps each to `{ body }`, and hands the list to `extractLatestAdwId` — which takes the LATEST matching comment, so chronological comment order is load-bearing on this route. Without a boundary, it falls back to the legacy `fetchIssueCommentBodies(issueNumber, repoInfo)` from `adws/github/issueListApi.ts`. Either way the result feeds the same `extractLatestAdwId` predicate.
- `acquireIssueSpawnLock` (`spawnGate`): atomically creates a JSON lock file under `agents/spawn_locks/` using `O_EXCL` (exclusive create); reclaims stale locks from dead PIDs.
- `releaseIssueSpawnLock`: removes the lock file; tolerates `ENOENT`.
- `readSpawnLockRecord`: returns the stored `{ pid, pidStartedAt }` without modifying the lock.
- `isConcurrencyLimitReached` (`concurrencyGuard`): counts in-progress issues (ADW comment present + no linked merged/closed PR) and returns true when the count reaches `MAX_CONCURRENT_PER_REPO`.
- `shouldDispatchMerge` (`mergeDispatchGate`): reads the spawn lock for an issue and returns true when no lock record exists, the record's PID is dead, or the record's `pidStartedAt` is empty (stale format). Returns false only when a live PID holds the lock.
- `scanPauseQueue` (`pauseQueueScanner`): runs every `PROBE_INTERVAL_CYCLES` cycles; sends a cheap `claude --print "ping"` probe; on `clear` calls `resumeWorkflow` for each queued entry; on `limited` updates the `lastProbeAt` timestamp; on `unknown` increments `probeFailures` and removes the entry after `MAX_UNKNOWN_PROBE_FAILURES`.
- `resumeWorkflow`: resolves the entry's repo via `resolveEntryRepoInfo`, verifies the worktree exists, acquires the spawn lock for verification, checks the canonical adwId claim in the top-level state, releases the lock, spawns the orchestrator detached with a per-resume log file, waits 2 seconds for readiness, commits side-effects (remove from queue, post resumed comment) only on success.
- `resolveEntryRepoInfo`: extracts the target repo from a paused entry's `extraArgs` if present; falls back to the local git remote to prevent GH_TOKEN bleed (issue #565).
- `resolveEntryBoundary` / `postEntryStageComment` (`pauseQueueScanner`): every stage comment the scanner posts (worktree-gone, claim-diverged, probe-failure, resumed) routes through one private helper. `resolveEntryBoundary(entry)` calls `buildLaunchBoundary(parseTargetRepoArgs(entry.extraArgs ?? []))` — the same `--target-repo` resolution `resolveEntryRepoInfo` already used for the spawn/lock flow — and `postEntryStageComment(entry, stage, ctx)` posts via `postIssueStageComment(boundary.providers, entry.issueNumber, stage, ctx)` inside a try/catch, logging a warning on failure rather than throwing.
- `nextResumeAction(attempts, max?)` (`adws/core/resumePolicy.ts`) — pure cap decision for automatic `phase_timeout` recovery: returns `'resume'` while `attempts < MAX_RESUME_ATTEMPTS` (3), `'escalate'` at or above the bound. `evaluateCandidate`'s `phase_timeout` branch reads `state.resumeAttempts`, calls `nextResumeAction`, and either increments the counter and calls `recoverViaResumeInPlaceOrReset`, or writes `workflowStage: 'human_gated'`, posts `formatHumanGatedComment(adwId, attempts, max)` (`workflowCommentsIssue.ts`), and releases the lock as `escalate_human_gated`.
- `adws/triggers/retryHandler.ts`'s `handleRetryDirective` maps a human's `## Retry` issue comment to a state reset for the three human-gated recovery paths: `merge_blocked → awaiting_merge` (resets `mergeRetryCount: 0`), `human_gated → phase_timeout` (re-arms `resumeAttempts: 0`), `review_failed → phase_timeout` (re-arms `resumeAttempts: 0`, so the review re-runs while completed plan/build/step-def phases stay skipped); any other stage is a no-op that returns `false`.
- `review_failed` is classified `human_gated` (never auto-spawned by cron, routed to `spawn_fresh` by takeover): `cronIssueFilter.evaluateIssue` pins its ineligibility with an explicit guard placed before the grace-period and processed-spawn dedup checks (a money-fire guard — a just-failed review must stay ineligible even after a period of inactivity); it is recoverable only via `## Retry`.
- `executeSdlcReviewFailedHandoff` (`adws/phases/sdlcReviewHandoff.ts`) — extracted from `adwSdlc.tsx` so the SDLC review-failure outcome can be driven in isolation: writes `workflowStage: 'review_failed'` via `AgentStateManager.writeTopLevelState`, posts the branch-pointing `review_failed` comment via `postIssueStageComment`/`formatReviewFailedComment` (guarded on `ctx.branchName`, includes `## Retry` instructions), and logs a warning; `adwSdlc.tsx` then persists cost/metadata and returns before the doc/PR phases run.

The table below summarizes the `StageClass` → decision mapping both `evaluateCandidate` (takeover) and `evaluateIssue` (cron) dispatch on:

| `StageClass` | `WorkflowStage` literals | Cron decision | Takeover decision |
|---|---|---|---|
| `active` | `starting`, `resuming`, `build_running`, `test_running`, `review_running`, `document_running`, `install_running` | exclude (in progress) | SIGKILL-if-live → reset → reconcile → `take_over_adwId` |
| `awaiting_merge` | `awaiting_merge` | eligible → `merge` | `spawn_fresh` |
| `retriable` | `abandoned` | eligible → `spawn` | probe → reuse/reset → reconcile → `take_over_adwId` (no kill) |
| `terminal` | `completed`, `discarded`, `paused`, `paused_auth` | exclude (inline checks) | `skip_terminal` (release lock) |
| `human_gated` | `merge_blocked`, `human_gated`, `review_failed` | exclude (inline checks + explicit guard for `review_failed`) | `spawn_fresh` |
| `resumable` | all remaining literals including `phase_timeout`, `error`, `plan_building`, etc. | exclude by default; `phase_timeout` explicitly eligible | `spawn_fresh` by default; `phase_timeout` explicitly cap-gated |

## Contracts & Invariants

- Every `WorkflowStage` literal maps to exactly one `StageClass`; omitting a `case` in `classifyStage` is a `tsc` compile error (the `default` branch assigns `stage` to `never`). The `terminal` class is exactly `{completed, discarded, paused, paused_auth}` — no dynamic string maps to `terminal`.
- `classifyStageString` checks `endsWith('_running')` → `active` and `endsWith('_completed')` → `resumable` **before** delegating to `classifyStage`, so dynamic phaseRunner strings classify correctly even though they are not `WorkflowStage` literals. Unknown strings and `''` fall through to `default` and return `'resumable'` at runtime — the safest defensive class (`spawn_fresh` in takeover, excluded in cron).
- The spawn lock file uses `O_EXCL` (exclusive create) — exactly one writer wins the race; the loser re-reads the file to get the holder's PID and returns `defer_live_holder`. Stale locks (PID is dead according to `isProcessLive`) are reclaimed synchronously before the exclusive-create retry.
- `evaluateCandidate` always either releases the lock (on non-takeover exits) or leaves it held (for `spawn_fresh` and `take_over_adwId`). The caller's spawn releases the lock via `releaseIssueSpawnLock`.
- `paused` and `paused_auth` return `skip_terminal` — the pause queue scanner and auth queue scanner are the sole resumers; the takeover handler must never compete with them.
- `resumeWorkflow` acquires the spawn lock for verification only and releases it before spawning, so the child's `acquireOrchestratorLock` call takes the lifetime lock. The brief gap is accepted per design. Canonical-claim verification aborts the resume when `topLevelState.adwId !== entry.adwId` — diverged state triggers a removal from the queue and an error comment on the issue.
- `shouldDispatchMerge` only returns false when a live PID holds the lock; a dead PID is treated as "dispatch" and `acquireIssueSpawnLock` handles the stale-lock reclaim when `adwMerge` starts.
- `EvaluateCandidateInput` carries two optional launch-boundary fields, both absent only in legacy callers: `gitContext?: GitContext` (worktree paths resolve via its base path, never ambient cwd) and `boundary?: LaunchBoundary` (routes `resolveAdwId` and `deriveStageFromRemote` through the boundary's providers instead of building fresh `gh`-backed calls). The cron passes its own `cronBoundary` for both; `scanAuthQueue` and `webhookGatekeeper` — legacy callers with no boundary — are unchanged and keep using `fetchIssueCommentBodies` / the module-private `remoteReconcile` repo-info wiring. `deriveStageFromRemote` in `buildDefaultTakeoverDeps` is built as `deriveStageFromRemote(issueNumber, adwId, repoInfo, boundary ? buildDefaultReconcileDeps(boundary) : undefined)` — passing `deps` only when a boundary exists.
- `nextResumeAction` is pure (no I/O): `attempts < max → 'resume'`; `attempts >= max → 'escalate'`; identical inputs always produce identical output. `state.resumeAttempts` is cumulative — incremented on each automatic `phase_timeout` resume, cleared only on `## Retry` — and survives cron ticks because `writeTopLevelState` shallow-merges. The `escalate_human_gated` decision never spawns; both `trigger_cron` and `webhookGatekeeper` skip the spawn on this kind.
- `phase_timeout` recovery is via per-consumer raw-stage branches, not reclassification — `phase_timeout` stays `resumable` in `classifyStage`. Both `evaluateIssue` (cron) and `evaluateCandidate` (takeover) add an explicit `if (stage === 'phase_timeout')` branch keyed on the raw string, checked after the `retriable`/class checks.
- `## Retry` on `human_gated` or `review_failed` resets to `{ workflowStage: 'phase_timeout', resumeAttempts: 0 }`; on `merge_blocked` it resets to `{ workflowStage: 'awaiting_merge', mergeRetryCount: 0 }`; on any other stage it is a no-op. The `review_failed` cron exclusion guard is placed **before** the grace-period and processedSpawns checks — placement before is load-bearing, since placing it after would let a just-failed review become eligible after a period of inactivity.
- No PR exists when `review_failed` is written — `adwSdlc.tsx` returns before the PR phase, so the `review_failed` comment points the operator at the (PR-less) branch. No SIGKILL happens on `phase_timeout` — `handlePhaseTimeout` already calls `process.exit(0)`, so the orchestrator is dead before the stage is written and the takeover branch skips straight to the cap gate.
- `cronStageResolver.isActiveStage` (compatibility bridge for `devServerJanitor` and `webhookHandlers`) preserves the historical "in progress" set `{starting, *_running, *_completed}`, which differs from the `active` class: `cls === 'active' && stage !== 'resuming'` OR `cls === 'resumable' && stage.endsWith('_completed')`.

## Configuration

`AGENTS_STATE_DIR` is the base directory for spawn lock files (`agents/spawn_locks/`). `PROBE_INTERVAL_CYCLES` and `MAX_UNKNOWN_PROBE_FAILURES` are core constants controlling the pause probe cadence and retry limit. `MAX_CONCURRENT_PER_REPO` caps in-progress workflows per repository. `READINESS_WINDOW_MS` = 2000 ms is the window for confirming a resumed child did not immediately crash. `MAX_RESUME_ATTEMPTS = 3` in `adws/core/resumePolicy.ts` is the hard cap on automatic `phase_timeout` resumes — no environment variable; change the constant to adjust the cap. All of this is pure TypeScript with no I/O outside the injected `TakeoverDeps` (`takeoverHandler`) and `RetryHandlerDeps` (`retryHandler`).

## Gotchas

- `evaluateCandidate` caches a single `_defaultDeps` instance for performance; tests must inject their own deps to avoid cross-test contamination.
- `worktreeReset` in the takeover handler is best-effort — the takeover proceeds even if the worktree path does not exist on disk. The remote reconcile (`deriveStageFromRemote`) provides the authoritative next stage.
- `probeRateLimit` uses `--dangerously-skip-permissions` on the `claude` CLI; this is intentional for the lightweight rate-limit probe and does not reflect broader permission policy.
- The `READINESS_WINDOW_MS` guard in `resumeWorkflow` only catches immediate child crash/exit — it does not guarantee the orchestrator completes successfully. The queue entry is only removed after the window elapses without an exit event.
- `isConcurrencyLimitReached` fetches all open issues with comments on every invocation — it does not cache results. Callers should be aware of the API cost at high poll frequencies.
- **Fixed bug — target-repo entries used to lose their error comments**: before `postEntryStageComment` existed, all four pause-queue comment call sites used `createRepoContext({ cwd: process.cwd() })`, which validated the cron host's OWN git remote against the paused entry's repo. Any `--target-repo` entry failed that validation and threw, and the surrounding try/catch silently swallowed the throw — so worktree-gone, claim-diverged, and probe-failure comments were never posted for non-self-hosting repos. `postEntryStageComment` builds its boundary from the entry's own `--target-repo` args (via `resolveEntryBoundary`, mirroring `resolveEntryRepoInfo`), so target-repo entries now correctly receive these comments.
- **`review_failed` is `human_gated`, not `resumable`.** It was previously classified as `resumable`, which would have let cron auto-spawn it — a money-fire risk. The reclassification is a single-line move in the exhaustive switch, enforced at compile time by the `never` guard.
- **`review_failed → phase_timeout` re-arm does NOT consume the resume counter.** Only the automatic `evaluateCandidate` cap gate increments it; a human `## Retry` resets `resumeAttempts: 0`, giving the next automatic recovery a full fresh budget.
- **Intermediate loop comments vs. terminal handoff comment.** `reviewPhase.ts` posts a `review_failed` comment on each failed attempt in the retry loop (per-attempt informational). The terminal operator-facing comment is posted by `executeSdlcReviewFailedHandoff` after the loop exhausts. Multiple branch-pointing comments on the issue are acceptable known behaviour.
- **`executeSdlcReviewFailedHandoff` is extracted for BDD testability**, mirroring the `completePRReviewWorkflow` pattern from `prReviewCompletion.ts` — the inline-in-`main()` form could not be driven by a scenario without spawning a full orchestrator subprocess.
- **`human_gated` stage name equals its class name** (mirroring the `awaiting_merge` precedent). `merge_blocked` and `review_failed` remain distinct siblings in the same `human_gated` class; the three have different `## Retry` reset targets (`awaiting_merge`, `phase_timeout`, `phase_timeout`) so they must stay separate.
- **`resumeAttempts` is cumulative, not per-phase.** A workflow that makes progress but times out at several distinct phases will still escalate after 3 total resumes.
- **Dynamic phaseRunner stages** (`${phaseName}_running`, `${phaseName}_completed`, e.g. `plan_running`, `test_completed`) are not `WorkflowStage` literals. Always use `classifyStageString` (not `classifyStage`) when reading a raw `string` from the state file.
- **`isActiveStage` is NOT the same as `active`.** The compat bridge preserves a different set. Do not replace `isActiveStage` calls in `devServerJanitor.ts` or `webhookHandlers.ts` with `classifyStageString(s) === 'active'` without migrating the grace semantics.
