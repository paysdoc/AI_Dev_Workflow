# Device Lifecycle

## Overview

The device lifecycle gives a workflow its own Android emulator and iOS simulator for as long as a piece of work needs them, and removes both whatever happened. `withDevices(request, work, deps?)` creates one AVD and one simulator named `adw-<adwId>` from the resolved device source, boots and awaits both (up to three attempts each), calls `work` with their identities, and then shuts down and deletes both. It returns a closed `DeviceOutcome<T>`; a device that does not come up, or a missing host tool, parks the workflow as `device_boot_failed` instead of failing it. The scenario phase wraps the scenario proof run in it when the application profile has platforms, so parallel workflows never share a device, an `adb` port or a simulator identity. A device janitor, run on the cron's janitor cadence, removes the devices that dead workflows left behind.

## Responsibilities

- `deviceLifecycle.ts` (`adws/core/`) — `withDevices<T>(request, work, deps?): Promise<DeviceOutcome<T>>`, mirroring `withHealthyDevServer`. `request` carries `adwId`, the resolved `DeviceSource`, `emulatorOutputPath` and a `record(message, level)` run-log sink. `work` receives `DeviceEnvironment`: `ADW_ANDROID_AVD` (`adw-<adwId>`), `ADW_ANDROID_SERIAL` (`emulator-<console port>`) and `ADW_IOS_UDID`
- `deviceLifecycle.ts` — owns the public types (`DeviceEnvironment`, `DeviceRequest`, `DeviceLifecycleDeps`, `DeviceFailure`, `DeviceOutcome`) and the attempts loop: per device, run one bring-up attempt, keep the device on `ready`, otherwise record the failure (`warn` with `attempt <n> of 3` while another attempt follows, `error` for the last or for a missing tool), tear down what the attempt created, and try again, up to `MAX_BOOT_ATTEMPTS` (3). The two devices are attempted concurrently so each boot time is measured on its own
- `deviceLifecycle.ts` — the closed outcome: `ready` (with the callback's result), `boot_failed` (`platform`, `attempts`, combined `output`) or `tool_missing` (`platform`, `tool: HostTool`, `output`). When both devices fail the reported failure is a `tool_missing` first, then Android's, then iOS's. The combined output is one block per failed attempt, `Attempt <n> of 3: <message>` followed by that attempt's output
- `deviceBringUp.ts` (`adws/core/`) — one attempt to bring up each device, and each device's teardown. Android: allocate a console port, `avdmanager create avd` (input `no\n`), `adb start-server`, `emulator -avd … -port <p> -no-window -no-audio -no-boot-anim -no-snapshot` started detached with output in the emulator log, then polling `adb get-state` (`device`) and `getprop sys.boot_completed` (`1`) on the injected clock. iOS: `xcrun simctl create`, `boot`, `bootstatus`. It reads a missing host tool from the executor's answer. A failed Android attempt's output ends with the last `EMULATOR_OUTPUT_LINES` (20) lines the emulator printed, read before the next attempt's start truncates the output file. Teardown per device: shut down then delete (`adb emu kill`, wait for the emulator process to exit, `kill()` if it ignores that, then `avdmanager delete avd`; `simctl shutdown` then `delete`)
- `deviceBringUp.ts` — records the run log: a creation line per device per attempt (Android's names AVD, device-source values, console port and attempt; iOS's names device type and runtime), `booted in <s>s` per device, and `Removed …` per device (or a `warn` line naming the command, exit code and last output line)
- `deviceCommands.ts` (`adws/core/`) — pure: device names, port candidates, every device command as a `DeviceCommand`/argv, the readers `lastLine`, `lastLines` and `lastUdid`, `MAX_BOOT_ATTEMPTS`, the `HostTool` enum (`avdmanager`, `emulator`, `adb`, `xcrun simctl`) and `missingToolOf(command, result)`, which reads a missing program, or `xcrun`'s `unable to find utility "simctl"` answer, as the missing tool. Exports `deviceNameFor(adwId)` and `emulatorConsolePortCandidates(adwId)`, and for the janitor the inverse `adwIdOfDeviceName(name)` (an ADW-ID-shaped suffix after `adw-`, otherwise `null`), the listing commands (`listAvds`, `listAttachedDevices`, `queryEmulatorAvdName`, `listSimulators`) and their readers (`avdNamesIn`, `emulatorSerialsIn`, `avdNameIn`, `simulatorsIn`, `isShutDown`)
- `deviceInventory.ts` (`adws/core/`) — `listAdwDevices(deps)` lists the AVDs (`avdmanager list avd -c`, matched to running emulators through `adb devices` and `adb -s <serial> emu avd name`) and simulators (`xcrun simctl list --json devices`) named for an ADW ID, as `DeviceInventory` (a `DeviceListing` per platform: `listed`, `tool_missing` or `failed`). `removeAdwDevice(device, deps)` shuts down then deletes one device; for an AVD with a running emulator it kills it and waits up to `EMULATOR_EXIT_TIMEOUT_MS` for it to leave adb before deleting. Never rejects; `DeviceRemoval.failures` is empty on success. `deviceLifecycle.ts` re-exports both, defaulting `executor`/`clock` to its own
- `deviceJanitor.ts` (`adws/triggers/`) — `runDeviceJanitorPass(deps?, targetReposDir?)`: lists the devices, groups them by ADW ID and, per ID, decides right before removing: reap only when `isAgentProcessRunning(adwId)` is false and the worktree (rebuilt from the top-level state's `repoIdentity` and `branchName`) is older than `JANITOR_GRACE_PERIOD_MS` of the dev-server janitor, a missing worktree or state counting as very old (`shouldReapDevices`). Logs `Device janitor: …` lines (info for scans and removals, warn for failures). Never rejects. `DEFAULT_DEPS` is exported frozen
- `trigger_cron.ts` — `runJanitorTick(cycleCount, passes?)`: on a `JANITOR_INTERVAL_CYCLES` cycle runs the dev-server janitor, then the device janitor
- `deviceExecutor.ts` (`adws/core/`) — the `DeviceExecutor` port: `run(command)` runs a command to completion, `start(argv, outputPath)` starts a detached long-running process with output written to a file. `DeviceCommandResult.programMissing` is set when the spawn fails with `ENOENT`; a started `DeviceProcess` answers `programMissing()` once `exited` has settled and `output()` (what it has printed to its output file so far). `systemDeviceExecutor` is the `child_process` implementation; no shell, no blocking call
- `scenarioTestPhase.ts` (`adws/phases/`) — `requireDeviceSource` returns the resolved `DeviceSource` (or `null` for a profile without platforms); the proof run goes through `ScenarioTestPhaseDeps.withDevices` (inside the declared dev server when there is one, so the server has stopped before a park) and the three variables are spread into the run command's `env` beside `ADW_APPLICATION_URL`. On a failed outcome it logs a summary and the combined output, then calls the injected `park` (default `parkWorkflow`) with `device_boot_failed`. `runScenarioProof` still adds `ADW_PROOF_DIR` and `ADW_JUNIT_REPORT_PATH`. The request's `record` writes to the orchestrator log and the emulator log is `<logsDir>/android-emulator.log`
- `forge/parkComment.ts` — the `device_boot_failed` park reason (evidence `{ reason, failure: DeviceFailure }`, imported type-only): the comment names the platform (and the tool), says what failed or that it was not retried, quotes the output under the existing fence rules, and states that `## Retry` re-runs the scenario phase while `## Continue` waives nothing
- Test support: `adws/core/__tests__/fixtures/recordingDeviceHost.ts` (recording executor, fake clock, port probe; scripts `failing`, `failingTimes`, `missingTools`, `emulatorEarlyExits`, `emulatorOutput`; no vitest import) for unit tests; `features/regression/support/standInDevices.ts` (the real lifecycle over an executor that answers like a healthy host, with failure options; no hooks, no steps) and `features/per-issue/step_definitions/feature-1047-host.steps.ts` keep BDD scenarios that run the real phase on a `mobile:kotlincm` worktree hermetic

## Contracts & Invariants

- Teardown runs on every outcome: a callback that throws (its error propagates unchanged, after teardown), a device that does not come up, a failed sibling bring-up. Nothing created is left behind
- Teardown never throws: a failed teardown command is recorded as a `warn` and the callback's result or error passes through
- `withDevices` resolves to `ready`, `boot_failed` or `tool_missing`; it rejects only with the callback's own error. The attempts loops never reject and both settle before either outcome is read, so a half-created device is always torn down; what a failed attempt created is removed before the next attempt reuses the names and port and before the outcome is read; per device the shut down comes before the delete, and an AVD is deleted only after its emulator process has exited
- Each device is attempted at most `MAX_BOOT_ATTEMPTS` (3) times. A missing host tool (`avdmanager`, `emulator`, `adb`, `xcrun simctl`) is never retried: the outcome is `tool_missing` at once. A tool that ran and failed is a boot failure, not a missing tool
- A failed outcome parks the workflow `human_gated` with `parkReason: 'device_boot_failed'` through `parkWorkflow`, after the devices and any dev server have been removed; the phase does not return. `## Retry` re-arms it to `phase_timeout` and the resumed run runs the scenario phase again with fresh devices; `## Continue` waives nothing (`WAIVABLE_PARK_REASONS` stays the three base-branch parks). A device-source configuration error still throws and does not park
- Each Android attempt probes for a free console port again, so a port another workflow took since the last probe is skipped. The port is one of 64 even ports 5554–5680, chosen from the ADW ID's SHA-256 hash order; ports in use (the console port or the adb port above it) are skipped, wrapping around. With none free the attempt fails for `android` before creating anything
- The executor never rejects (`exitCode: null` for a command that could not start or hit its timeout) and `start` never throws; commands are argv arrays, so no ADW ID or device-source value can inject anything
- Only a profile with platforms (`mobile:kotlincm`) asks for devices; for `cli` and `web` no device command is issued, the run `env` stays exactly `{ ADW_APPLICATION_URL }` and nothing parks. No scenarios or a `N/A` run-by-tag command means no devices
- The module never uses the identifier `applicationType` (the mapping-reader guard); it receives only the resolved `DeviceSource` and the platforms come from the profile
- `deviceLifecycle.ts` and `deviceBringUp.ts` stay under 300 lines and have no runtime import cycle; `forge/parkComment.ts` may import lifecycle types with `import type` only

## Configuration

- Device-source values come from `.adw/project.md` (`## Android System Image`, `## Android Device Profile`, `## iOS Device Type`, `## iOS Runtime`), resolved by `resolveDeviceSource`
- Constants in `deviceCommands.ts`/`deviceBringUp.ts`: `DEVICE_COMMAND_TIMEOUT_MS` (120 s), `DEVICE_BOOT_TIMEOUT_MS` (300 s), `POLL_COMMAND_TIMEOUT_MS` (10 s), `BOOT_POLL_INTERVAL_MS` (2 s), `EMULATOR_EXIT_TIMEOUT_MS` (30 s), `MAX_BOOT_ATTEMPTS` (3), `EMULATOR_OUTPUT_LINES` (20). `BOOT_POLL_INTERVAL_MS` and `EMULATOR_EXIT_TIMEOUT_MS` are re-exported from `deviceLifecycle.ts`
- `deps` (`executor`, `clock` as the `WaitClock` of `rateLimitWaitPolicy.ts`, `isPortAvailable`) are partial and default to the real implementations
- The host must have `avdmanager`, `emulator`, `adb` and `xcrun simctl` on its `PATH`

## Gotchas

- `adb start-server` runs before the emulator: a running server is told about an emulator when it starts, while a server started later scans only ports 5555–5585
- An empty `getprop sys.boot_completed` answer is a booting emulator, not an error; only the last output line is compared, because a daemon start-up message may precede it
- The `simctl create` UDID is read with a UUID pattern from the last match, since a warning may precede it
- The emulator prints why it cannot boot (`PANIC: Broken AVD system path…`) only to its output file, so a failed attempt reads the last lines back before the next attempt's start truncates it; the file keeps the full output of the last attempt only
- A host with the Command Line Tools but no Xcode answers `xcrun` with `unable to find utility "simctl"` (exit 72); that is read as `xcrun simctl` missing, not as a boot failure
- The hash alone does not prevent a collision (64 ports, up to five workflows per repository): the port probe is what guarantees uniqueness, and it probes `127.0.0.1` because on macOS a wildcard bind can succeed beside the emulator
- Every call is asynchronous: a boot takes minutes and the orchestrator heartbeat must keep ticking
- BDD scenarios that run the real lifecycle directly must use a clock whose `sleep` resolves at once and advances `now`, or an emulator that never boots spins through `DEVICE_BOOT_TIMEOUT_MS` of real time on each attempt; scenarios that run the real phase must trap `process.exit`, since a park exits the process
- Existing BDD scenarios that run the real phase on a `mobile:kotlincm` worktree must install the stand-in device host (the step "the host's device tools are stand-ins…"), or they would run the real SDK tools

- The device janitor never touches a device of a live workflow, one inside the grace period, or one whose name is not `adw-` plus an ADW-ID-shaped suffix (the operator's devices). A tool the host lacks yields an empty listing, not a warning; any other listing failure is a warning and the pass goes on
- An AVD whose emulator outlives the kill by `EMULATOR_EXIT_TIMEOUT_MS` is left for the next pass, as `avdmanager` will not delete a running AVD
- The cron process needs `avdmanager`, `emulator`, `adb` and `xcrun` on its `PATH` for the janitor to see devices
- `cucumber.js` sets `JANITOR_INTERVAL_CYCLES` out of reach so a BDD run from a worktree never sweeps the real host's devices; scenarios that drive the janitor tick use stand-in devices (`standInLeftoverDevices`)
