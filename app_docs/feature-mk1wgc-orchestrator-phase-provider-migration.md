# Orchestrator & Phase Provider Consumption

## Overview

Orchestrator scripts and phase modules that perform forge work (comment, label, PR, board, secret operations) consume the launch-boundary-minted `IssueTracker`/`CodeHost` provider pair instead of calling forge-semantic methods on `GitContext`. `GitContext` itself now has zero forge methods — it is used strictly for git operations (`pushBranch`, `commandEnv`, worktree management, `show`).

## Responsibilities

- `adwMerge.tsx` — `buildDefaultDeps(boundary: LaunchBoundary)` (exported) sources `findPRByBranch`, `issueHasLabel`, `fetchPRApprovalState`, and `commentOnIssue` from `boundary.providers`, with `issueHasLabel` implemented as `providers.issueTracker.fetchLabels(n).includes(labelName)`. `ensureTargetRepoWorkspace(targetRepo, () => boundary.providers.codeHost.getDefaultBranch())` supplies the workspace's default-branch thunk. `mergeWithConflictResolution` and `notifyBlockedTransition` still take a `repoInfo` argument built from `boundary.repoId` at the call site — both live in `adws/triggers/`/`adws/github/`, outside this migration's scope.
- `adwUpgrade.tsx` — `main()` calls `buildLaunchBoundary(targetRepo)` once instead of deriving a `RepoIdentifier` and a `GitContext` independently. `buildDefaultUpgradeDeps(providers, gitCtx)` (exported) sources every forge dependency (`getDefaultBranch`, `findPRByBranch`, `createPullRequest`, `mergePR`, `commentOnIssue`, `fetchIssueLabels`, `fetchIssueComments`, `ensureLabel`, `applyLabel`, `moveToStatus`) from `providers`. `fetchIssueComments` wraps `providers.issueTracker.fetchComments` in a `try/catch` returning `[]`, because the port throws on a malformed response where the old `parseIssueComments` returned `[]` — without the wrapper the failure-cap gate would crash instead of counting zero. `moveToStatus` is `await`ed (`IssueTracker.moveToStatus` returns `Promise<boolean>`). `ensureTargetRepoWorkspace(targetRepo, () => providers.codeHost.getDefaultBranch())` supplies `baseRepoPath` when a target repo is set, else `process.cwd()`.
- `adwPrReview.tsx` — builds a `LaunchBoundary` and passes it as a trailing optional parameter to `initializePRReviewWorkflow`, the same shape `adwMerge` uses.
- `workflowInit.ts` — reads the default branch from `boundary.providers.codeHost.getDefaultBranch()` behind a guard clause that throws if `boundary` is `undefined` (unreachable in production: the boundary and the preceding `gitContextForSync` construct their `GitContext` from the same identity resolution and credential probe). `resolveWorkflowProviders(boundary, callerRepoId?)` (exported) is the single place that decides which `RepoIdentifier`/`BoundProviders` pair a workflow's `RepoContext` uses — see Contracts. `ensureTargetRepoWorkspace(targetRepo, () => boundary.providers.codeHost.getDefaultBranch())` sets up the target repo workspace. The `RepoContext` itself is built via `bindWorkspaceContext(boundary, worktreePath, repoIdForContext)` (`adws/core/launchGitContext.ts`) once `resolveWorkflowProviders` has resolved the identity.
- `upgradeGate.ts` — `buildDefaultUpgradeGateDeps(providers: BoundProviders, worktreePath: string, gitCtx: GitContext)` sources `createIssue`, `applyLabel`, `updateIssueBody`, `findOpenUpgradeIssue`, and `moveToStatus` from `providers.issueTracker`, and derives `gitShow` internally as `(ref, filePath, cwd) => gitCtx.show(ref, filePath, cwd)` for `readAdwVersion`; callers pass the `GitContext` directly rather than a pre-built `gitShow` thunk. The previous per-call `createRepoContext` inside the `moveToStatus` closure is gone.
- `autoMergePhase.ts` — guards on `if (!repoContext) return` and reads `repoContext.issueTracker.fetchLabels(...)`, `repoContext.codeHost.isPullRequestApproved(...)`, `repoContext.issueTracker.addLabel(...)`, `repoContext.issueTracker.commentOnIssue(...)`, and `repoContext.codeHost.commentOnPullRequest(...)`. It uses `addLabel` (fail-open), not `applyLabel`, preserving the gate's existing lenient failure behaviour. `mergeWithConflictResolution` still receives a `repoInfo` built from `repoContext.repoId` at its call site.
- `reviewPhase.ts` — `repoContext.codeHost.approvePullRequest(prNumber)` replaces the standalone `approvePR(prNumber, repoInfo)` call; `executeReviewPatchCycle`'s `gitContextFor` is unchanged (it is used only for git operations).
- `prPhase.ts` — `repoContext ? repoContext.codeHost.getDefaultBranch() : config.defaultBranch` replaces `gitCtx?.defaultBranch()`; `gitCtx` is still held for `pushBranch`/`commandEnv`.
- `docsSelfCheck.ts` — `buildDefaultDocsSelfCheckDeps(issueTracker: IssueTracker)` builds `createIssue`/`findExistingRefactorIssue` from an injected tracker; the open-issue lookup is `tracker.searchOpenIssues(\`docs-bloat: ${docPath}\`, 5)` with the same title-includes filter and swallow-to-`null` as before.
- `depauditSetup.ts` — the secret-propagation dep is `codeHost?: CodeHost` (defaulting to `config.repoContext?.codeHost`); with no code host, secrets land in `skippedSecrets` with a warning rather than throwing.
- `prReviewPhase.ts` — accepts an optional `boundary: LaunchBoundary`. When `targetRepo` is set it requires `boundary` (throws if absent) and calls `ensureTargetRepoWorkspace(targetRepo, () => boundary.providers.codeHost.getDefaultBranch())`. `RepoContext` is built via `bindWorkspaceContext(boundary, worktreePath, repoId)` when a boundary is present, else `repoContext` stays `undefined` and phases fall back to direct API calls. The `gitContextFor` call for worktree creation is unchanged.
- `documentPhase.ts` — passes `repoContext.issueTracker` into `buildDefaultDocsSelfCheckDeps` rather than constructing a tracker itself.
- `phaseCommentHelpers.ts` — `postIssueStageComment`'s first parameter is `Pick<RepoContext, 'issueTracker'>`, not a full `RepoContext`. This lets any caller that only has a bare `BoundProviders` (no `cwd`/`repoId`, e.g. `pauseQueueScanner.ts`) post an issue-stage comment without minting a full `RepoContext`. `postPRStageComment` still takes a full `RepoContext` (it also needs `repoId` context conventions used elsewhere in the PR-review flow).
- `targetRepoManager.ts` — `ensureTargetRepoWorkspace(targetRepo: TargetRepoInfo, getDefaultBranch: () => string)` takes an explicit thunk rather than deriving the default branch itself. The thunk is invoked only on the already-cloned (fetch) branch inside `ensureRepoWorkspace`, never on a first clone. Four call sites pass `() => <providers or boundary.providers>.codeHost.getDefaultBranch()`: `adwMerge.tsx`, `adwUpgrade.tsx`, `workflowInit.ts`, `prReviewPhase.ts`.

## Contracts & Invariants

- No orchestrator or phase module in this set calls a forge-semantic method directly on a `GitContext`; every issue/PR/label/board/secret operation goes through the provider pair it was handed. `GitContext` has zero forge-semantic methods to call even by mistake.
- `resolveWorkflowProviders` (`workflowInit.ts`) is the sole authority for which `RepoIdentifier`/`BoundProviders` pair a workflow's `RepoContext` uses: with no caller-supplied `repoId` it returns the boundary's identity and providers unchanged (no second git-remote read); a caller-supplied `repoId` that names a different repository than the boundary **throws** rather than falling back to a second, ad-hoc-minted provider set. `bindWorkspaceContext(boundary, cwd, repoId?)` (`adws/core/launchGitContext.ts`) applies the same same-identity check before calling `createRepoContext({ repoId, cwd, providers: boundary.providers })` — it is the shared constructor both `workflowInit.ts` and `prReviewPhase.ts` call once identity is resolved.
- `IssueTracker.addLabel` (fail-open) and `IssueTracker.applyLabel` (lazy-create, rethrow) are picked deliberately per caller: `autoMergePhase.ts` uses `addLabel` so a labeling failure never blocks the merge gate; `adwUpgrade.tsx`/`upgradeGate.ts` use `applyLabel` because the terminal label must exist or the failure must surface.
- `adwUpgrade.tsx`'s `fetchIssueComments` dependency must not be replaced with a bare `providers.issueTracker.fetchComments` call — the port throws on a malformed response, and the failure-cap gate depends on `[]` on failure. Keep the `try/catch`.
- `GitContext` is still held by every migrated module (`workflowInit`, `prReviewPhase`, `executeReviewPatchCycle`, `prPhase`) but strictly for git operations (`pushBranch`, `commandEnv`, `gitContextFor`, worktree management, `show`), never for a forge-semantic call.
- `MergeDeps`/`UpgradeDeps`/`UpgradeGateDeps` forge-facing methods no longer take a `repoInfo` parameter — the provider is already bound to one repository, so there is no wrong-repo parameter to pass incorrectly. `mergeWithConflictResolution`, `notifyBlockedTransition`, and `claimUpgrade` are the deliberate exceptions: they live in modules (`adws/triggers/`, `adws/core/upgradeClaim.ts`) outside this migration's scope and still take `repoInfo`.
- `ensureTargetRepoWorkspace`'s `getDefaultBranch` thunk must be lazy (`() => providers.codeHost.getDefaultBranch()`, not a pre-evaluated value) — it is only safe to invoke once the workspace is already cloned, and passing an eagerly-evaluated call would run it before a first clone exists.

## Configuration

No new configuration. Every module in this set already receives its `LaunchBoundary`/`RepoContext` from the existing boundary-construction path (`buildLaunchBoundary` in orchestrators, `config.repoContext` in phases).

## Gotchas

- `GitHubCodeHost` methods that don't yet have a bound-context shortcut (e.g. `getDefaultBranch`, `setSecret`) still construct a `gitContextForSync`/`gitContextForRepo` internally — this is the adapter's implementation detail, not a regression back to ad-hoc construction by the caller; the emitted `gh` command is unchanged from what the caller used to build directly.
- Providers are not yet threaded into every minted-object construction site — a boundary-minted `GitHubCodeHost`, `BoardManager`, or the `adws-github-layer` construction path may still resolve their own `GitContext` internally rather than receiving one from the caller. This is a later slice, not a regression: the caller-facing contract (no forge calls on `GitContext`) already holds; only the adapters' internal wiring is unfinished.
- A handful of modules (`adws/adwChore.tsx`, `adws/adwClearComments.tsx`, `unitTestPhase.ts`, `stackCoherenceReporter.ts`) still consume `adws/github/*` wrapper functions directly rather than a bound `IssueTracker`/`CodeHost` — deferred, not part of this migration's scope. `prReviewPhase.ts`'s `fetchPRDetails`/`getUnaddressedComments`, `workflowCompletion.ts`, and `adwBuildHelpers.ts` were verified to either already route through wrappers without holding a `GitContext`, or to contain no forge-semantic calls at all.
- `notifyBlockedTransition`'s platform branch (`adwMerge.tsx`: `platform === Platform.GitHub ? notifyBlockedTransition : async () => undefined`) is deliberately **not** folded into a provider — it is a Slack board-notification concern reached through `adws/github/hitlBoardNotifier`, outside the operations this slice's ports cover. A Slack notification port remains deferred.
- `pauseQueueScanner.ts` posts issue-stage comments through a bare `BoundProviders` (no `cwd`/`repoId`) via `postIssueStageComment`'s `Pick<RepoContext, 'issueTracker'>` parameter — see `app_docs/feature-9gjajh-takeover-and-coordination.md` for that module's own documentation; this doc only records the signature change that makes it possible.
