# Orchestrator & Phase Provider Consumption

## Overview

Orchestrator scripts and phase modules that perform forge work (comment, label, PR, board, secret operations) consume the launch-boundary-minted `IssueTracker`/`CodeHost` provider pair instead of calling forge-semantic methods on `GitContext` or minting a second, ad-hoc provider set from a hand-rebuilt identity. A `GitContext` is still held by these modules, but only for git operations (`pushBranch`, `commandEnv`, worktree management) — never for forge semantics.

## Responsibilities

- `adwMerge.tsx` — `buildDefaultDeps(boundary: LaunchBoundary)` (exported) sources `findPRByBranch`, `issueHasLabel`, `fetchPRApprovalState`, and `commentOnIssue` from `boundary.providers`, with `issueHasLabel` implemented as `providers.issueTracker.fetchLabels(n).includes(labelName)`. `mergeWithConflictResolution` and `notifyBlockedTransition` still take a `repoInfo` argument built from `boundary.repoId` at the call site — both live in `adws/triggers/`/`adws/github/`, outside this migration's scope.
- `adwUpgrade.tsx` — `main()` calls `buildLaunchBoundary(targetRepo)` once instead of deriving a `RepoIdentifier` and a `GitContext` independently. `buildDefaultUpgradeDeps(providers, gitCtx)` (exported) sources every forge dependency (`getDefaultBranch`, `findPRByBranch`, `createPullRequest`, `mergePR`, `commentOnIssue`, `fetchIssueLabels`, `fetchIssueComments`, `ensureLabel`, `applyLabel`, `moveToStatus`) from `providers`. `fetchIssueComments` wraps `providers.issueTracker.fetchComments` in a `try/catch` returning `[]`, because the port throws on a malformed response where the old `parseIssueComments` returned `[]` — without the wrapper the failure-cap gate would crash instead of counting zero. `moveToStatus` is `await`ed (`IssueTracker.moveToStatus` returns `Promise<boolean>`).
- `adwPrReview.tsx` — builds a `LaunchBoundary` and passes it as a trailing optional parameter to `initializePRReviewWorkflow`, the same shape `adwMerge` uses.
- `workflowInit.ts` — reads the default branch from `boundary.providers.codeHost.getDefaultBranch()` behind a guard clause that throws if `boundary` is `undefined` (unreachable in production: the boundary and the preceding `gitContextForSync` construct their `GitContext` from the same identity resolution and credential probe). `resolveWorkflowProviders(boundary, callerRepoId?)` (exported) is the single place that decides which `RepoIdentifier`/`BoundProviders` pair a workflow's `RepoContext` uses — see Contracts.
- `upgradeGate.ts` — `buildDefaultUpgradeGateDeps(providers: BoundProviders, worktreePath, gitShow)` sources `createIssue`, `applyLabel`, `updateIssueBody`, `findOpenUpgradeIssue`, and `moveToStatus` from `providers.issueTracker`; the previous per-call `createRepoContext` inside the `moveToStatus` closure is gone.
- `autoMergePhase.ts` — guards on `if (!repoContext) return` and reads `repoContext.issueTracker.fetchLabels(...)`, `repoContext.codeHost.isPullRequestApproved(...)`, `repoContext.issueTracker.addLabel(...)`, `repoContext.issueTracker.commentOnIssue(...)`, and `repoContext.codeHost.commentOnPullRequest(...)`. It uses `addLabel` (fail-open), not `applyLabel`, preserving the gate's existing lenient failure behaviour. `mergeWithConflictResolution` still receives a `repoInfo` built from `repoContext.repoId` at its call site.
- `reviewPhase.ts` — `repoContext.codeHost.approvePullRequest(prNumber)` replaces the standalone `approvePR(prNumber, repoInfo)` call; `executeReviewPatchCycle`'s `gitContextFor` is unchanged (it is used only for git operations).
- `prPhase.ts` — `repoContext ? repoContext.codeHost.getDefaultBranch() : config.defaultBranch` replaces `gitCtx?.defaultBranch()`; `gitCtx` is still held for `pushBranch`/`commandEnv`.
- `docsSelfCheck.ts` — `buildDefaultDocsSelfCheckDeps(issueTracker: IssueTracker)` builds `createIssue`/`findExistingRefactorIssue` from an injected tracker; the open-issue lookup is `tracker.searchOpenIssues(\`docs-bloat: ${docPath}\`, 5)` with the same title-includes filter and swallow-to-`null` as before.
- `depauditSetup.ts` — the secret-propagation dep is `codeHost?: CodeHost` (defaulting to `config.repoContext?.codeHost`); with no code host, secrets land in `skippedSecrets` with a warning rather than throwing.
- `prReviewPhase.ts` — accepts an optional `boundary: LaunchBoundary`; `createRepoContext` reuses `boundary.providers` when `sameRepoIdentity(repoIdForContext, boundary.repoId)` holds, mirroring `workflowInit.ts`'s pattern. The `gitContextFor` call for worktree creation is unchanged.
- `documentPhase.ts` — passes `repoContext.issueTracker` into `buildDefaultDocsSelfCheckDeps` rather than constructing a tracker itself.

## Contracts & Invariants

- No orchestrator or phase module in this set calls a forge-semantic method directly on a `GitContext`; every issue/PR/label/board/secret operation goes through the provider pair it was handed.
- `resolveWorkflowProviders` (`workflowInit.ts`) is the sole authority for which `RepoIdentifier`/`BoundProviders` pair a workflow's `RepoContext` uses: with no caller-supplied `repoId` it returns the boundary's identity and providers unchanged (no second git-remote read); a caller-supplied `repoId` that names a different repository than the boundary **throws** rather than falling back to a second, ad-hoc-minted provider set. This resolved feature-796's ADW-WARNING in favor of refusal over silent dual-minting — a caller cannot address a repository other than the one the process was launched for.
- `IssueTracker.addLabel` (fail-open) and `IssueTracker.applyLabel` (lazy-create, rethrow) are picked deliberately per caller: `autoMergePhase.ts` uses `addLabel` so a labeling failure never blocks the merge gate; `adwUpgrade.tsx`/`upgradeGate.ts` use `applyLabel` because the terminal label must exist or the failure must surface.
- `adwUpgrade.tsx`'s `fetchIssueComments` dependency must not be replaced with a bare `providers.issueTracker.fetchComments` call — the port throws on a malformed response, and the failure-cap gate depends on `[]` on failure. Keep the `try/catch`.
- `GitContext` is still held by every migrated module (`workflowInit`, `prReviewPhase`, `executeReviewPatchCycle`, `prPhase`) but strictly for git operations (`pushBranch`, `commandEnv`, `gitContextFor`, worktree management), never for a forge-semantic call — that boundary is what `#795`'s guard rule is expected to enforce structurally.
- `MergeDeps`/`UpgradeDeps`/`UpgradeGateDeps` forge-facing methods no longer take a `repoInfo` parameter — the provider is already bound to one repository, so there is no wrong-repo parameter to pass incorrectly. `mergeWithConflictResolution`, `notifyBlockedTransition`, and `claimUpgrade` are the deliberate exceptions: they live in modules (`adws/triggers/`, `adws/core/upgradeClaim.ts`) outside this migration's scope and still take `repoInfo`.

## Configuration

No new configuration. Every module in this set already receives its `LaunchBoundary`/`RepoContext` from the existing boundary-construction path (`buildLaunchBoundary` in orchestrators, `config.repoContext` in phases).

## Gotchas

- `GitHubCodeHost` methods that don't yet have a bound-context shortcut (e.g. `getDefaultBranch`, `setSecret`) still construct a `gitContextForSync`/`gitContextForRepo` internally — this is the adapter's implementation detail, not a regression back to ad-hoc construction by the caller; the emitted `gh` command is unchanged from what the caller used to build directly.
- `adws/gitContext/gitContext.ts`'s forge-semantic methods (`commentOnIssue`, `listOpenIssues`, `fetchIssue`, `createIssue`, label and PR operations, …) are still present and still work — this migration only changed which route the orchestrators/phases above take to reach the forge. Deleting those methods from `GitContext` is a later slice (#797), not this one.
- A handful of modules named in earlier drafts of this migration (`adws/adwChore.tsx`, `adws/adwClearComments.tsx`, `unitTestPhase.ts`, `stackCoherenceReporter.ts`, `prReviewPhase.ts`'s `fetchPRDetails`/`getUnaddressedComments`, `workflowCompletion.ts`, `adwBuildHelpers.ts`) were **not** touched here: they either already route through `adws/github/*` wrappers without holding a `GitContext`, or (`workflowCompletion.ts`, `adwBuildHelpers.ts`) were verified to contain no forge-semantic calls at all.
- `notifyBlockedTransition`'s platform branch (`adwMerge.tsx`: `platform === Platform.GitHub ? notifyBlockedTransition : async () => undefined`) is deliberately **not** folded into a provider here — it is a Slack board-notification concern reached through `adws/github/hitlBoardNotifier`, outside the operations this slice's ports cover. It is deferred to the next wave.
