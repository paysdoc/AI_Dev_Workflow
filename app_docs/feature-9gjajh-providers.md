# Providers — Multi-Platform Abstraction Layer

## Overview

The providers module defines platform-agnostic interfaces for issue tracking, code hosting, and project board management, and supplies the `RepoContext` factory that assembles them into a single immutable context object. It is the sole forge-semantic boundary in ADW: `GitContext` and its adapters handle git plumbing only, and every issue/PR/label/board/secret/listing operation goes through the `IssueTracker`/`CodeHost`/`BoardManager` triple defined here. The GitHub adapter (`adws/providers/github/`) is the most complete implementation: it builds `gh` command strings, mints GitHub App credentials, and resolves veracious tokens on top of the forge-neutral `adws/gitContext/` core's `exec()` primitive (see `app_docs/feature-oqb76h-gitcontext-base-path-authority.md` for the core-side half of that split), and is one of exactly two packages exempted from the git/gh shell-out guard (`checkGitGhGuard.ts`) that may issue `gh` commands at all.

## Responsibilities

- Define the `IssueTracker`, `CodeHost`, and `BoardManager` interfaces that all workflow phases program against.
- Define `RepoIdentifier`, `Issue`, `PullRequest`, `ReviewComment`, `IssueSummary`, `PullRequestSummary`, `ForgeActionResult`, `IssueListField`, `IssueListQuery`, `IssueListEntry`, `MergedPullRequestRecord`, and related platform-agnostic data types.
- Expose the `Platform` enum (`github`, `gitlab`, `bitbucket`) and `BoardStatus` enum with the canonical five-column set.
- Parse provider configuration from `.adw/providers.md` (`## Code Host`, `## Issue Tracker`, and optional URL / project-key sections).
- Validate the working directory (must exist, be a directory, contain `.git`) and verify the `origin` remote matches the declared `RepoIdentifier` before constructing context.
- Resolve concrete provider implementations (GitHub, GitLab, Jira) based on the configured platforms.
- Return a `Readonly<RepoContext>` frozen with `Object.freeze`.
- Export GitHub-specific implementations (`createGitHubIssueTracker`, `createGitHubCodeHost`, `createGitHubBoardManager`), the GitLab code host (`createGitLabCodeHost(repoId, { token, instanceUrl }, { logger?, runCurl? })`), and the Jira issue tracker (`createJiraIssueTracker({ instanceUrl, projectKey, auth }, { logger?, fetchFn? })`), the latter two from injected configuration (#818).
- Own the raw GitHub payload shapes (`adws/providers/github/domain/issue.ts`: `GitHubUser`/`GitHubLabel`/`GitHubMilestone`/`GitHubComment`/`GitHubIssueListItem`/`GitHubIssue`/`IssueCommentSummary`; `domain/pullRequest.ts`: `PRReviewComment`/`PRDetails`/`PRListItem`/`RawPR`) that the mappers and the framework's GitHub API layer are typed against (#817).
- Cover the full set of forge operations orchestrators and phases need — labels (two error policies), issue creation/body edit, open-issue search, bulk issue listing with field projection, PR-by-branch lookup, approval read/write, merge, merged-PR listing, and repo secret — so callers never need to reach past the provider triple for a forge-semantic operation.
- **GitHub adapter (`adws/providers/github/`)**: builds every `gh` command string used anywhere in the codebase as pure, side-effect-free functions across five leaf modules in `commands/` (`issueCommands.ts`, `prCommands.ts`, `labelCommands.ts`, `boardCommands.ts`, `secretCommands.ts`); mints and caches GitHub App installation tokens (`appAuth.ts`); resolves a veracious token bound to `owner/repo` (`tokenResolver.ts`: App mint → PAT → `gh auth token`, never `process.env.GH_TOKEN`); implements the `TokenProvider` port for GitHub (`githubTokenProvider.ts`, additionally deciding the PAT-vs-installation-token question for `'alternateIdentity'` requests); and manages GitHub Projects V2 boards (`githubBoardManager.ts`: `findBoard`, `createBoard`, `ensureColumns`).
- `ghCommandRunner.ts`'s `createGhCommandRunner(ctx: GitContext)` is the GitHub adapter's only route to a child process — it imports nothing from `child_process`; every command reaches a process through the injected `GitContext.exec()`. Every command runs with `cwd: {kind: 'frameworkRoot'}` (never `basePath`, since these `gh` commands carry repository identity in the command string itself — issue #775) and a per-command credential env from `ctx.commandEnv({}, purpose)` (`purpose` defaults to `'default'`, or `'alternateIdentity'` for the elevated credential class Projects V2 board writes need).
- `ghIssueApi.ts`, `ghPrApi.ts`, and `ghRepoApi.ts` compose the GitHub adapter's full command surface as bound views over an injected `GitContext`: `ghIssueApi(run, owner, repo)` (14 issue ops) and `ghPrApi(run, owner, repo)` (13 PR ops) are leaf factories bound to one `owner`/`repo`; `createGhRepoApi(ctx): GhRepoApi` composes both plus the repo/label/secret/board remainder (`ghRepoOps`) into the full 35-operation surface. This is what the GitHub adapter's `listIssues`/`listMergedPullRequests`/`createPullRequest`/`setSecret`/`getDefaultBranch` methods (see Contracts) delegate to. All three are deep-import-only — never through the package barrel.

## Contracts & Invariants

- `createRepoContext` always validates the repo identifier, working directory, and git remote before resolving providers; it throws on any mismatch.
- The returned `RepoContext` is immutable (`Object.freeze`); workflow phases must not mutate it.
- `BoardManager` is optional on the context; platforms without board support simply leave `boardManager` undefined rather than throwing.
- Provider platform resolution falls back to `.adw/providers.md` when neither explicit options nor a `ProvidersConfig` object is supplied; GitHub is the default for both code host and issue tracker when the file is absent.
- Remote URL parsing supports both HTTPS and SSH URL formats, using a case-insensitive owner/repo comparison.
- `BOARD_COLUMNS` is a frozen constant defining the five canonical ADW board columns in display order; column colors and descriptions can only be set at creation time (GitHub API limitation).
- `IssueTracker.addLabel` and `IssueTracker.applyLabel` are deliberately separate methods, not one collapsed method: `addLabel` logs and swallows any error (fail-open, used where a caller like auto-merge must proceed regardless), `applyLabel` lazy-creates a missing label and rethrows anything else. Picking the wrong one silently changes failure behaviour in failure-cap escalation and auto-merge gating paths.
- `IssueTracker.fetchComments` throws on a malformed response; callers that need `[]` on failure (e.g. `adwUpgrade`'s failure-cap counter) must wrap the call in their own `try/catch` — the port does not swallow this for them.
- `IssueTracker.listIssues(query: IssueListQuery)` and `CodeHost.listMergedPullRequests(limit)` follow the same throws-not-swallows policy as `fetchComments`: both throw on failure and leave the swallow/retry decision to the caller. `listIssues` returns a forge-neutral field projection — an `IssueListEntry` only carries the fields the caller asked for in `query.fields`; fields not requested are absent (`undefined`), not empty placeholders, so a caller can tell "not requested" apart from "requested and empty."
- `IssueTracker.findOpenUpgradeIssue` keeps its ADW-domain name rather than being expressed as a generic label/search query — the ports are forge-neutral, not domain-neutral (`moveToStatus(BoardStatus)` already encodes ADW's board vocabulary), and doing otherwise would change the emitted command string for no benefit.
- Every GitHub adapter method for these operations delegates to an existing `adws/github/*` function (or, for `listIssues`/`listMergedPullRequests`/`createPullRequest`/`setSecret`/`getDefaultBranch`, to `createGhRepoApi(gitContext)` from `adws/providers/github/ghRepoApi.ts`) rather than reimplementing it, so the emitted `gh` command strings, error policy, and log lines are unchanged from calling that function directly — delegation is what makes provider migration behaviour-preserving. `GitHubIssueTracker.listIssues` delegates to the `adws/github/issueListApi.ts` wrapper's `listIssues(query, repoInfo)`, which itself calls `createGhRepoApi(...).listOpenIssues(query)` and parses the JSON result.
- `GitLabCodeHost` and `JiraIssueTracker` implement every port method but refuse (throw, naming the method) any operation with no GitLab/Jira capability yet, including `listMergedPullRequests`/`listIssues` — this keeps the interfaces total without expanding either adapter's real capability.
- **The GitLab and Jira adapters read zero `process.env` and import nothing from `adws/core`** (#818): configuration (`GitLabConfig`/`JiraConfig`) is injected through the factories; both log through the `Logger` port from `adws/gitContext` (default `consoleLogger`). The one environment-reading site is `repoContext.ts`'s `gitLabConfigFromEnv`/`jiraAuthFromEnv`, bound to `adws/core/environment.ts`'s constants and relocating to `adws/core/` with #823; `jiraAuthFromEnv` has no production caller until then because `Platform` has no Jira member.
- **`RepoIdentifier` is the only repository-identity shape.** `RepoInfo` (the old `{owner, repo}` framework shape) is gone from the tree — `parseGitHubRemoteUrl`/`readLocalRepoInfo` (`githubIdentity.ts`) return `RepoIdentifier` with `platform: Platform.GitHub`, the GitHub adapter classes (`GitHubIssueTracker`, `GitHubCodeHost`, `GitHubBoardManager`) hold only their bound `repoId: RepoIdentifier`, and the `toRepoInfo` mapper no longer exists (#817).
- **`adws/providers/github` is one of exactly two entries** in `checkGitGhGuard.ts`'s closed `EXEMPT_PACKAGES` set (the other is `adws/gitContext` itself) — it may issue `gh` commands, but only by feeding command strings into the core's `GitContext.exec`; it holds no independent spawn capability of its own.
- **`appAuth.ts` reads zero `process.env` directly** — `isGitHubAppConfigured`/`getInstallationToken` take a `GitHubAppConfig` (`appId?`, `appSlug?`, `privateKeyPath?`) as an explicit argument; the one process-env-reading site for these three variables is the ADW wiring shim `adws/github/githubAppAuth.ts`, which reads them fresh on every call and passes the resulting config in. The bearer credential never appears in argv or a thrown error (issue #780): it travels to `curl` over the `--config` stdin channel, and failure messages echo at most GitHub's own `message` field, with `redactBearerTokens` as a final net over untrusted text.
- **`tokenResolver.ts`'s `resolveContextToken` never reads `process.env.GH_TOKEN`** as a fallback — App mint (any throw propagates loudly, e.g. a foreign/uninstalled App identity) → PAT → `gh auth token` → throws `resolveContextToken: no veracious token for owner/repo`. `createGitHubTokenProvider` is called once per command, never memoised; the only caching on this path is `appAuth.ts`'s expiry-aware installation-token cache keyed by `owner/repo`.
- **The GitHub adapter's command builders, auth/token modules, and API composition views are deep-import-only** and never re-exported through the package barrel (`adws/providers/github/index.ts`) — the barrel's surface is limited to the provider-interface factories (`createGitHubIssueTracker`, `createGitHubCodeHost`/`GitHubCodeHost`, `createGitHubBoardManager`), `mappers.ts`, and (type-only, since #817) the eleven raw shapes from `domain/issue.ts`/`domain/pullRequest.ts`. Bootstrap-adjacent modules (`gitContextFactory.ts`, `launchGitContext.ts`, `githubAppAuth.ts`, `adws/core/targetRepoManager.ts`) must deep-import specific files rather than the barrel, since importing the barrel from any of them would close an import cycle through `githubCodeHost.ts`.
- **`githubBoardManager.ts` preserves the `'alternateIdentity'` purpose on every GraphQL call** (`findBoard`, `createBoard`, `updateStatusFieldOptions`/`ensureColumns`, `getStatusFieldOptions`) since Projects V2 board writes on user-owned repos require the PAT credential path, not the App installation token.

## Configuration

Provider platforms are read from `.adw/providers.md` in the working directory. Supported sections: `## Code Host`, `## Issue Tracker`, `## Code Host URL`, `## Issue Tracker URL`, `## Issue Tracker Project Key`. All sections are optional; GitHub is the default. Platforms can also be passed explicitly via `RepoContextOptions.codeHostPlatform` / `issueTrackerPlatform`, or via a `ProvidersConfig` object injected by the project config layer.

The GitHub adapter additionally takes a `GitHubAppConfig` (`appId?`, `appSlug?`, `privateKeyPath?`) as an explicit argument to `appAuth.ts` — never read from `process.env` inside the adapter itself. The one process-env-reading site is `adws/github/githubAppAuth.ts`'s `readAppConfig()`, which reads `GITHUB_APP_ID`/`GITHUB_APP_SLUG`/`GITHUB_APP_PRIVATE_KEY_PATH` fresh on every call. `GhCommandRunner.run(command, opts?)` accepts `opts.input?` for stdin and `opts.purpose?: 'default' | 'alternateIdentity'` (default `'default'`).

`GitLabConfig` (`token`, `instanceUrl`) and `JiraConfig` (`instanceUrl`, `projectKey`, `auth: JiraAuth`) are injected into their respective factories (#818); ADW's wiring (`repoContext.ts`'s `gitLabConfigFromEnv`/`jiraAuthFromEnv`) reads `GITLAB_TOKEN`, `GITLAB_INSTANCE_URL`, `JIRA_EMAIL`, `JIRA_API_TOKEN`, and `JIRA_PAT` to build them; `projectKey` comes from the caller's own configuration, not an environment variable.

## Gotchas

- `BoardManager` resolution errors are silently swallowed at construction time; callers that need board support must check for `undefined` before calling board methods.
- The git remote validation compares against `origin` only; repositories with non-standard remote names will always fail.
- Platform string parsing is case-insensitive but must exactly match one of the `Platform` enum values (`github`, `gitlab`, `bitbucket`); any other string throws.
- `dataTypes.ts` in `adws/types/` is a re-export barrel that delegates to `issueTypes.ts`, `issueRouting.ts`, `agentTypes.ts`, and `workflowTypes.ts`; it is kept only for backward compatibility.
- `IssueListQuery.fields` drives the shape of the response, not just a display hint: requesting `['number', 'title']` and then reading `.body` on a result yields `undefined`, not a parse error — callers must request every field they intend to read.
- The GitHub adapter's command builders and API composition views are not on the barrel — `import { fetchIssueCmd } from 'adws/providers/github'` does not work; deep-import `adws/providers/github/commands/issueCommands` (or `ghIssueApi`/`ghPrApi`/`ghRepoApi`) instead.
- `ghCommandRunner.ts` cannot spawn a process on its own, and its cwd class (`frameworkRoot`) is not overridable — a command that needs the actual git working tree (branch/commit/worktree operations) does not belong on this seam; it stays a `GitContext` method.
- Board writes silently degrade to the resolved `'default'` token, not an error, when no PAT is configured — `createGitHubTokenProvider`'s `'alternateIdentity'` branch only short-circuits to `alternateIdentityPat` when it is non-blank.
- `githubBoardManager.ts`'s private `gh` accessor constructs a fresh `GhCommandRunner` on every property access (not cached on the instance), so each call re-resolves `gitContextForRepo(this.repoId)`.
- The domain modules (`adws/providers/github/domain/issue.ts`, `domain/pullRequest.ts`) are deep-import-only, like the rest of the adapter's internals — the package barrel (`adws/providers/github/index.ts`) re-exports all eleven shapes type-only for external consumption, but framework consumers still deep-import from `domain/*` directly (the barrel closes an import cycle through `githubCodeHost.ts` → `adws/core`, same rationale as the command builders and API composition views above).
- `mappers.ts` and `domain/` are inside `EXTRACTION_SCOPE` since #817: any import there that resolves outside `adws/gitContext`/`adws/providers` fails `bun run lint:git-guard`.
- `ghIssueApi`/`ghPrApi`/`ghRepoApi` are deliberately absent from the git/gh guard's `PROVIDER_CONSTRUCTORS`/`CONTEXT_CONSTRUCTORS` name sets — a bound view over a caller-supplied `GitContext` selects no identity, so it is not a construction site the guard's `unsanctioned-construction` rule needs to see.
- `adws/providers/gitlab/**` and `adws/providers/jira/**` are inside `EXTRACTION_SCOPE` since #818.
- `runCurl`/`fetchFn` (`GitLabApiClientDeps`/`JiraApiClientDeps`) are hermetic transport test seams, not capability — production always defaults to a real curl / global `fetch`.
- `validateWorkingDirectory`/`parseOwnerRepoFromUrl` live in `adws/providers/workspaceValidation.ts` (moved out of `repoContext.ts` in #818 to keep it under the 300-line cap) and are re-exported from `repoContext.ts` unchanged.
