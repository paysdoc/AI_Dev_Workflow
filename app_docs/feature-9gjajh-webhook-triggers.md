# Webhook Triggers

## Overview

The webhook trigger is ADW's real-time event handler: an HTTP server that receives GitHub webhook events, constructs an immutable `LaunchBoundary` per event from the payload's repository, and immediately routes the event to the appropriate handler. It complements the cron sweeper by reacting to events within seconds rather than waiting for the next poll cycle. Because a single webhook process handles events for many repositories concurrently and asynchronously, each event gets its own authoritative `LaunchBoundary` (a `GitContext` plus the bound `IssueTracker`/`CodeHost` pair) at receipt — before any `await` — so interleaved multi-repo events cannot cross-contaminate auth, forge reads, or worktree base paths. The dispatch is wrapped in a per-event resilience boundary (`webhookEventBoundary.ts`, an unrelated naming coincidence — it predates and is distinct from the `LaunchBoundary` type) so one event's failure — synchronous or asynchronous — is contained, logged, and Slack-alerted instead of crashing the long-running process.

## Responsibilities

- `trigger_webhook.ts`: starts an HTTP server on port 8001 (or a random port if 8001 is taken), validates webhook signatures, and routes events by type — `issues`, `issue_comment`, `pull_request`, `pull_request_review`, and `pull_request_review_comment`.
- The `req.on('end', …)` callback is a thin try/catch: it calls `dispatchWebhookEvent(req, res, rawBody)` (the full dispatch, extracted verbatim into a top-level hoisted function below `const server = …`) and routes any synchronous throw to `containEventFailure`, which reports the failure and answers `500` — guarded by `res.headersSent` so a throw after a response was already flushed cannot double-respond.
- `dispatchWebhookEvent` is exported and takes an optional 4th `mintEventBoundary` parameter (default: the real `buildEventBoundary` from `webhookRepoResolver.ts`), so BDD steps can drive a full dispatch with a fake/recording boundary instead of a real `LaunchBoundary`. The module also carries an entry-script guard (`process.argv[1]?.includes('trigger_webhook')`, mirroring `trigger_cron.ts`'s `cronBoundary` guard) so importing `trigger_webhook.ts` in a test never binds a real HTTP port.
- `webhookEventBoundary.ts`: the per-event resilience boundary. `safeParseWebhookBody` (never throws) and `describeWebhookEvent` (pure) extract a `WebhookEventContext { event, repo, issueNumber, prNumber }` from the raw payload, each field defensively falling back to `'unknown'`/`null`. `formatWebhookFailureLog`/`formatWebhookFailureAlert` are pure string builders naming event type, `owner/repo`, and issue/PR. `reportWebhookEventFailure(context, error, deps?)` logs at `'error'` and fires a best-effort, never-awaited Slack alert via `postSlack`; it is contractually never-throwing, even if the logger or notifier itself throws.
- Every async continuation on the request path (`isAdwRunningForIssue(…).then(…)` catch, `handlePullRequestEvent(…).catch(…)`, `handleIssueClosedEvent(…).catch(…)`, and the `issues.opened` IIFE's generic catch) calls `reportWebhookEventFailure` instead of a bespoke `log(...)` line — no `500` is attempted there, since those deliveries were already answered `200 processing` before the continuation ran and a response cannot be retracted.
- The `GET /health` IIFE has a terminal `.catch` that logs and answers `500` (guarded by `res.headersSent`) instead of letting a probe throw become an unhandled rejection; it does not go through `reportWebhookEventFailure` — a health probe is not a GitHub event and must not page Slack.
- Per-event repo resolution via `resolveWebhookRepo(body)` (from `webhookRepoResolver.ts`): parses the raw payload `repository` object into `{ repoInfo, targetRepo, targetRepoArgs }`, or `null` when no usable repository is present. Pure — no I/O. Internally calls `parseRepoFullName(repoFullName)` — the one `owner/repo` parse that survives `githubApi.ts`'s deletion (#821), because it runs upstream of any provider (it decides which repository the per-event boundary will be built for), so it cannot itself be migrated onto one.
- Per-event `LaunchBoundary` construction via `buildEventBoundary(resolution.targetRepo)` (both now in `webhookRepoResolver.ts`, not `trigger_webhook.ts`): wraps `buildLaunchBoundary` in a try/catch, constructed synchronously before any `await`. On success, `eventBoundary` is an immutable `{ gitContext, repoId, providers }` triple that all async continuations for this event carry — owner/repo, base path, auth token, and the bound `IssueTracker`/`CodeHost` pair all travel together. On failure it logs a `warn` (naming the repository) and returns `undefined`; the long-lived server never crashes on one malformed event. `selfHostBoundary()` is the memoised counterpart used only when the payload names no repository at all (GitHub never sends one; defensive).
- `issue_comment` alone keeps a pre-boundary self-host fallback: `commentBoundary = eventBoundary ?? (resolution ? undefined : selfHostBoundary())` — i.e. the fallback fires only when the payload named NO repository at all, never when a named repo's boundary failed to mint (that case reports `boundary_unavailable` instead of silently redirecting to the self-host identity).
- Threads the per-event boundary through all spawn paths: `classifyAndSpawnWorkflow` → `evaluateCandidate` (worktree/takeover path resolution) takes `commentBoundary`/`eventBoundary` as a required parameter; `routeIssueOpened` (issues.opened router) takes `boundary: LaunchBoundary` as a required field of its params; `handleIssueClosedDependencyUnblock` (closed-event dependency unblocking, in `issueClosedUnblockRouter.ts`) takes `boundary: LaunchBoundary` as a required parameter.
- Ensures a cron process is running for each repo it handles (`ensureCronProcess` before all per-event branching).
- Handles `issues.opened`: routes through `routeIssueOpened` (label-based routing); applies a 60-second per-issue cooldown to de-duplicate rapid webhook delivery.
- Handles `issues.closed`: calls `handleIssueClosedEvent` to clean up worktrees, delete the remote branch, and unblock or close dependent issues.
- Handles `issue_comment.created`: checks for `## Cancel` (calls `handleCancelDirective`), `## Retry` (calls `handleRetryDirective`), or an actionable ADW comment pattern (dependency + concurrency check, then `classifyAndSpawnWorkflow`).
- Handles `pull_request.closed`: calls `handlePullRequestEvent` to write `discarded` state and close the linked issue when the PR was abandoned (closed without merge).
- Handles `pull_request_review` and `pull_request_review_comment`: spawns `adwPrReview.tsx` with a 60-second per-PR cooldown; ignores `approved` review events (merge is handled by cron).
- `webhookRepoResolver.ts`: per-event repo identity resolution and boundary construction, extracted from `trigger_webhook.ts` so it is unit-testable without starting the HTTP server. Exports the pure `resolveWebhookRepo(body)` / `WebhookRepoResolution` interface (identity resolution — no I/O), plus the boundary-minting `buildEventBoundary(targetRepo)` and the memoised `selfHostBoundary()` (both do I/O via `buildLaunchBoundary`).
- `validateWebhookSignature`: validates the `x-hub-signature-256` header using HMAC-SHA256 with constant-time comparison.
- `handlePullRequestEvent`: for abandoned PRs, extracts the issue number from the branch name, writes `discarded` state for the adwId, and closes the linked issue with a comment.
- `handleIssueClosedEvent(issueNumber, boundary, cwd, targetRepoArgs, deps?)`: reads state to detect active vs. finished workflows, applies a grace period guard, removes worktrees, deletes the remote branch, and dispatches dependency unblocking or cascaded closure depending on the workflow stage. `boundary` is `LaunchBoundary | undefined` — comment/dependency reads are skipped when it is absent, and worktree/branch cleanup degrades to a no-op count rather than throwing.
- `classifyAndSpawnWorkflow(issueNumber, boundary, targetRepoArgs, existingAdwId?, precomputedDecision?, labelRouting?)` (in `webhookGatekeeper`): enforces auth gate, routes `adw:upgrade` issues directly to `adwUpgrade.tsx`, calls `evaluateCandidate({ issueNumber, boundary })` for takeover decisions (unless a cron-supplied `precomputedDecision` skips re-evaluation), classifies and spawns the appropriate workflow script. `boundary` is a required `LaunchBoundary` — the webhook always resolves `commentBoundary`/`eventBoundary` to a real value before calling this (the `boundary_unavailable`/`no_repository` ignore responses happen first).
- `handleIssueClosedDependencyUnblock(closedIssueNumber, boundary, targetRepoArgs, deps?)` (in `issueClosedUnblockRouter.ts`): finds open issues that depend on the closed issue, re-evaluates their eligibility, and spawns using the required per-event `boundary` for correct worktree base resolution. Uses `extractDependencies` (the same prose-aware extractor `findOpenDependencies` uses for creation-time detection/defer) rather than the heading-only `parseDependencies`, so a dependent deferred via a prose `- blocked by #N` declaration is correctly unblocked when its blocker closes.
- `spawnDetached`: spawns a detached child process with `cwd` pinned to `REPO_ROOT` and relative script paths resolved.
- `ensureCronProcess`: checks whether a cron process is alive for the event's repo and spawns one if not.
- `closeAbandonedDependents`: finds open issues that depend on an abandoned issue and closes them with an explanatory comment.
- `issueOpenedRouter.ts`: `routeIssueOpened(params, deps)` — `params.boundary: LaunchBoundary` is a required field, forwarded to `IssueOpenedRouterDeps.classifyAndSpawn` (which calls `classifyAndSpawnWorkflow(n, boundary, args, …)`).

## Contracts & Invariants

- **A crashing event handler never terminates the webhook server process.** Every unguarded reach on the request path — synchronous (`dispatchWebhookEvent`) or asynchronous (the four `.catch`/IIFE sites) — is routed through the boundary. The boundary itself (`reportWebhookEventFailure`) is contractually never-throwing.
- **The `500` response is never delayed by Slack.** The alert is fired via `void Promise.resolve(notify(...)).catch(...)`, never `await`ed; a black-holed `SLACK_WEBHOOK_URL` cannot stall a delivery.
- **`res.headersSent` is the single switch between "answer 500" and "log only".** Failures caught before a response was flushed (the synchronous path) get a `500`; failures in continuations that already answered `200 processing` do not attempt a second response — HTTP has no retraction.
- **Per-event `LaunchBoundary` is constructed synchronously at receipt, before any `await`/`.then`.** This makes the boundary an immutable per-event capture (its own `GitContext` plus its own bound `IssueTracker`/`CodeHost`); no later event can overwrite it, and the async continuations carry the right identity and providers regardless of interleaving. It is the only sanctioned construction site on this path — never a process-global.
- `resolveWebhookRepo` returns `null` for payloads without a usable `repository.full_name` + (`clone_url` or `html_url`); all downstream callers guard on `resolution !== null`.
- `ensureCronProcess` is called whenever `resolution` is non-null — even when the boundary itself subsequently fails to mint. Resolution (the payload parse) and boundary construction (the mint) are independent steps; the `ensureCronProcess`-before-branching ordering invariant is over `resolution`, not over a successfully-minted boundary.
- Webhook signature validation uses `timingSafeEqual` to prevent timing attacks; when `GITHUB_WEBHOOK_SECRET` is not set, validation is skipped with a warning.
- The auth gate is checked before every spawn — when set, all spawn paths return immediately with `status: ignored`.
- The grace period guard in `handleIssueClosedEvent` prevents cleanup when the orchestrator is actively running within `GRACE_PERIOD_MS` of its last phase activity.
- For PR-closed events, only abandoned (not merged) PRs trigger the `discarded` state write and issue closure.
- `extractIssueNumberFromBranch` uses the `issue-N` pattern; PRs without this pattern in the branch name are ignored on closure.
- `classifyAndSpawnWorkflow` intercepts `adw:upgrade` issues before calling `evaluateCandidate` to prevent the classifier from mislabeling the upgrade tracking issue.
- The `precomputedDecision` path in `classifyAndSpawnWorkflow` (cron) skips re-calling `evaluateCandidate` — the cron already evaluated it against `cronBoundary` and passes the decision through; `boundary` is still required on every call (cron passes `cronBoundary`, the webhook passes `commentBoundary`/`eventBoundary`), it is only the *decision* that is optionally pre-computed.

## Configuration

Server port defaults to `process.env.PORT || 8001`. `GITHUB_WEBHOOK_SECRET` enables signature validation. GitHub App credentials (`GITHUB_APP_ID`/`GITHUB_APP_SLUG`/`GITHUB_APP_PRIVATE_KEY_PATH`) are read fresh per command by `adws/core/githubAppAuth.ts` — there is no startup-time "activation" call. The `PR_REVIEW_COOLDOWN_MS` and `ISSUE_COOLDOWN_MS` cooldowns are module-level constants (60 000 ms each). The server listens on `0.0.0.0`. `.env` is loaded at the top of `trigger_webhook.ts` via an explicit `import '../core/environment'`.

## Gotchas

- **Per-command auth cutover is complete.** `ensureAppAuthForRepo`/`activateGitHubAppAuth` no longer exist anywhere in the tree — every `gh` command resolves its credential through the `TokenProvider` port on each call (`adws/gitContext`'s `commandEnv()`), never a process-global `GH_TOKEN` write. `checkIssueEligibility`, `isAdwRunningForIssue`, and every other in-process forge read on this path go through the per-event boundary's `IssueTracker`/`CodeHost` (`commentBoundary.providers`/`eventBoundary.providers`), not a legacy `gh` helper. See `app_docs/feature-oqb76h-gitcontext-base-path-authority.md` for the full auth-model contract.
- **`pull_request*` spawn paths do not receive the per-event boundary:** they `spawnDetached` with `--target-repo` args; the spawned child mints its own `LaunchBoundary` from those args at its own launch boundary. No in-process takeover on that path, so no boundary needed in-process.
- **`webhookRepoResolver.ts` cannot be bypassed for testing:** `trigger_webhook.ts` starts an HTTP server on import, so it cannot be imported by a unit test. `resolveWebhookRepo` is extracted precisely to provide a directly importable, I/O-free seam for the per-event boundary test (`webhookRepoResolver.test.ts`).
- **Two-context isolation is proven at the command boundary:** `webhookRepoResolver.test.ts` injects a recording `exec` into each context's `GitContextDeps` and asserts that each context's `getCurrentBranch()` — a git op — records its own cwd/token, including immunity to a mid-flight `process.env.GH_TOKEN` overwrite (vestmatic #181 bleed) and to interleaved two-repo execution. `GitContext` no longer has a `defaultBranch()` method at all (issue #797 deleted every forge-semantic method from `GitContext`; the default-branch read now lives on `CodeHost`/`GhRepoApi` as a `gh repo view` call, not a `GitContext` op), so the per-event/per-repo **cwd** isolation assertions (§3a "recorded command cwd equals the context basePath", §4 "each context records its own basePath as cwd") are pinned to `getCurrentBranch()`, which is what actually resolves a cwd per repo. Any new cwd-isolation assertion must use a git-classified `GitContext` op for the same reason — forge ops no longer live on `GitContext` to assert against.
- The `issue_comment` handler is fully async via `.then().catch()` but the HTTP response is sent immediately (`status: processing`). Errors in the async continuation are logged but not surfaced to the client.
- The `pull_request_review` handler ignores `approved` reviews by design; ADW relies on the cron + `adwMerge.tsx` path to poll approval state, not real-time merge-on-approve.
- When port 8001 is in use and `GITHUB_WEBHOOK_SECRET` is set (tunnel mode), the server throws instead of falling back to a random port — a tunnel must have a fixed port.
- `recentPrReviewTriggers` and `recentIssueTriggers` are in-memory maps and reset on server restart; rapid consecutive events within the cooldown window after a restart may both be processed.
- **`handleIssueClosedDependencyUnblock` was moved out of `webhookGatekeeper.ts` into its own `issueClosedUnblockRouter.ts`** (mirrors `issueOpenedRouter.ts`'s pure-selection + DI pattern via `selectDependents`/`DependencyUnblockDeps`) to fix issue #753: the old inline version used `parseDependencies` (heading-only `## Blocked by` parser), which missed dependents declared only via a prose `- blocked by #N` line — those issues silently never re-evaluated after their blocker closed. `trigger_webhook.ts` and `webhookHandlers.ts` re-export/import it from the new module.
- **No `process.on('uncaughtException')` net is installed, deliberately (#776).** A process-level handler would also swallow genuinely fatal, non-request-scoped errors and leave a half-initialised daemon serving, with no place to answer the failed delivery. The fix instead removes every unguarded fire-and-forget on the request path.
- **The dispatch is extracted, not deleted or relocated.** `dispatchWebhookEvent` holds the exact previous callback body, moved verbatim into a top-level function below `const server = …` (function declarations hoist, so file order is preserved) — every `if (event === …)` branch stays in `trigger_webhook.ts` in the same order. `webhookEventBoundary.ts` holds only the boundary/reporting logic, which has no branch-marker coupling.
- **`adws/__tests__/triggerWebhook.test.ts` asserts on source text**, not runtime behaviour — brace-matched extraction of the catch blocks (`getOpenedCatchBlock`/`getCommentCatchBlock`) plus a wiring guard (`try {` + `containEventFailure(` in the `req.on('end'` body; `.catch(` terminating the `/health` IIFE). Real containment behaviour is proven by `features/per-issue/feature-776.feature` (`@adw-776`, 16 scenarios) instead.
- **Every contained failure pings Slack, unthrottled.** A retry storm (GitHub redelivering a failing event) produces one alert per delivery by design — an ongoing outage should be loud. No dedup/rate-limit exists; if needed, it belongs in `slackNotifier.ts`.
