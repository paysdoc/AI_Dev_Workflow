# GitHub Forge Adapter — Command Builders, App Auth, Token Resolution, Executor Seam

## Overview

`adws/providers/github/` is the GitHub-specific forge adapter built over the forge-neutral `adws/gitContext/` core. It owns everything the core deliberately knows nothing about: gh command-string construction, GitHub App JWT/installation-token minting, the veracious token resolution order, and the `TokenProvider` port's GitHub implementation. It is structurally exempt from `adws/checkGitGhGuard.ts`'s `git-gh-shellout` rule as one of exactly two entries in the guard's closed `EXEMPT_PACKAGES` array — the other being `adws/gitContext` itself, which may run `git`. This package may issue `gh` commands, but only by feeding command strings into the core's `GitContext.exec` — it holds no independent spawn capability.

The package's only route to a child process is `ghCommandRunner.ts`'s `createGhCommandRunner(ctx: GitContext)`. It imports nothing from `child_process`; every command it issues reaches a process through the injected `GitContext`'s `exec()` method. It reproduces the core's private `#runRepoApi` classifier verbatim on the public surface: every command runs with `cwd: {kind: 'frameworkRoot'}` (the injected framework repo root, never `basePath`, regardless of whether the target workspace has ever been cloned — issue #775's repo-API contract, since these `gh` commands carry their repository identity in the command string itself, not in the working directory) and a per-command credential env assembled from `ctx.commandEnv({}, purpose)`, where `purpose` defaults to `'default'` and callers may request `'alternateIdentity'` for the elevated credential class.

`appAuth.ts` mints GitHub App installation tokens via a JWT + `curl`-based token exchange. As of this consolidation it reads zero `process.env` variables directly — configuration (`appId`, `appSlug`, `privateKeyPath`) is injected via a `GitHubAppConfig` value on every call. The sole site in the codebase that reads `GITHUB_APP_ID`/`GITHUB_APP_SLUG`/`GITHUB_APP_PRIVATE_KEY_PATH` from `process.env` is the ADW wiring shim `adws/github/githubAppAuth.ts`, which reads them fresh on every call (not captured once at module load) and passes the resulting `GitHubAppConfig` into this package's `isGitHubAppConfigured`/`getInstallationToken`.

`tokenResolver.ts` is the single veracious token resolver: given `owner`/`repo` plus an `isAppConfigured`/`mintInstallationToken`/`ghAuthToken` dependency bag, it returns a token provably bound to that `owner/repo` and never reads `process.env.GH_TOKEN` as a fallback. `githubTokenProvider.ts` wraps it as the `TokenProvider` port's GitHub implementation (`createGitHubTokenProvider`), additionally owning the PAT-versus-installation-token decision for `'alternateIdentity'` requests.

As of #793, this package also owns the GitHub half of bootstrap identity resolution and clone-URL construction — the pieces the git core (`adws/gitContext/`) deliberately no longer knows about. `githubIdentity.ts` holds `RepoInfo`, the HTTPS/SSH GitHub remote-URL regexes, `parseGitHubRemoteUrl`, `readLocalRepoInfo` (composing the core's `readOriginRemoteUrl` with the parse), the App bot-identity derivation, the `ADW_BOT_FALLBACK_IDENTITY` default, and `resolveBootstrapGitIdentity` (composing the core's `readEnvGitIdentity`/`readGitConfigIdentity` for steps 2–3 of its four-step order). `cloneUrl.ts` holds `convertToSshUrl`, the HTTPS→SSH rewrite the core used to apply silently — now applied one call frame earlier, by `adws/core/targetRepoManager.ts`, before the core's `ensureRepoWorkspace`/`cloneRepo` ever see the URL. `ghAuthToken.ts` holds the `execSync('gh auth token')` credential read that #792 flagged as an open question and #793 resolved in the adapter's favor (see Gotchas). All three modules compose the core's generic readers rather than shelling out or duplicating logic — see `app_docs/feature-oqb76h-gitcontext-base-path-authority.md` for the core-side half of the split.

`githubBoardManager.ts` (Projects V2 board management: `findBoard`, `createBoard`, `ensureColumns`) is rewired onto this seam: its private `gh` accessor constructs a `GhCommandRunner` from a `GitContext` (via `gitContextForRepo`) and every GraphQL call runs `this.gh.run(graphQLCmd(...), { purpose: 'alternateIdentity' })` instead of the pre-consolidation `GitContext.runGraphQL`/`runGraphQLInput` methods.

**Deep-import-only rule:** consumers must import specific modules directly (e.g. `adws/providers/github/appAuth`, `adws/providers/github/tokenResolver`, `adws/providers/github/githubTokenProvider`, `adws/providers/github/ghCommandRunner`, and as of #793 `adws/providers/github/githubIdentity`, `adws/providers/github/cloneUrl`, `adws/providers/github/ghAuthToken`) — never the package barrel (`adws/providers/github/index.ts`) — from `gitContextFactory.ts`, `launchGitContext.ts`, `githubAppAuth.ts`, or `adws/core/targetRepoManager.ts`. The barrel re-exports `createGitHubIssueTracker`, `createGitHubCodeHost`/`GitHubCodeHost`, `createGitHubBoardManager`, and the `mappers.ts` surface — importing it from those bootstrap-adjacent modules would close an import cycle through `githubCodeHost.ts`. The ~41 gh command-string builders in `commands/*.ts`, and the three #793 identity/clone-URL/gh-auth modules, are deliberately **not** re-exported through the barrel at all; only deep imports reach them, keeping the barrel's surface limited to the provider-interface implementations.

## Responsibilities

- Build every gh command string used anywhere in the codebase, as pure, side-effect-free functions (no `exec`, no `process.env`) split across five leaf modules in `commands/`: `issueCommands.ts` (issue fetch/comment/state/close/title/comments/labels/create/update/find-upgrade/delete-comment, `listOpenIssuesCmd`, `issueCommentsCmd`), `prCommands.ts` (PR find-by-branch/details/reviews/comments/comment/merge/approve/approval-state/list/create with optional `labels?`/`fetchMergedPRsCmd`/`prChangedFilesCmd`), `labelCommands.ts` (`createLabelCmd`, `applyLabelCmd`), `boardCommands.ts` (Projects V2 GraphQL query/mutation builders and parsers: `graphQLCmd`, `graphQLInputCmd`, `projectQueryCmd`, `itemQueryCmd`, `fieldQueryCmd`, `moveStatusCmd`, `parseProjectId`, `parseIssueItem`, `parseStatusField`), `secretCommands.ts` (`setSecretCmd`)
- Mint and cache GitHub App installation tokens (`appAuth.ts`): `isGitHubAppConfigured(config)`, `getInstallationToken(config, owner, repo, deps?)`, JWT creation, installation-ID and token caching (`REFRESH_BUFFER_MS` = 5 minutes before expiry), `clearAppAuthCaches()` (test-only)
- Resolve a veracious token bound to `owner/repo` (`tokenResolver.ts`): App mint → PAT → `gh auth token`, never `process.env.GH_TOKEN`
- Implement the `TokenProvider` port for GitHub (`githubTokenProvider.ts`): `createGitHubTokenProvider(input): TokenProvider` — wraps `resolveContextToken` unchanged, and additionally decides the `'alternateIdentity'` credential (a configured `alternateIdentityPat` short-circuits the App mint; otherwise resolves identically to `'default'`)
- Provide the adapter's only route to a child process (`ghCommandRunner.ts`): `createGhCommandRunner(ctx: GitContext): GhCommandRunner` — `run(command, opts?)` always spawns with `{kind: 'frameworkRoot'}` and a per-command credential env from `ctx.commandEnv({}, opts.purpose ?? 'default')`
- Manage GitHub Projects V2 boards (`githubBoardManager.ts`): `createGitHubBoardManager(repoId): BoardManager` — `findBoard`, `createBoard`, `ensureColumns` (merges required ADW columns into the existing Status field's options via `mergeStatusOptions`, preserving option IDs and anchoring new columns near existing ADW columns of adjacent `order`)
- Own GitHub identity conventions on behalf of the core (`githubIdentity.ts`, #793): `RepoInfo`, `parseGitHubRemoteUrl(remoteUrl): RepoInfo | null` (pure HTTPS/SSH regex parser, the single source of truth for GitHub remote-URL parsing), `readLocalRepoInfo(cwd?): RepoInfo` (composes the core's `readOriginRemoteUrl` with the parse; throws `Failed to get repo info: …` wrapping either failure), `ADW_BOT_FALLBACK_IDENTITY`, `resolveBootstrapGitIdentity(deps?): GitIdentity` (App bot → `GIT_AUTHOR_*`/`GIT_COMMITTER_*` → `git config user.*` → `ADW Bot` default, composing the core's `readEnvGitIdentity`/`readGitConfigIdentity` for steps 2–3), `BootstrapIdentityDeps`
- Construct a ready GitHub clone URL (`cloneUrl.ts`, #793): `convertToSshUrl(cloneUrl): string` — HTTPS GitHub URLs become `git@github.com:owner/repo.git`; SSH, other forges, and unparseable/empty input pass through unchanged
- Resolve the bootstrap `gh` credential (`ghAuthToken.ts`, #793): `ghAuthToken(): string` — `execSync('gh auth token')`, returns `''` on failure; the pre-context read that produces the credential `ghCommandRunner`'s TokenProvider needs, so it cannot itself route through the runner
- Re-export the provider-interface implementations through the package barrel (`index.ts`): `createGitHubIssueTracker`, `createGitHubCodeHost`/`GitHubCodeHost`, `createGitHubBoardManager`, and `mappers.ts` — but never the command builders, the auth/token modules, or the #793 identity/clone-URL/gh-auth modules, all of which are deep-import-only

## Contracts & Invariants

- **`appAuth.ts` reads zero `process.env`** — `isGitHubAppConfigured`/`getInstallationToken` take a `GitHubAppConfig` (`appId?`, `appSlug?`, `privateKeyPath?`) as an explicit first argument; any missing field means "not configured." The one process-env-reading site in the codebase for these three variables is `adws/github/githubAppAuth.ts`, which reads them fresh per call and passes them in
- **The bearer credential never appears in argv or a thrown error** (issue #780) — it travels to `curl` over the `--config` stdin channel (`buildCurlConfig`), and `requestGitHubApi` reads the HTTP status off a `write-out` trailer rather than relying on `execFileSync`'s `-f`-style throw, so failure messages are composed via `describeApiFailure`/`describeStatus`, echoing at most GitHub's own `message` field, never a raw response body. `redactBearerTokens` is the final net over untrusted text (curl stderr, GitHub error bodies)
- **`ghCommandRunner.ts` imports nothing from `child_process`** — the adapter's only route to a spawned process is `GitContext.exec`, injected via the `GitContext` passed to `createGhCommandRunner`
- **Every command issued through the runner uses the framework-root cwd class** — `{kind: 'frameworkRoot'}`, never `basePath`, mirroring the core's `#runRepoApi` classifier and issue #775's repo-API contract: these commands carry repository identity in the command string (`--repo owner/repo`, `gh api repos/owner/repo/…`, or GraphQL variables), not in the working directory, so they run correctly even when the target workspace has never been cloned on this host
- **`resolveContextToken` never reads `process.env.GH_TOKEN`** — App configured → bound mint (any throw, e.g. foreign/uninstalled App identity, propagates loudly, never substituted with an ambient token); else PAT; else `gh auth token`; else throws `resolveContextToken: no veracious token for owner/repo`
- **`createGitHubTokenProvider` is called once per command, never memoised** — the only caching on this path is `appAuth.ts`'s expiry-aware installation-token cache (keyed by `owner/repo`), which lives inside the credential source itself, not in the provider
- **`'alternateIdentity'` purpose is preserved on every `githubBoardManager` GraphQL call** — `findBoard`, `createBoard`, `updateStatusFieldOptions` (called from `ensureColumns`), and `getStatusFieldOptions` all pass `{ purpose: 'alternateIdentity' }` to `this.gh.run(...)`, since Projects V2 board writes on user-owned repos require the PAT credential path, not the App installation token
- **Deep-import-only from bootstrap-adjacent modules** — `gitContextFactory.ts`, `launchGitContext.ts`, `adws/github/githubAppAuth.ts`, and (as of #793) `adws/core/targetRepoManager.ts` import specific files under `adws/providers/github/` directly, never the barrel `index.ts`; importing the barrel from any of these would close an import cycle through `githubCodeHost.ts`
- **The ~41 command builders, and the #793 identity/clone-URL/gh-auth modules, are never re-exported through the barrel** — only the provider-interface factory functions (`createGitHubIssueTracker`, `createGitHubCodeHost`, `createGitHubBoardManager`) and `mappers.ts` are. Consumers of a command builder always deep-import `commands/<module>`; consumers of `readLocalRepoInfo`/`resolveBootstrapGitIdentity`/`convertToSshUrl`/`ghAuthToken` always deep-import `githubIdentity`/`cloneUrl`/`ghAuthToken`
- **`ghAuthToken`'s home was a deliberate decision, not an oversight (#793)** — #792 left it unpinned in the core's `bootstrapIdentity.ts` and flagged the question explicitly. It belongs here because: (1) the guard's post-#792 contract is "only the git core may run git; only this adapter may issue gh", and `gh auth token` is a `gh` command; (2) `adws/github/` (the ADW boundary) is unprivileged under `checkGitGhGuard.ts`'s closed `EXEMPT_PACKAGES` — a shell-out there fails `bun run lint:git-guard`; (3) it cannot route through `ghCommandRunner` — it is the pre-context read that *produces* the credential the runner's TokenProvider needs, so routing it through the runner would be circular. It is the adapter's one direct `execSync` alongside the curl-based `appAuth.ts` mint.
- **`parseGitHubRemoteUrl`'s regex contract travels with the #793 move, unchanged** — lazy repo group, end-anchored optional `.git` (`([^/]+?)(?:\.git)?\/?$`); a greedy or dot-excluding group would truncate dotted names like `paysdoc.nl` (#779). `readLocalRepoInfo`'s try/catch still spans both the core's `readOriginRemoteUrl` read and the parse, so the inner `Could not parse GitHub URL: …` stays wrapped in the outer `Failed to get repo info: …`.
- **The core's identity readers supply no forge default** — `readEnvGitIdentity`/`readGitConfigIdentity` (in `adws/gitContext/bootstrapIdentity.ts`) return `null` when nothing is configured; `resolveBootstrapGitIdentity` here is what falls back to `ADW_BOT_FALLBACK_IDENTITY` (`ADW Bot <adw-bot@users.noreply.github.com>`) as the fourth and final step
- **`gitContext.ts` still imports the five command-builder modules from this package (TRANSITIONAL, #792)** — for its surviving semantic methods (`fetchIssue`, `commentOnIssue`, `createPR`, `setSecret`, etc.), pending migration to their callers in future issues #796/#797. This is the one upward dependency the core has on this package, and it is deleted once those methods leave the core
- **`checkGitGhGuard.ts`'s `EXEMPT_PACKAGES` closed set** — exactly two entries: `adws/gitContext` (git core, may run `git`) and `adws/providers/github` (this package, may issue `gh` commands by feeding command strings into the core's executor, never by spawning independently); `isExemptPackage(relPath)` matches the directory itself or any path beneath it

## Configuration

| Type / Field | Description |
|---|---|
| `GitHubAppConfig.appId?` | GitHub App ID; missing means "not configured" |
| `GitHubAppConfig.appSlug?` | GitHub App slug |
| `GitHubAppConfig.privateKeyPath?` | Path to the App's PEM private key |
| `AppAuthDeps.apiBaseUrl?` | Overrides the GitHub API origin; defaults to `GITHUB_API_BASE_URL` (`https://api.github.com`) |
| `AppAuthDeps.runCurl?` | Overrides the curl runner; production uses `execFileSync` |
| `GitHubTokenProviderInput.pat?` | Candidate in the resolution order, after the App mint |
| `GitHubTokenProviderInput.alternateIdentityPat?` | Credential served to `'alternateIdentity'` requests; absent/whitespace-only falls back to the resolved token |
| `GitHubTokenProviderInput.isAppConfigured` / `mintInstallationToken` / `ghAuthToken` | Injected seams mirroring `ResolveContextTokenInput` |
| `ResolveContextTokenInput` (`tokenResolver.ts`) | `owner`, `repo`, `pat?`, `isAppConfigured`, `mintInstallationToken`, `ghAuthToken` |
| `GhCommandRunner.run(command, opts?)` | `opts.input?` for stdin, `opts.purpose?: CredentialPurpose` (`'default' | 'alternateIdentity'`, default `'default'`) |

The one process.env read site: `adws/github/githubAppAuth.ts`'s `readAppConfig()` reads `GITHUB_APP_ID`/`GITHUB_APP_SLUG`/`GITHUB_APP_PRIVATE_KEY_PATH` fresh on every call.

## Gotchas

- **Never import the package barrel (`adws/providers/github/index.ts`) from `gitContextFactory.ts`, `launchGitContext.ts`, or `githubAppAuth.ts`** — always deep-import the specific module (`.../appAuth`, `.../tokenResolver`, `.../githubTokenProvider`, `.../ghCommandRunner`). The barrel pulls in `githubCodeHost.ts`, and importing it from a bootstrap-adjacent module closes an import cycle
- **The command builders are not on the barrel** — `import { fetchIssueCmd } from 'adws/providers/github'` does not work; deep-import `adws/providers/github/commands/issueCommands` instead
- **`appAuth.ts` takes `GitHubAppConfig` as an explicit parameter, not an ambient read** — a caller that forgets to pass it (or passes an empty object) gets `isGitHubAppConfigured` returning `false` / `getInstallationToken` throwing a named "not configured" error, never a `TypeError` from `fs.readFileSync(undefined)`
- **`readAppConfig()` in `adws/github/githubAppAuth.ts` reads env fresh per call, not once at module load** — this matters for tests/spawned processes (feature-780's steps, feature-776's spawned webhook server) that export `GITHUB_APP_ID`/etc. after the module has already been imported
- **`ghCommandRunner.ts` cannot spawn a process on its own** — it is a thin adapter over an injected `GitContext`; there is no fallback path to `child_process` if the injected context is missing or misconfigured, by design
- **`ghCommandRunner`'s cwd class is always `frameworkRoot`, never overridable** — mirroring `#runRepoApi`, there is no `cwd` option on `GhCommandRunner.run`; a command that needs the actual git working tree (branch/commit/worktree operations) does not belong on this seam — it stays a `GitContext` method routed through `#run`
- **`githubBoardManager.ts`'s `gh` accessor constructs a fresh `GhCommandRunner` on every property access** (`private get gh(): GhCommandRunner`) — it is not cached on the instance, so each call re-resolves `gitContextForRepo(this.repoInfo)`
- **Board writes silently degrade to the resolved token, not an error, when no PAT is configured** — `createGitHubTokenProvider`'s `'alternateIdentity'` branch only short-circuits to `alternateIdentityPat` when it is non-blank; an unset `GITHUB_PAT` is not a construction-time or call-time error, it just means board/approve ops run under whichever token `'default'` would have resolved to (App mint or `gh auth token`)
- **`resolveContextToken` is byte-identical to its pre-#792 gitContext-package form** — the move to this package changed nothing about its resolution order or its refusal to read `process.env.GH_TOKEN`; only its file location and import path changed
- **The five command-builder modules living here are what `adws/gitContext/gitContext.ts` imports TRANSITIONALLY** — do not delete or rename `issueCommands.ts`/`prCommands.ts`/`labelCommands.ts`/`boardCommands.ts`/`secretCommands.ts` (or their exported function names) without also updating the core's import block; the migration that removes this dependency is future work (#796/#797), not yet done
