## Feature Description

This is the eighth and last de-tangling slice of the GitContext library extraction (`specs/prd/gitcontext-library-extraction.md`, Implementation Decisions → *Assembly function contract* and the de-tangling wave's fourth bullet; Testing Decisions → *Assembly function — the critical suite*; user stories 4, 5, 6, 24). #816 landed the extraction-readiness guard; #817 moved the domain model into the provider package; #818 gave the GitLab and Jira adapters injected configuration and the `Logger` port; #819 cut the GitHub adapter off the legacy layer and put everything under `adws/providers/**` except `repoContext.ts` into the guard's scope; #820/#821 walked every caller onto the launch boundary and deleted the legacy `adws/github/*` free-function layer; #822 retired every transitional construction site. What is left is exactly what this issue names:

- `adws/providers/repoContext.ts` — the last file in either extractable directory the guard cannot see. It still imports `../github/gitContextFactory`, `../core/environment`, `../core/logger`, `../core/adwLabels`, `../core/githubAppAuth`, `../core/projectConfig`, `../forge/hitlBoardNotifier` and re-exports `../core/providerConfig` — ADW wiring parked inside the library-to-be.
- `adws/github/gitContextFactory.ts` — the last file that *defines* a boundary-free `GitContext` factory (`gitContextFor`/`gitContextForSync`/`gitContextForRepo`), kept alive only by `repoContext.ts`'s `validateGitRemote` (which builds a second, differently-credentialed context just to run `git remote get-url`) and `healthCheck.tsx`'s `readLocalRepoInfo` re-export. `adws/github/githubAppAuth.ts` is a five-line re-export shim with no production importer.
- `mintBoundProviders` / `createRepoContext` — the two construction entry points the guard's permanent allowlist sanctions in `repoContext.ts`.

After this slice:

1. **`forgeProviders(options)` lives in `adws/providers/forgeProviders.ts`** and is the library's one public way to build a bound provider set. Input: a per-port forge selection (`{ codeHost: 'github' | 'gitlab', issueTracker: 'github' | 'jira' }` — closed unions, one per port), one `identity: RepoIdentifier`, the consumer's `tokenProvider`, the executor `gitContext` the consumer already constructed, and an optional `deps` bag (logger, GitHub seams, GitLab/Jira configuration). Output: a frozen `BoundProviders` whose every member is bound to `identity`. It refuses — before constructing anything — an identity that fails `validateRepoIdentifier`, a `gitContext` bound to another repository (naming both), a `tokenProvider` that does not implement the port, and an unknown or wrong-port forge name (`UnknownForgeError`, naming the value and the port). The board manager is present only for a GitHub code host and omitted (never a refusing stub) otherwise; the unknown-forge rejection is never swallowed by that omission.
2. **`buildLaunchBoundary` is its only caller.** The boundary keeps constructing its `GitContext` directly, parses `.adw/providers.md` through `adws/core/providerConfig.ts` (which now yields forge names, not `Platform`), builds ADW's wiring with `adws/core/forgeWiring.ts` (the `.env`-to-config reads from #818, the HITL Slack `onStatusMoved` hook, the `adw:*` label catalogue, the PR-approval capability predicate, and — new — the Jira config assembled from `## Issue Tracker URL` / `## Issue Tracker Project Key` plus `jiraAuthFromEnv()`), and calls `forgeProviders` lazily on first `.providers` access exactly as it minted before.
3. **Workspace binding moves to `adws/core/workspaceBinding.ts`**: `bindWorkspaceContext(boundary, cwd, repoId?)` validates the identifier, the directory and the `origin` remote — reading the remote through `boundary.gitContext.remoteUrl(cwd)`, the context the caller already holds — and freezes `{ ...boundary.providers, cwd, repoId }`. `createRepoContext` (the constructor path) and `validateGitRemote`'s private context construction are gone.
4. **`adws/providers/repoContext.ts`, `adws/github/gitContextFactory.ts` and `adws/github/githubAppAuth.ts` are deleted** (`adws/github/` ceases to exist).
5. **The guard follows.** `EXTRACTION_SCOPE` gains the whole `adws/providers` directory (`since: '#823'`) so scope == extractable set; the construction rule's allowlist is two permanent entries (`adws/core/launchGitContext.ts`, `adws/providers/forgeProviders.ts`) and zero sunset entries; `forgeProviders` joins the guarded constructor name sets while the retired names stay as reintroduction guards; the cwd-derived-identity rule additionally inspects `forgeProviders({ identity: … })`.

The BDD contract already exists: `features/per-issue/feature-823.feature` (`@adw-823`, 811 lines, eight sections) was written by the scenario phase and this plan is aligned to it — including its seven findings (mixed identity is an input, the board-manager swallow, `validateGitRemote`'s second context, the two `process.env` seams that must stay, the permanent allowlist half the ratchet cannot see, the five suites that break at import time, and the `mintProviders` seam four BDD files drive the boundary through).

## User Story
As a library consumer (Pi_Dev_Workflow, and ADW itself at the switchover)
I want a single assembly function that takes a forge selection, a repository identity, a token provider and the executor and returns a fully bound provider set — refusing unknown forge names and mixed identities by name — with ADW's launch boundary as its only caller
So that provider construction and identity binding are written once in the library, the wrong-repo firewall becomes the library's guarantee rather than a per-consumer convention, and both extractable packages can be moved into `@paysdoc/gitcontext` as a pure file move.

## Problem Statement
`repoContext.ts` is framework wiring living inside the extractable provider package: it reads the environment, the ADW logger, the label catalogue and the Slack notifier, and it constructs a second `GitContext` (via `gitContextForRepo`) just to read a workspace's remote. Because of it the extraction-readiness guard cannot cover `adws/providers/**` in full, `adws/github/gitContextFactory.ts` cannot be deleted, the construction rule keeps a permanent allowlist entry for a file that will not exist in the library, and `mintBoundProviders` — the function every consumer would have to reimplement — never checks that the context it is handed agrees with the identity it binds. Extraction is not yet a file move.

## Solution Statement
Build the assembly function inside the provider package with only executor, ports and adapter imports; move every ADW-only concern `repoContext.ts` still carries into two new `adws/core/` modules (`forgeWiring.ts` for the env→config and GitHub-seam wiring, `workspaceBinding.ts` for workspace validation over the caller's own context); rewire `buildLaunchBoundary` to parse forge names and call `forgeProviders` through an injectable seam; delete the three retired files; widen the guard scope to the whole provider package and shrink the construction allowlist to the two permanent sites; repoint every test and step definition that imported the retired modules; and refresh the living docs, the conditional-docs registry and the README so nothing points at `adws/github/` or `repoContext.ts`.

## Implementation Plan

### Phase 1: Foundation
Create the assembly module inside the provider package with its per-port closed unions, its named refusals and its deps bag, and prove it with the critical suite over a real `GitContext` and a spy executor. Create the two `adws/core/` homes for the wiring `repoContext.ts` still carries (`forgeWiring.ts`) and for workspace binding over the caller's own context (`workspaceBinding.ts`), moving the existing tests with the code. Change `providerConfig.ts` to yield forge names.

### Phase 2: Core Implementation
Rewire `buildLaunchBoundary` onto `forgeProviders` through the renamed seam, delete `repoContext.ts`, `gitContextFactory.ts` and the App-auth shim, repoint `healthCheck.tsx`, and update the launch-boundary and workflow-init suites.
