## Feature Description

Issue #819 is the fourth de-tangling slice of the GitContext library extraction (`specs/prd/gitcontext-library-extraction.md`: Solution → de-tangling wave, second bullet; Implementation Decisions → De-tangling wave; Testing Decisions → *GitHub adapter absorption*; user stories 8 and 10). It lands on the extraction-readiness guard #816 built and #817/#818 widened. After it, the whole GitHub forge adapter (`adws/providers/github/**`) — not just its `domain/` and `mappers.ts` — imports nothing outside the extractable set, and the guard holds that result.

Today exactly nine import lines in three files are the entire entanglement. Every one of them reaches *upward* from the adapter into the framework that is supposed to sit on top of it:

| File | Framework imports today |
|---|---|
| `adws/providers/github/githubIssueTracker.ts:9-25` | `../../github/issueApi` (12 free functions), `../../github/issueListApi`, `../../github/labelManager`, `../../github/projectBoardApi` |
| `adws/providers/github/githubCodeHost.ts:6-17` | `../../core` (`log`), `../../github/prApi` (8 free functions), `../../github/gitContextFactory` (`gitContextForSync`, `gitContextForRepo`) |
| `adws/providers/github/githubBoardManager.ts:7,10` | `../../core` (`log`), `../../github/gitContextFactory` (`gitContextForRepo`) |

Those legacy free functions are thin: each mints a *fresh* `GitContext` via `gitContextForRepo(repoInfo)`, hands it to `createGhRepoApi(...)` (already adapter-owned since #797), runs one `gh` command, parses the JSON, applies an error/log policy, and returns an adapter-owned domain shape (owned since #817). The adapter then maps that shape to a port type. So "absorbing" them means: the port classes call `createGhRepoApi(ctx)` / `createGhCommandRunner(ctx)` themselves over a context **the caller hands in**, the JSON parsing moves into two new pure adapter modules, and every error policy and log line moves into the port methods — delivered through the `Logger` port instead of `adws/core`'s `log`.

Concretely, after this slice:

- **Factory shape.** `createGitHubIssueTracker(ctx, repoId, deps?)`, `createGitHubCodeHost(ctx, repoId, deps?)` and `createGitHubBoardManager(ctx, repoId, deps?)` take the `GitContext` the caller already holds as their first argument. The adapter constructs no context, resolves no token, and reads no environment: it selects no identity of its own. A context bound to a different `owner/repo` than `repoId` is refused at construction (a mixed-identity provider is the one thing the PRD's assembly function exists to make impossible).
- **`mintBoundProviders` threads the boundary context.** `MintProvidersOptions` gains a required `gitContext`; `buildLaunchBoundary` passes the very `GitContext` it just built, so every provider in the triple runs its `gh` commands over the launch identity — one construction per process instead of one per adapter call.
- **Logger port.** All three port classes log through `Logger` (`adws/gitContext/types.ts`, default `consoleLogger`), injected by ADW's wiring as `log`. Every legacy log line — text *and* level — is reproduced, so production output is byte-identical.
- **Two ADW behaviours that were lodged inside the legacy layer are re-homed as injected seams.** (1) The HITL Slack notification `projectBoardApi.moveIssueToStatus` fired on a move to *Review* becomes an optional `onStatusMoved` hook on the tracker, wired by ADW to `notifyReviewTransition`. (2) The `adw:*` label catalogue `labelManager.applyLabel` used to lazy-create a missing label becomes an optional `resolveLabelDefinition` hook, wired by ADW to the catalogue. The library never learns about Slack or about ADW's label colours.
- **Alternate-identity parity.** The legacy functions ran over `gitContextForRepo`'s token provider, which serves `GITHUB_PAT` to `'alternateIdentity'` requests (PR approval — GitHub forbids bot self-approval — and every Projects V2 write). The launch boundary's provider does not serve one today. `createLaunchTokenProvider` gains `alternateIdentityPat: GITHUB_PAT` so the migrated operations keep their credential; `'default'` requests are untouched.
- **Guard scope widens** by `adws/providers/github` (the whole directory), `adws/providers/workspaceValidation.ts` and `adws/providers/index.ts` — everything under `adws/providers/**` except `repoContext.ts`, which stays ADW wiring until #823 replaces it with `forgeProviders()`.
- **The legacy layer is not touched.** `adws/github/issueApi.ts`, `prApi.ts`, `labelManager.ts`, `projectBoardApi.ts`, `issueListApi.ts`, `gitContextFactory.ts`, `githubAppAuth.ts` and their ~60 framework callers stay exactly as they are (#820/#821 migrate and delete them). Their parsing bodies are therefore duplicated in the adapter for the lifetime of two issues — a deliberate, bounded transition, called out in Notes.

This is a HITL issue: the constructor shapes and deps seams defined here ship frozen at `@paysdoc/gitcontext` 1.0.0.

## User Story

As a framework developer
I want the GitHub adapter to reach only the executor, the ports, and the domain model — logging through the injected logger port and constructing no identity of its own
So that it carries no dependency on ADW's legacy GitHub API layer (or ADW's logger, or ADW's environment) at extraction time, and the library's first release is a pure file move of an API already proven against ADW's full consumer base

## Problem Statement

The adapter that is supposed to be the *bottom* of the stack depends on the layer *above* it. `githubIssueTracker.ts` delegates every operation to `adws/github/issueApi|issueListApi|labelManager|projectBoardApi`; `githubCodeHost.ts` to `adws/github/prApi` plus `adws/core`'s `log`; `githubBoardManager.ts` mints its own `GitContext` on every `gh` call through `adws/github/gitContextFactory` and logs through `adws/core`. Extracting `adws/providers/github/` in that state publishes a package that does not compile.

Three consequences of the current shape are independently wrong:

1. **The adapter selects identity.** Every port method calls `gitContextForRepo(this.repoId)` (directly or through the legacy function), building a fresh context — with its own token resolution, its own self-host cache probe, its own git identity read — per operation. The launch boundary's one-context-per-process guarantee (`buildLaunchBoundary`) stops at the provider boundary; the providers it mints immediately construct more.
2. **ADW behaviours hide inside the "GitHub API" layer.** `projectBoardApi.moveIssueToStatus` posts to Slack; `labelManager.applyLabel` knows ADW's label colours. Absorbing those functions verbatim would drag `postSlack` and the `adw:*` catalogue into the library; dropping them would change what operators see (a HITL issue moved to Review without its Slack ping; a lazily-created `adw:blocked` label in grey instead of red).
3. **The guard cannot yet hold the adapter.** `EXTRACTION_SCOPE` deliberately excludes the three port files, so any new framework import into the adapter is invisible to CI until this slice widens the scope.

## Solution Statement

Do the absorption **inside the adapter**, under exec-fake tests, so the frozen API is proven against ADW before it ships:

1. **Two pure parser modules absorb the legacy parsing.** `ghIssueParsers.ts` (the `gh issue …` JSON → `GitHubIssue`/`IssueCommentSummary`/label names/created-issue number/list entries) and `ghPrParsers.ts` (the `gh pr …`/`gh api` JSON → `PRDetails`/`PRReviewComment[]`/`PRListItem[]`, plus `selectPreferredPR`, `isApprovedFromReviewsList` and the `reviewDecision` decision) hold the parsing bodies verbatim, typed only against `domain/` and the ports. `mappers.ts` stays the GitHub→port mapping layer it is.
2. **The three port classes bind once and delegate downward.** Each takes `(ctx, repoId, deps)`, binds `createGhRepoApi(ctx)` (tracker, code host) or `createGhCommandRunner(ctx)` (board manager) in its constructor, and reproduces each legacy function's command, parse, error policy and log lines through `this.logger`. Nothing in the adapter constructs a `GitContext`, imports `gitContextFactory`, or reads `process.env`.
3. **Optional deps seams carry the two ADW behaviours out of the library.** `GitHubIssueTrackerDeps = { logger?, onStatusMoved?, resolveLabelDefinition? }`; `GitHubCodeHostDeps`/`GitHubBoardManagerDeps = { logger? }`. ADW's wiring in `repoContext.ts` injects `log`, the Review-transition Slack notifier, and the `adw:*` catalogue, so operator-visible behaviour is unchanged while the adapter itself is forge-only.
4. **The boundary context flows through the mint.** `mintBoundProviders({ repoId, gitContext, … })`; `buildLaunchBoundary` passes its own context; `createRepoContext`'s no-providers path mints via `gitContextForRepo(repoId)` inside the sanctioned `repoContext.ts` (today's identity semantics, unchanged).
5. **Token parity at the boundary.** `createLaunchTokenProvider()` passes `alternateIdentityPat: GITHUB_PAT` — exactly what `gitContextForRepo`'s provider does — so approval and board writes keep the PAT they run with today.
6. **The guard widens and the pinned rows flip.** Three `EXTRACTION_SCOPE` entries are appended (`since: '#819'`); the unit tests and the `@adw-817`/`@adw-818` fixture rows that pin the three port files as *not yet checked* are rewritten to name the last remaining out-of-scope file, `adws/providers/repoContext.ts`.
7. **Line budget.** `repoContext.ts` (295 lines) receives the GitHub deps wiring; to stay under the 300-line cap its `.adw/providers.md` reader (`ProviderConfig`, `parsePlatform`, `loadProviderConfig`, ~75 lines) moves verbatim to `adws/core/providerConfig.ts` — the destination #823 already names for it — and is re-exported so no importer changes.

## Implementation Plan

### Phase 1: Foundation
Land the pure building blocks first, each fully unit-tested before any port class changes: the two parser modules (behaviour lifted verbatim from `issueApi.ts`/`prApi.ts`/`issueListApi.ts`, with the ported legacy test cases proving it), the `contextBinding.ts` identity assertion, and the `adws/core/providerConfig.ts` move that makes room in `repoContext.ts`. Nothing in this phase changes a signature anyone calls.

### Phase 2: Core Implementation
Rewrite the three port classes to `(ctx, repoId, deps)`: bind `createGhRepoApi(ctx)` / `createGhCommandRunner(ctx)` once, delegate every method downward with the legacy error policy and log lines reproduced through `this.logger`, expose the `onStatusMoved` and `resolveLabelDefinition` seams, and refuse a context whose identity differs from `repoId`. Replace the three delegation-mock test files with exec-fake behaviour tests; add the board-manager suite. Export the new types through the barrel.

### Phase 3: Integration
Thread the boundary context through `mintBoundProviders`/`resolve*` and `buildLaunchBoundary`; add ADW's GitHub deps wiring in `repoContext.ts`; give `createLaunchTokenProvider` the alternate-identity PAT; widen `EXTRACTION_SCOPE` with tests in both directions; rewrite the pinned `@adw-817`/`@adw-818` rows and the `@adw-818` driver; update living docs, registry and README; implement the `@adw-819` step definitions; run every validation command.

## Step by Step Tasks
Execute every step in order, top to bottom.

### 1. Issue payload parsers (`adws/providers/github/ghIssueParsers.ts`)
- Header docblock: pure parsers for the `gh issue …` JSON the tracker receives from `GhIssueApi`; the canonical home of parsing that `adws/github/issueApi.ts`/`issueListApi.ts` still carry a copy of until #821 deletes them. Imports: `type { GitHubIssue, IssueCommentSummary } from './domain/issue'`, `type { IssueListEntry, IssueSummary } from '../types'`. Nothing else.
- Move the module-private raw wire shapes from `issueApi.ts` verbatim (`RawGitHubUser`, `RawGitHubLabel`, `RawGitHubMilestone`, `RawGitHubComment`, `RawGitHubIssue`); keep them module-private.
- `parseGitHubIssue(json: string): GitHubIssue` — `JSON.parse` then `transformIssueResponse` (body verbatim from `issueApi.ts:60-105`, including every `|| 'unknown'`, `|| ''`, `|| null`, `|| false` default).
- `parseIssueState(json: string): string` — `JSON.parse(json).state`.
- `parseIssueCommentsRest(json: string): IssueCommentSummary[]` — verbatim from `fetchIssueCommentsRest` (`id`, `body || ''`, `user.login || 'unknown'`, `created_at`).
- `parseIssueLabelNames(json: string): string[]` — `(result.labels || []).map(l => l.name)`.
- `parseCreatedIssueNumber(output: string): number` — `output.trim().match(/\/issues\/(\d+)$/)`; throws `createIssue: could not parse issue number from gh output: "${output.trim()}"` (message verbatim).
- `parseFirstIssueNumber(json: string): number | null` — `results.length > 0 ? results[0].number : null`.
- `parseIssueSummaries(json: string): IssueSummary[]` and `parseIssueListEntries(json: string): IssueListEntry[]` — typed `JSON.parse` pass-throughs (the legacy functions do no more).
- Every function is pure and throws on malformed JSON; the error policy (swallow / wrap / rethrow) lives in the port methods, not here.

### 2. Pull-request payload parsers (`adws/providers/github/ghPrParsers.ts`)
- Imports: `type { PRDetails, PRReviewComment, PRListItem, RawPR } from './domain/pullRequest'`. Nothing else.
- Move the module-private raw shapes from `prApi.ts` verbatim (`RawPRDetails`, `RawPRReview`, `RawPRLineComment`, `RawPRListItem`, `RawPRListEntry extends RawPR { updatedAt }`); export `RawPRListEntry` (the code host and tests name it).
- `issueNumberFromBranch(branchName: string | null | undefined): number | null` — the four-line body of `adws/triggers/webhookHandlers.ts:27-31` (`/issue-(\d+)/`), copied because the adapter cannot import triggers; document the copy in its JSDoc.
- `parsePRDetails(json: string): PRDetails` — verbatim from `fetchPRDetails`: `Implements #(\d+)` in the body first, then `issueNumberFromBranch(raw.headRefName)`; `body || ''`; `reviewComments: []`.
- `parsePRReviews(json: string): PRReviewComment[]` — verbatim filter (`state !== 'PENDING'` and (non-blank body or `CHANGES_REQUESTED`)), verbatim mapping including the `[Review submitted: ${state}]` placeholder, `isBot: user?.type === 'Bot'`, `path: ''`, `line: null`, both timestamps `submitted_at`.
- `parsePRLineComments(json: string): PRReviewComment[]` — verbatim (`line: c.line || c.original_line || null`, `path: c.path || ''`).

## Notes
- If `.adw/coding_guidelines.md` exists in the target repository (or `guidelines/coding_guidelines.md` as a fallback), strictly adhere to those coding guidelines. If necessary, refactor existing code to meet the coding guidelines as part of implementing the feature.
- **No new library is needed.** The `typescript` compiler API, vitest and Node builtins cover everything. (If one were needed, `.adw/commands.md` says `bun add <package>`.)
- **Why the parsing is duplicated rather than re-pointed.** The issue is explicit that the legacy layer and its ~60 callers are not touched here. Re-pointing `issueApi.ts`/`prApi.ts` at the adapter's parsers would be behaviour-free but would edit the very files #821 deletes; copying the bodies keeps this HITL diff confined to the API being reviewed. The duplication is bounded (two issues) and both copies are frozen — the legacy tests keep proving the legacy copy, the ported tests prove the adapter's. The adapter's copy is the canonical one; #821 deletes the other.
- **Why `onStatusMoved` is a hook, not a decorator.** The alternative — ADW wrapping the tracker after minting — needs a `Proxy` or a 17-method delegating class because `GitHubIssueTracker` is a class (spreading it drops prototype methods). An optional post-move callback is three lines in the adapter, three in wiring, matches the deps-bag idiom #818 established, and is a legitimate generic extension point for any library consumer. #823's `forgeProviders()` will thread the ADW deps the same way it threads the logger. If the HITL reviewer prefers the decorator, only `repoContext.ts` changes.
- **Why `resolveLabelDefinition` exists.** `IssueTracker.applyLabel` is documented as "lazy-creating [the label] first if missing"; today that lazy-create uses ADW's `adw:*` colours. Without the seam a lazily-created `adw:blocked` would turn grey — an operator-visible change on a rare path. The fallback definition `{ ededed, 'ADW label' }` is reproduced in wiring from the two exported catalogue constants because `labelManager.resolveLabelDefinition` is private and that file is not edited.
- **Why `createLaunchTokenProvider` gains the alternate PAT — read this before reviewing.** Its current docblock says adding one "would be a behaviour change, not a refactor". That was true while the boundary context only ran git and default-purpose repo reads. This slice makes the boundary context the one the adapter's `'alternateIdentity'` operations run over (PR approval, Projects V2 board moves/creates/field updates), which today run over `gitContextForRepo`'s provider *with* `GITHUB_PAT`. Not adding it would make the App token approve its own PRs (rejected by GitHub) and drive board writes with the wrong identity — the opposite of "operator-visible behaviour unchanged". Only `purpose === 'alternateIdentity'` is affected; `healthCheckChecks.ts` and every git command keep resolving exactly as before.
- **Why the identity cross-check.** `createGitHubIssueTracker(ctx, repoId)` has two identity-bearing arguments; the PRD's assembly-function suite (#823) demands that no construction path yields a mixed-identity set. A three-line, case-insensitive refusal at each factory makes that structural instead of conventional. Nothing in production can trip it (the boundary derives both from one `{owner, repo}`; `createRepoContext` mints from `repoId`).
- **Why `loadProviderConfig` moves now.** `repoContext.ts` is at 295 lines and the wiring adds ~30; the 300-line cap is hard. The `.adw/providers.md` reader is ADW's own config parser — the PRD says the library never reads consumer config files — so `adws/core/providerConfig.ts` is where #823 was going to put it anyway.
