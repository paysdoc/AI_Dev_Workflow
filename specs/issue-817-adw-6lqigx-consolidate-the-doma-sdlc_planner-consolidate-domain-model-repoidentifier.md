## Feature Description

This is the second de-tangling slice of the GitContext library extraction (`specs/prd/gitcontext-library-extraction.md`, Solution → de-tangling wave, first bullet; user story 7). It moves the domain model that the provider package still borrows from the rest of ADW *into* the provider package, so that the extractable set (`adws/gitContext/` + `adws/providers/`) is typed only against types it owns.

Two groups move:

1. **The eleven raw GitHub payload shapes** — `GitHubUser`, `GitHubLabel`, `GitHubMilestone`, `GitHubComment`, `GitHubIssueListItem`, `GitHubIssue`, `IssueCommentSummary` (today in `adws/types/issueTypes.ts`), `PRReviewComment`, `PRDetails`, `PRListItem` (today in `adws/types/workflowTypes.ts`) and `RawPR` (today in `adws/github/prApi.ts`) — become two adapter-owned, import-free modules under `adws/providers/github/domain/`. Every framework consumer (agents, core, phases, triggers, proof, the legacy `adws/github/*` API layer, orchestrators, tests and BDD step definitions) imports them from there. The barrels that re-exported them (`adws/core/index.ts`, `adws/index.ts`, `adws/github/index.ts`) stop doing so, so each shape has exactly one home.
2. **`RepoInfo` (`{ owner, repo }`)** collapses into the provider package's `RepoIdentifier` (`{ owner, repo, platform }`). Both declarations of `RepoInfo` — the framework one in `adws/github/githubApi.ts` and the adapter-local twin in `adws/providers/github/githubIdentity.ts` — are deleted. Every parameter, field and fixture typed `RepoInfo` becomes `RepoIdentifier`; every `{ owner, repo }` literal that fed one gains `platform: Platform.GitHub`; the two GitHub-only remote-URL parsers (`parseGitHubRemoteUrl`, `readLocalRepoInfo`) and their framework wrappers (`getRepoInfo`, `getRepoInfoFromUrl`, `getRepoInfoFromPayload`) return a full `RepoIdentifier`; the `toRepoInfo` mapper (an identity function after the collapse) is deleted. No alias, `Pick`, or re-export of the old shape survives.

Finally the extraction-readiness guard (#816) widens by exactly what this slice cleaned: `adws/providers/github/mappers.ts` and the new `adws/providers/github/domain/` directory are appended to `EXTRACTION_SCOPE`, turning "mappers and the domain model import nothing from the framework" into a CI-enforced invariant.

This is a mechanical rename with **no behaviour change**: no `gh` command string, log line, error message, or control flow changes. The compiler and the existing unit/BDD suites are the regression net.

## User Story

As a framework developer
I want the forge-neutral domain model (raw GitHub payload shapes and the repository identifier) owned by the provider package
So that the library's interfaces and adapters are typed only against types the library owns, and extraction remains a pure file move

## Problem Statement

`adws/providers/github/mappers.ts` — the pure GitHub→port mapping layer that will ship inside `@paysdoc/gitcontext` — imports its input types from four framework modules: `../../types/issueTypes`, `../../types/workflowTypes`, `../../github/githubApi` and `../../github/prApi`. The GitHub adapter classes (`githubIssueTracker.ts`, `githubCodeHost.ts`, `githubBoardManager.ts`) each carry a private `repoInfo: RepoInfo` field derived from their bound `RepoIdentifier` through `toRepoInfo`, purely so they can call legacy `adws/github/*` functions that take the framework's `{ owner, repo }` shape. And the adapter's own `githubIdentity.ts` declares a second, structurally identical `RepoInfo` for its parsers.

The result is two repo-identity shapes for one concept, ~70 framework files typed against `RepoInfo` (including 15 vitest suites and 15 BDD step-definition files), and a provider package whose extraction would fail to compile because its mappers reach into `adws/types/` and `adws/github/`. The #816 guard cannot enforce cleanliness for `mappers.ts` until it is clean, and the PRD's next slices (GitHub-adapter absorption, injected GitLab/Jira config, the assembly function) all assume the domain model is already where the library expects it.

## Solution Statement

- **Relocate, don't redesign.** Create `adws/providers/github/domain/issue.ts` and `adws/providers/github/domain/pullRequest.ts` holding the eleven shapes verbatim (fields, optionality and doc comments unchanged). The only import in the directory is `pullRequest.ts` → `./issue` (for `GitHubUser`). Delete the originals from `adws/types/issueTypes.ts`, `adws/types/workflowTypes.ts` and `adws/github/prApi.ts`, drop the barrel re-exports, and switch every consumer to a deep `import type` from the domain module (deep imports, never the `adws/providers/github` barrel — the living doc's cycle rule).
- **Collapse `RepoInfo` into `RepoIdentifier`.** Delete both `RepoInfo` interfaces. Retype every consumer to `RepoIdentifier` (from `adws/providers/types`), keeping parameter and property *names* (`repoInfo`, `cronRepoInfo`, `webhookRepoInfo`, …) and function *names* (`getRepoInfo`, `readLocalRepoInfo`, `getRepoInfoFromPayload`, `resolveEntryRepoInfo`) unchanged — the guard's `cwd-derived-identity` rule, its rename-detection test and `ensureCronOnEveryEventSteps.ts` pin those names. Where a `RepoIdentifier` is already in hand (`repoId`, `boundary.repoId`, `repoContext.repoId`) pass it through instead of re-wrapping; where a literal is built from a `TargetRepoInfo` or a webhook payload, add `platform: Platform.GitHub`. The GitHub-only parsers return `RepoIdentifier` with `platform: Platform.GitHub` — truthful, since they match only `github.com` remotes.
- **Widen the guard by exactly the cleaned surface.** Append `adws/providers/github/mappers.ts` and `adws/providers/github/domain` to `EXTRACTION_SCOPE` (`since: '#817'`), extend the guard's rule-level and scan-level tests in both directions, and keep the "out-of-scope providers file passes today" test (it still names `githubCodeHost.ts`, which this slice does not widen).
- **Regression net.** `bunx tsc --noEmit` (root, includes `features/`) enumerates every remaining call site; the updated unit and BDD suites prove nothing else changed. The only assertion edits are the handful of whole-object equality checks on a parsed identity, which gain the `platform` key (see Notes).

## Notes
- If `.adw/coding_guidelines.md` exists in the target repository (or `guidelines/coding_guidelines.md` as a fallback), strictly adhere to those coding guidelines. If necessary, refactor existing code to meet the coding guidelines as part of implementing the feature.
- **No new library is needed** (`.adw/commands.md`: `bun add <package>` if one were).
- **The one class of assertion edits beyond import paths.** Collapsing `{ owner, repo }` into `RepoIdentifier` makes the GitHub-only parsers return a `platform` key. Whole-object `toEqual`/`deepStrictEqual` checks on a *parsed* identity (`githubIdentity.test.ts` ×8, `cronRepoResolver.test.ts` ×2, `webhookRepoResolver.test.ts` ×1, `feature-779.steps.ts` ×2) therefore gain `platform: Platform.GitHub`; the asserted owner/repo values are unchanged. This is the mechanical consequence of the collapse the issue mandates, not a behaviour change — nothing at runtime reads `platform` on these paths. Every other test edit is an import path, a fixture type annotation, or a fixture literal.
- **Why the parsers stamp `Platform.GitHub` rather than returning a narrower shape.** The issue requires every consumer to take `RepoIdentifier` and forbids any surviving alias. Returning `Pick<RepoIdentifier, 'owner' | 'repo'>` from `readLocalRepoInfo`/`getRepoInfo` would not be assignable to those consumers and would just be `RepoInfo` under another name. `parseGitHubRemoteUrl` matches only `github.com` remotes, so the platform is known, not guessed. `buildLaunchBoundary` keeps its own `deps.platform ?? Platform.GitHub` authority and ignores the seam's value, so the injected-`Platform.GitLab` test still holds.
- **Names stay, only the type goes.** `getRepoInfo`, `readLocalRepoInfo`, `getRepoInfoFromPayload`, `getRepoInfoFromUrl`, `resolveEntryRepoInfo`, the `repoInfo` parameter/property names, and the `cronRepoInfo`/`webhookRepoInfo` variables are all pinned by something outside this issue (`CWD_DERIVED_IDENTITY_FNS` in `adws/guard/identityRule.ts`, the rename-detection table in `checkGitGhGuard.test.ts`, the source-text assertions in `ensureCronOnEveryEventSteps.ts`, and dozens of dep-object literals in step definitions). Renaming them would balloon the diff and is not required by any acceptance criterion; `grep -w RepoInfo` distinguishes the type from those identifiers.
- **Deep imports, no domain barrel.** `app_docs/feature-9gjajh-providers.md` documents that bootstrap-adjacent framework modules must deep-import adapter files because importing the `adws/providers/github` barrel closes a cycle through `githubCodeHost.ts` → `adws/core`. Type-only imports would not trip that at runtime, but one convention is simpler than two, and `adws/providers/github/index.ts` is left exactly as it is.
- **`fetchPRReviews` signature.** It is exported (via `githubApi.ts`, `adws/github/index.ts`, `adws/index.ts`) but its only caller is `fetchPRReviewComments` in the same file; changing it to `(prNumber, repoId)` removes the last `gh({ owner, repo })`-shaped call without touching any behaviour. If a reviewer prefers zero exported-signature changes, the alternative is `gh({ owner, repo, platform: Platform.GitHub })` inside the function — either satisfies the acceptance criteria.
- **What stays out of guard scope, deliberately.** `githubCodeHost.ts`, `githubIssueTracker.ts`, `githubBoardManager.ts` still delegate to `adws/github/*` functions and log via `adws/core`; `repoContext.ts` still reads `ProvidersConfig` from `adws/core/projectConfig` and constructs contexts via `adws/github/gitContextFactory`; `gitlab/*` and `jira/*` read `adws/core` config. Those are the PRD's remaining de-tangling slices (GitHub-adapter absorption, injected GitLab/Jira config, the assembly function). This issue widens the scope by exactly what it cleaned and nothing more; `githubIdentity.ts` and the other leaf adapter files are already clean and will be swept in when the whole `adws/providers/github` directory is appended by the absorption slice.
- **Order of work vs. a green compiler.** `tsc` is red from step 2 until the end of step 5 (and step 8 for `features/`); that is expected for a rename of this breadth. Use the error list as the checklist rather than hand-hunting call sites; the greps in Validation Commands are the final sweep for comments and docblocks the compiler cannot see.
