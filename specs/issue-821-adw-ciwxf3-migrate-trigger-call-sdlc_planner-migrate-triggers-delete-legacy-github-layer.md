`cronRepoResolver.ts`, `mergeDispatchGate.ts`, `spawnGate.ts` and `scanAuthQueue.ts` import nothing from `adws/github`; `scanAuthQueue.ts` changes only because `evaluateCandidate`'s input now carries the boundary.

Outside the triggers, seven files still import a surviving module by its `adws/github/` path and move with it: `adws/adwMerge.tsx`, `adws/phases/prReviewCompletion.ts` and `workflowCompletion.ts` (the HITL notifier), `adws/phases/phaseCommentHelpers.ts`, `sdlcReviewHandoff.ts`, `workflowInit.ts`, `prReviewPhase.ts` (comment formatters and their types), `adws/providers/repoContext.ts` (the notifier again), `adws/index.ts` (the public barrel), and `adws/adwPrReview.tsx` / `adws/phases/autoMergePhase.ts` (call shapes of `resolvePrReviewSpawn` and `mergeWithConflictResolution`). Nineteen BDD step-definition files import a surviving module or call a trigger entry point whose shape changes (listed in Relevant Files).

Three things make this more than an import swap:

1. **The triggers need one thing the ports cannot express.** `fetchLinkedPRs` (cron's label-recovery gate and the concurrency guard) and the HITL notifier's PR lookup both read *every* PR of the repository — open, closed and merged — via `gh pr list --state all --json number,body,state,mergedAt --limit 200`. `CodeHost` offers only `listOpenPullRequests()` and `listMergedPullRequests(limit)`. One forge-neutral widening, `CodeHost.listPullRequests(): readonly PullRequestRecord[]`, implemented in the GitHub adapter from the command it already issues (`fetchAllPRs`) and refused by name on GitLab exactly as #796/#820 did, closes the gap. Nothing else the triggers do is missing from the ports.
2. **Relocated modules must construct nothing.** The construction guard's transitional allowlist may only shrink ("NOTHING MAY EVER BE ADDED"), so `hitlBoardNotifier.ts`, `linkedPrDetector.ts` and `prCommentDetector.ts` cannot carry their `createGhRepoApi(gitContextForRepo(repoInfo))` defaults into `adws/forge/`. Each becomes a helper over an injected port or over a `GitContext` the caller already holds (`createGhRepoApi(ctx)` is a bound view, not a constructor — the `adws/core/issueRecord.ts` precedent). The notifier's default readers therefore move out of the module and its `NotifierDeps` become required; `repoContext.ts`'s existing `buildNotifierDeps(ctx, repoId)` is the one production builder and moves to the forge module.
3. **The webhook gets a real per-event boundary.** `trigger_webhook.ts` builds `buildLaunchGitContext(resolution.targetRepo)` today and threads only the `GitContext`; every forge read on the event path still went through a free function that minted its own context from `repoInfo`. It now builds `buildLaunchBoundary(resolution.targetRepo)` per event and threads the `LaunchBoundary` — the only sanctioned construction site — so the handlers' identity, `GitContext` and providers are one object. The two `webhookRepoInfo ?? getRepoInfo()` fallbacks on the `issue_comment` path (a payload without a `repository` object, which GitHub never sends) are preserved by a lazily built, memoised self-host boundary (`buildLaunchBoundary(null)` — the same local-remote identity `getRepoInfo()` resolved to).

The pure ADW label policy already lives in `adws/core/adwLabels.ts` (#820); `labelManager.ts` is today a re-export shim plus three gh-issuing functions with no production caller except `webhookGatekeeper.applyLabel` (covered by `IssueTracker.applyLabel`). Its `ensureAdwLabelsExist` catalogue loop is the one piece of ADW label *provisioning* policy worth keeping; it relocates to `adws/forge/adwLabelProvisioning.ts` over `Pick<IssueTracker, 'ensureLabel'>`. The GitHub-App env wrapper already lives in `adws/core/githubAppAuth.ts` (#820); the `adws/github/githubAppAuth.ts` shim stays (with `gitContextFactory.ts`) until #823.

## User Story

As an ADW trigger process (the cron backlog sweeper, the webhook server and the handlers, sweeps and redrive passes they run)
I want every issue, PR, label and comment operation I perform to go through the provider triple of the launch boundary I hold — one per cron process, one per webhook event
So that no trigger can address a repository other than the one its boundary names, the legacy `adws/github/` layer can be deleted outright, and the only forge code ADW runs is the code that will be extracted into `@paysdoc/gitcontext`

## Problem Statement

Every legacy free function opens with `createGhRepoApi(gitContextForRepo(repoInfo))`: a fresh, caller-assembled identity per call. The triggers are the last callers, and they are the processes with the most repositories in flight — the webhook serves every registered repo from one process, and the cron passes a bare `cronRepoInfo` into a dozen helpers. Two of those helpers (`webhookGatekeeper.classifyAndSpawnWorkflow`, `trigger_webhook`'s comment path) still fall back to `getRepoInfo()`, a read of the process cwd's git remote, when no `repoInfo` arrives — precisely the wrong-repo class the PRD exists to kill.

The launch boundary (#794) already hands the cron a `LaunchBoundary` (`cronBoundary`) and the webhook a per-event `GitContext`; #820 already routes the orchestrators through `boundary.providers.*`. What remains is the long tail on the trigger side: eight free-function modules, one barrel, eighteen trigger import lines, three legacy-backed adapter closures, nine transitional allowlist entries whose files are about to disappear or stop constructing, and living docs that still describe `adws/github/` as "the sole interface between ADW's orchestrators and the GitHub platform".

Constraints that shape the solution:

- **No behaviour change.** Same `gh`/`git` commands, same error and swallow policies, same log lines, same HTTP responses from the webhook, same spawn arguments. The GitHub adapter's port methods reproduce the legacy bodies verbatim (#819), so routing through them is behaviour-preserving by construction; the one new port method is built to the same standard.
- **Test changes are call shapes, fixtures and mock paths only.** Every relocated test keeps its assertions; every trigger test that mocked a legacy module path now injects a fake tracker/code host/boundary instead.
- **The transitional allowlist only shrinks.** Every entry whose file is deleted, or which stops constructing, must be removed — the ratchet in `checkGitGhGuard.ts` fails the build otherwise. Files that keep a `gitContextForSync`/`gitContextForRepo` construction (`takeoverHandler`, `cancelHandler`, `devServerJanitor`, `trigger_webhook`'s `/health`, `webhookHandlers`) keep their entries: retiring those constructions is #822's enumerated scope.
- **`adws/providers/` must stay extraction-clean.** `repoContext.ts` (outside `EXTRACTION_SCOPE` until #823) may import `adws/forge/`; nothing inside the scope may.
- **Files already over the 300-line cap must not grow**: `trigger_cron.ts` (565), `trigger_webhook.ts` (362). `takeoverHandler.ts` (293) shrinks by its deleted boundary-less wiring.

## Solution Statement

1. **Widen one port, forge-neutrally.** `PullRequestRecord { number, body, state, mergedAt }` and `CodeHost.listPullRequests()` in `adws/providers/types.ts`; the GitHub implementation parses `fetchAllPRs()` and throws on failure (callers own the swallow, as `listMergedPullRequests` does); GitLab refuses by name; exec-fake and refusal tests.
2. **Relocate the ADW-application remnants to `adws/forge/`** as construction-free helpers: `issueLinkMarker` (verbatim), `linkedPrDetector` (`fetchLinkedPRs(codeHost)`), `hitlBoardNotifier` (required `NotifierDeps` + the moved `buildNotifierDeps(ctx, repoId)`), `prCommentDetector` (`buildUnaddressedCommentReads(boundary)` / `hasUnaddressedComments(prNumber, boundary)` over `adws/core/unaddressedComments.ts`), `workflowCommentsBase` (`isAdwRunningForIssue(issueNumber, tracker)`), `workflowCommentsIssue`, `workflowCommentsPR`, `proofCommentFormatter` (verbatim), and `adwLabelProvisioning` (`ensureAdwLabelsExist(repoId, tracker, logger)`). Their tests move with them; the callers outside the triggers re-point.
3. **Thread the boundary through the triggers.** The cron already holds `cronBoundary`; the webhook builds a per-event `LaunchBoundary`. Every trigger entry point that took a `repoInfo` (plus an optional `gitContext`) takes the boundary, or the narrowest `Pick<>` of its providers, instead: `classifyAndSpawnWorkflow`, `routeIssueOpened`, `handleIssueClosedEvent`, `handlePullRequestEvent` (deps), `handleIssueClosedDependencyUnblock`, `closeAbandonedDependents`, `checkIssueEligibility`, `findOpenDependencies`, `isConcurrencyLimitReached`, `registerRegionOverlapBlocker`, `handleCancelDirective`, `evaluateCandidate`, `buildDefaultTakeoverDeps`, `scanAuthQueue`, `resolvePrReviewSpawn`, `mergeWithConflictResolution`. Every `repoInfo` a bound provider makes redundant is dropped (the #796/#820 discipline); `adws/core/remoteReconcile.ts`'s two ignored positionals — kept in #820 "only because its trigger caller is #821's" — go with them.
4. **Delete the legacy layer**: `githubApi.ts`, `issueApi.ts`, `prApi.ts`, `projectBoardApi.ts`, `issueListApi.ts`, `labelManager.ts`, `workflowComments.ts` (a barrel-of-barrels with no direct importer), `index.ts`, and the whole `adws/github/__tests__/` directory (tests relocated to their new owners or dropped where the adapter suite already holds the same assertion). `adws/github/` ends as exactly `gitContextFactory.ts` + `githubAppAuth.ts`.
5. **Shrink the guard**: nine transitional entries removed (the eight `adws/github/*` sites and `adws/triggers/autoMergeHandler.ts`); `getRepoInfo` — a function that no longer exists — leaves the identity rule's cwd-read set and the guard test's declaration table.
6. **Update tests by call shape, the BDD step files by import path and call shape, the living docs, the registry and README; run every validation command**, including a mechanical AC grep and an `ls adws/github` check.

### Edge Cases
- **Webhook payload without a `repository` object**: `pull_request`, `issues.closed` and `issues.opened` events answer `200 { status: 'ignored', reason: 'no_repository' }`; `issue_comment` events fall back to the memoised self-host boundary — the same local-remote identity the deleted `getRepoInfo()` produced. - **Per-event boundary construction fails** (no token for that repo): warn line as today; the event answers `ignored`/`boundary_unavailable` instead of throwing inside a legacy free function and being reported as a handler failure. The process never dies (#776 invariant).

- **Upgrade-label gate when the label read fails**: `fetchLabels` is fail-open (`[]` + warn) → the issue is treated as not an upgrade issue, the same outcome `issueHasLabel`'s `false` produced.
- **Label persistence on a repo lacking the label**: `tracker.applyLabel` lazy-creates with the catalogue colour (wired in `repoContext.ts`) and retries once; a non-not-found error surfaces into the gatekeeper's existing warn.
- **Self-host cron auth-queue resume**: `scanAuthQueue` now hands `evaluateCandidate` the boundary, so worktree paths resolve from the boundary's (self-host) base path — the same path the orchestrator itself used — instead of the previous `selfHost: false` fallback context. The reset/probe seams still build a `selfHost: false` context (#822 aligns them).
- **HITL notification without a `GitContext` on the config** (test fixtures only): skipped with a warn; never constructs a context.
- **`resolvePrReviewSpawn` on a PR whose fetch fails**: `fetchPullRequest` throws the same `Failed to fetch PR #N: …` message; the cron's per-PR catch and the webhook's failure reporter handle it as before.
- **GitLab-configured repo hitting a widened method**: `listPullRequests` refuses by name; the forge detector's catch turns it into `[]` (concurrency limit never reached, label recovery unaffected) — the same non-fatal outcome `fetchLinkedPRs` had for any error.
- **Construction in a relocated module**: any `gitContextFor*`/`new GitContext` in `adws/forge/` is an `unsanctioned-construction` violation — the allowlist cannot grow.
