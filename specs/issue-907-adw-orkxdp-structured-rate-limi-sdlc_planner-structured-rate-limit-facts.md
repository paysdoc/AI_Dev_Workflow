## Feature Description

Make every rate-limit decision in ADW rest on structured facts from the Claude CLI's `--output-format stream-json` output, along the whole chain: `adws/core/claudeStreamParser.ts` → `adws/agents/agentProcessHandler.ts` / `adws/agents/claudeAgent.ts` → `RateLimitError` (`adws/types/agentTypes.ts`) → the pause-queue probe classifier in `adws/triggers/rateLimitProbe.ts`.

Three things are wrong in that chain today:

1. **The overloaded branch has never fired.** The parser tests the documented `system`/`api_retry` message against `error === 'overloaded_error'`. The documented enum value is `overloaded`. Recorded agent output on this host (`agents/*/*/output.jsonl`, 44 `api_retry` events across many runs) shows the CLI emitting `overloaded` (30 events, `error_status: 529`), `rate_limit` (10 events, `error_status: 429`), `server_error` and `unknown`, and never `overloaded_error`. Overloads were only ever caught by the generic "second consecutive retry of anything" rule. No real fixture proves the old value, so it goes.
2. **The reset facts are thrown away and the terminal error status is never read.** The `rate_limit_event` carries `rate_limit_info.resetsAt` (Unix epoch seconds) and `rateLimitType` (`five_hour`, `seven_day`); the parser only reads `status`. The `result` envelope carries `api_error_status` (`null` on success, the HTTP status on an API failure); the parser never reads it. In the 2026-09-22 incident the agent output for #840 carried both a rejected event with the 12:50 UTC reset time and a `result` with `api_error_status: 429`, and nothing downstream could use either.
3. **The probe still guesses from text and calls an expired login a limit.** The classifier introduced by #903 ends with a hand-kept substring list (`You've hit your`, `You're out of extra usage`, `502 Bad Gateway`, `Invalid authentication credentials`), so a CLI wording change can strand paused workflows again, and it maps `authErrorDetected` to `limited`, so an expired OAuth session is probed silently forever instead of counting toward the strike budget.

After this feature:

- `JsonlParserState` exposes `rateLimitDetected` (renamed from `rateLimitRejected`, because a documented 429 sets it as well as the event) plus `rateLimitType` and `resetsAt`, both optional and captured only from a **rejected** `rate_limit_event`.
- Detection is ranked. The documented `api_retry` `error` enum and its `error_status` (`401` auth, `429` rate limit, `529` overloaded, other `5xx` server error), and the `result` envelope's `api_error_status`, decide *whether* a run is auth-failed, rate-limited, overloaded or server-errored. The undocumented `rate_limit_event` still marks a rejected run as rate-limited (that is how a session limit surfaces), but its unique contribution is the limit type and reset time.
- `AgentResult` and `RateLimitError` carry `rateLimitType` / `resetsAt` when the parser captured them, so the PRD's wait policy (a later issue) can decide without re-parsing.
- `classifyProbeResult` and `probeRateLimit` return `{ verdict, rateLimitType?, resetsAt? }`. The verdict set becomes `clear | limited | failed | unknown`. The substring list and its helpers are deleted. Output with no parseable JSON is `unknown`. An authentication failure is `failed`, a confirmed non-rate-limit failure.

**The documented contract this plan leans on** (Claude Code headless docs, "Handle API retries", checked 2026-09-25): `api_retry.error` ∈ {`authentication_failed`, `oauth_org_not_allowed`, `account_on_hold`, `billing_error`, `rate_limit`, `overloaded`, `invalid_request`, `model_not_found`, `server_error`, `max_output_tokens`, `cloud_credential_error`, `unknown`}; `error_status` is an integer **or `null`** (no HTTP response); `attempt` starts at 1. The `result` envelope as emitted today is snake_case (`is_error`, `api_error_status`, `num_turns`, `session_id`, `duration_ms`); ADW's `ClaudeCodeResultMessage` still declares the older camelCase names. Correcting that drift and the conformance fixtures belongs to the PRD's envelope-gate issue, not this one; this plan only adds the two snake_case fields it reads.

## User Story
As an ADW operator
I want rate-limit detection, the rate-limit error, and the pause-queue probe to decide from the CLI's documented structured signals and to carry the limit type and reset time
So that a wording change in the CLI can never strand a paused workflow again, an expired login is treated as a failure instead of a limit, and the upcoming wait policy and pause-queue decider can use the reset time the CLI already reports

## Problem Statement

ADW has two rate-limit detectors (the live-agent handler and the pause-queue probe) that share one parser, but the parser classifies the documented retry message against a value the CLI does not emit, discards the only machine-readable reset time it is ever given, and ignores the terminal `api_error_status`. The probe layered on top of it keeps a text list as a safety net, which is the exact failure class that caused the 2026-09-22 and 2026-09-24 incidents, and it cannot tell an expired login from a limit. Every later step of the PRD (wait until the reset time, gate the scanner on it, count strikes only for confirmed failures) needs these facts to exist and to be trustworthy first.

## Solution Statement

1. **One parser, ranked signals, facts captured.** `claudeStreamParser.ts` gets a pure `classifyApiSignal(error, status)` that maps the documented enum and HTTP status to one of `auth | rate_limit | overloaded | server_error`, applied to both `api_retry` and `result.api_error_status`; a `rate_limit_event` handler that sets `rateLimitDetected` and captures `rateLimitType` / `resetsAt` only when `status === 'rejected'`; and a `createJsonlParserState()` factory so the four places that hand-build the state stop drifting.
2. **Facts travel with the error.** `RateLimitFacts` (in `agentTypes.ts`) is mixed into `JsonlParserState`, `AgentResult`, `RateLimitError` and the probe's `ProbeClassification`. `agentProcessHandler` copies the facts onto the rate-limited `AgentResult`; `claudeAgent` passes them into `new RateLimitError(agentName, facts)`.
3. **Probe decides from structure only.** `rateLimitProbe.ts` loses its text patterns; `classifyProbeResult` ranks `failed` (auth) above `limited` (rate limit / overloaded / server error) above `clear` (exit 0 and a non-errored `result` envelope) above `unknown` (everything else, including output with no JSON). `probeRateLimit` returns the classification; `pauseQueueScanner` reads `.verdict` and otherwise keeps today's behaviour (`failed` follows the same strike path as `unknown` until the PRD's decider issue).
4. **Every branch pinned by unit tests** from one hand-written incident fixture shared by the parser, handler and probe tests, and the #902 scenarios/step definitions that encoded the text fallback are updated to the new contract so `bun run test` (tsc) and `@adw-902` stay green.

### 4. Rewrite the parser's signal handling in `adws/core/claudeStreamParser.ts`
- Add a pure `classifyApiSignal(error: unknown, status: unknown): 'auth' | 'rate_limit' | 'overloaded' | 'server_error' | undefined` evaluated in this order (ranking): `auth` when `error === ApiRetryErrorKind.AuthenticationFailed || status === HTTP_UNAUTHORIZED`; `rate_limit` when `error === RateLimit || status === HTTP_TOO_MANY_REQUESTS`; `overloaded` when `error === Overloaded || status === HTTP_OVERLOADED`; `server_error` when `error === ServerError || isServerErrorStatus(status)`; else `undefined`. Treat a non-number `status` (including `null`) as "no status".
- Extract three named handlers so `parseJsonlOutput`'s loop body stays at depth ≤ 2 (coding guideline "Nesting & Extraction"):
  - `applyRateLimitEvent(state, record)` — only when `rate_limit_info.status === 'rejected'`: set `rateLimitDetected = true`, and set `rateLimitType` when it is a string and `resetsAt` when it is a finite number (the last rejected event wins). A non-rejected event (`allowed`, `allowed_warning`) changes nothing, even if it carries `resetsAt`.
  - `applyApiRetrySignal(state, record)` — `kind = classifyApiSignal(record.error, record.error_status)`. `auth` → `authErrorDetected = true` (any attempt, as today). `rate_limit` → `rateLimitDetected`, `overloaded` → `overloadedErrorDetected`, `server_error` **or `undefined`** (`unknown`, `billing_error`, …) → `serverErrorDetected`, each only when `attempt >= PAUSE_ON_RETRY_ATTEMPT`. See the Notes for why the transient categories keep the second-attempt threshold.
  - `applyResultSignal(state, record)` — `kind = classifyApiSignal(undefined, record.api_error_status)`; a terminal result is not a retry, so the mapping fires immediately: `auth` → `authErrorDetected`, `rate_limit` → `rateLimitDetected`, `overloaded` → `overloadedErrorDetected`, `server_error` → `serverErrorDetected`; `null`/absent/4xx → nothing. Keep setting `state.lastResult`.
- Delete the `overloaded_error` and `startsWith('authentication')` checks: no real fixture proves either value (the recorded outputs and `adws/known_issues.md` show `overloaded` and `authentication_failed` with their HTTP codes), and the status-code half of the ranking already covers any future wording.
- Keep `compact_boundary`, `tool_result` counting, assistant handling and the line buffering exactly as they are.

### Edge Cases
- `rate_limit_event` rejected but missing `resetsAt` or `rateLimitType`, or carrying a non-numeric `resetsAt`: flag set, facts absent.

- Two rejected events in one stream: the later one's facts win.
- `api_retry` with `error_status: null` (no HTTP response) and `error: 'unknown'`: attempt 1 nothing, attempt 2 `serverErrorDetected`.
- `api_retry` with a contradictory pair (`error: 'rate_limit'`, `error_status: 401`): `auth` wins (ranking).
- `api_retry` for a documented but non-pause category (`invalid_request`, `billing_error`, `model_not_found`): attempt 1 nothing, attempt 2 `serverErrorDetected` (unchanged repeated-retry rule, see Notes).

## Notes
- If `.adw/coding_guidelines.md` exists in the target repository (or `guidelines/coding_guidelines.md` as a fallback), strictly adhere to those coding guidelines. If necessary, refactor existing code to meet the coding guidelines as part of implementing the feature. Concretely for this feature: keep `parseJsonlOutput` flat by extracting the three signal handlers; no magic strings/numbers (enum + status constants); comments only for invariants and non-obvious rationale (the threshold, the "rejected only" capture rule, the snake_case/camelCase drift); no issue numbers in code comments.
- **Decision — retry threshold for transient categories.** `api_retry` `rate_limit`/`overloaded`/`server_error`/unclassified set their flags only from the second consecutive attempt (`PAUSE_ON_RETRY_ATTEMPT = 2`); auth fires on the first, and a terminal `result.api_error_status` fires immediately. Evidence from the recorded outputs on this host: `rate_limit` retries appear 6 times at attempt 1 and 4 times at attempt 2, `overloaded` 17 times at attempt 1 and 13 at attempt 2 — a meaningful share of first retries resolve inside the CLI's own backoff (about one second). Because the old `overloaded_error` check never matched, production has in fact always paused on the second attempt for every transient category; keeping that threshold fixes the classification without turning a one-second transient into a five-minute pause and a phase restart. The ranking the PRD asks for (enum and HTTP code decide the category, the event only supplies facts) is unaffected. Flip the constant to 1 if the operator prefers immediate pausing.
- **Decision — a fourth probe verdict.** `failed` is introduced rather than folding auth into `unknown`, because the PRD distinguishes "confirmed non-rate-limit failure" from "could not classify" (story 10 vs. story 28/29) and the decider issue will treat them differently (eviction message, logging). In this issue both still count a strike, so scanner behaviour is unchanged.
- **Decision — `clear` requires a result envelope.** A probe that exits 0 without any JSON used to be `clear`; it is now `unknown` (the PRD: "never guesses from text"). The only known exit-0-without-result producer is a broken or truncated CLI run, which should count a strike.
- **Out of scope, deliberately:** threading the facts into `handleRateLimitPause` / `PausedWorkflow` (PRD "Pause queue" issue), the wait policy in the phase runner (PRD "Wait policy" issue), the scanner decider and per-repo ownership, correcting `ClaudeCodeResultMessage`'s camelCase fields and the `adws/jsonl/fixtures/*.jsonl` shapes (`bun run jsonl:check` already fails at baseline — 4 of 4 fixtures — and is owned by the envelope-gate issue; do not add it to validation), and any `## Retry` change.
- The `rate_limit_event`'s `resetsAt` is Unix epoch **seconds** (e.g. `1790081400`); do not convert to milliseconds or ISO at the parser boundary. Consumers convert.
- The 2026-09-22 incident's rejected event was not recorded on this host (only `allowed` events with `resetsAt` and `unifiedWindows` are), so the fixture is hand-written per the issue; its `result` line uses `subtype: error_during_execution` and `terminal_reason: api_error` as the issue specifies. The PRD's envelope-gate issue will replace it with a captured one.
