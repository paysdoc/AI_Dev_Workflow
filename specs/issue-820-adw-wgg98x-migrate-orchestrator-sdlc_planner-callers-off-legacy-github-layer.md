Four callers listed in the issue need no forge change: `adws/phases/autoMergePhase.ts` and `adws/phases/docsSelfCheck.ts` already import nothing from `adws/github` (#796 finished them), `adws/proof/types.ts` only carries the `CommenterFn` shape (updated with the publisher), and `adws/adwMerge.tsx`'s one import is a dead dependency.

Three things make this more than an import swap:

1. **Two forge-shaped records are load-bearing for prompt fidelity.** `WorkflowConfig.issue` is the full `GitHubIssue` and is `JSON.stringify`'d into the commit, PR, alignment and validation agents' prompts (`buildPhase.ts:235`, `prPhase.ts:39,62`, `alignmentPhase.ts:143,205`, `planValidationPhase.ts:173,287`, `documentPhase.ts:122`, `planPhase.ts:142`); `planAgent.ts:37-40` and `scenarioAgent.ts:46-49` print `issue.state`, `issue.author.login`, `issue.createdAt`; `buildAgent.ts:116` prints `issue.url`. The port's `Issue` has none of `createdAt`/`url`/`author.login`, so reading the issue through `IssueTracker.fetchIssue` would change the bytes every agent sees. The issue record therefore keeps its shape and is read by a new core helper over the **boundary's own `GitContext`** using the adapter's parser — the legacy function's exact command, parse and error text, reached over the one context the process constructed. This is the single GitHub-shaped read left in the framework and is called out in Notes.
2. **The ports lack five things the callers need.** A synchronous issue-title read (`adwClearComments`), a pull request's `state` (`prReviewPhase` exits on CLOSED/MERGED), a comment author's bot flag and the authenticated login (the unaddressed-comment filter), and an approval-capability question (`reviewPhase`'s `isGitHubAppConfigured() && GITHUB_PAT` gate is a GitHub-specific probe standing in a forge-neutral phase). Each is widened forge-neutrally in `adws/providers/types.ts`, implemented in the GitHub adapter from the same `gh` commands it already runs, and refused by name on GitLab/Jira — except the capability question, which answers `false` there (a probe that throws is not a probe).
3. **Two core defaults exist only for boundary-less trigger callers.** `remoteReconcile.ts`'s `buildLegacyReconcileDeps` and `issueClassifier.ts`'s `fetchGitHubIssue` default are reached only from `adws/triggers/takeoverHandler.ts` and `adws/triggers/webhookGatekeeper.ts`. AC1 covers `adws/core/`, so both defaults go: the two trigger files take the legacy wiring themselves (the one-line adaptations #821 then replaces with the boundary providers). Those are the only trigger-side edits in this slice.

The pure ADW label vocabulary (`ADW_*_LABEL` constants, `ADW_LABEL_DEFINITIONS`, `readAdwLabelNames`, `shouldSkipScenarioAuthoring`, `hasRegressionPromotionLabel`, `hasWontFixLabelName`, …) is not a forge operation, but it lives in two of the seven modules the issue names. It moves to `adws/core/adwLabels.ts` — the home #821 already assigns it ("`adws/core/` for the label policy") — and `labelManager.ts`/`prApi.ts` re-export it, so trigger callers, the barrel and every existing test keep working unchanged. After that move, AC1 is verifiable by a single grep (see Validation Commands).

The GitHub-App environment wrapper (`adws/github/githubAppAuth.ts`, the one `process.env.GITHUB_APP_*` reader) moves verbatim to `adws/core/githubAppAuth.ts`, leaving a re-export shim at the old path for `gitContextFactory.ts` and the barrel until #823 retires them.

## Problem Statement

`adws/github/*` free functions each open with `createGhRepoApi(gitContextForRepo(repoInfo))` — a fresh, caller-assembled identity per call. Every `repoInfo` parameter threaded to them is a wrong-repo hazard, and several callers fill that parameter from `getRepoInfo()`, a read of the *local git remote* of the process's cwd: `adwClearComments.tsx:65` (`repoInfo ?? getRepoInfo()` — run it inside a worktree whose remote names another repository and the deletions land there), `orchestratorLock.ts:29` (the spawn-lock namespace), `proofPublishPhase.ts:34`, `depauditSetup.ts:71`, `stackCoherenceReporter.ts:29`, `unitTestPhase.ts:136`, and the `repoContext?.repoId.owner ?? getRepoInfo().owner` idiom in five phases. `workflowInit.ts:132,153,222` reads the local remote three times in the one function whose job is to establish which repository the run is about — even though `buildLaunchBoundary` resolved that identity on line 140.

The launch boundary (#794) already hands every process a `GitContext` and a bound provider triple, and #796 moved the label/PR/approval operations onto the ports and made `WorkflowConfig.repoContext` the boundary's triple. What remains is the long tail: identity fallbacks, a handful of operations the ports cannot express yet, two core defaults kept alive for boundary-less triggers, an orchestrator (`adwPrReview.tsx:99-102`) that performs its branch→PR lookup three lines *before* it builds the boundary, and pure label vocabulary that has no non-legacy home.

Constraints that shape the solution:

- **No behaviour change.** Same `gh`/`git` commands, same error and swallow policies, same log lines, same prompt bytes. The GitHub adapter's port methods already reproduce the legacy bodies verbatim (#819), so routing through them is behaviour-preserving by construction; the new port methods must be built to the same standard.
- **AC3 forbids expectation changes beyond call shapes.** Unit tests and step definitions may change how they *call* (dropped `repoInfo` parameters, injected deps, mock paths) and what fixtures they build, never what they assert about behaviour.
- **AC2 forbids new transitional construction sites.** `adws/guard/constructionRule.ts`'s transitional list may only shrink; its stale-entry ratchet fails the build when a listed file stops constructing. Exactly one file in this slice stops constructing (`adws/core/remoteReconcile.ts`); its entry must be removed. The `gitContextFor`/`gitContextForSync` constructions in the worktree-owning phases and `workflowInit` are **#822's** remit (its issue body lists those files by name) and stay, imported by deep path instead of through the barrel.
- **The scenario file already exists.** `features/per-issue/feature-820.feature` (untracked, written by the scenario phase) pins the behaviours below and names three port widenings (`getIssueTitle`, `canApprovePullRequests`, a composite unaddressed-comment read). This plan adopts the first two, decomposes the third into two smaller forge-neutral widenings plus a core composite, and lists in Notes the four places the alignment phase must reconcile.

## Solution Statement

1. **Pure moves first, no behaviour.** `adws/core/adwLabels.ts` receives the label vocabulary verbatim from `labelManager.ts` (+ `hasWontFixLabelName` from `prApi.ts`, + the label-definition resolver duplicated in `repoContext.ts`); both legacy files re-export. `adws/core/githubAppAuth.ts` receives the env wrapper verbatim; the old path becomes a shim.
2. **Widen the ports forge-neutrally**, each implemented in the GitHub adapter from a command it already issues and refused by name elsewhere: `IssueTracker.getIssueTitle(n): string` ('(unknown)' on error), `CodeHost.getAuthenticatedUser(): string | null`, `CodeHost.canApprovePullRequests(): boolean` (GitHub answers from an injected ADW-wired seam; GitLab answers `false`), `PullRequest.state: string`, `ReviewComment.isBot?: boolean`.
3. **Three small core modules absorb the composites the callers need**, over injected reads so they are hermetically testable: `fetchIssueRecord(ctx, n)` (the full issue record over the boundary context), `readUnaddressedComments(prNumber, reads)` (the pr-review filter, formerly `prCommentDetector.getUnaddressedComments`, which becomes a thin legacy wrapper over it for `trigger_cron`), and `resolvePrReviewInvocation(positionals, deps)` (the branch→PR/adwId resolution lifted out of `adwPrReview.tsx`'s `main()` so it can run *after* the boundary is built and be driven from a test). One phase helper, `resolveWorkflowRepoId(config)`, replaces every `?? getRepoInfo()` fallback with `repoContext.repoId → gitContext → targetRepo`, throwing an actionable error when a config carries none.
4. **Migrate the callers** to `boundary.providers.*` / `config.repoContext.*`, dropping every `repoInfo` parameter the bound providers make redundant (`UpgradeClaimDeps`, `UpgradeGateParams`, `CommenterFn`, `ClassifyIssueForTriggerDeps`). Where a phase has no `repoContext`, it skips the forge operation with a log line — the #796 precedent (`depauditSetup`, `documentPhase`'s self-check, `autoMergePhase`) — rather than constructing anything.
5. **Push the two boundary-less defaults down into their trigger callers** (`takeoverHandler.ts`, `webhookGatekeeper.ts`, `cancelHandler.ts`) as legacy-backed adapters of the new shapes, so `adws/core/` and the orchestrators are clean now and #821 deletes those adapters from its own files.
6. **Retire the one stale guard entry**, update tests by call shape only, implement `@adw-820` step definitions on feature-796's harness, and update the living docs.
